# Proposal: Harden gh CLI repo targeting across all orchestration templates

## Goal

Ensure every `gh` CLI invocation in orchestration templates explicitly targets the correct repository, and add infrastructure-level defense against `gh-resolved` poisoning in `createWorktrees()`.

## Acceptance Criteria

- [ ] `pr-comments.md`: all `gh pr view` calls include `{{#IF PROJECT_REPO}}--repo "{{PROJECT_REPO}}" {{/IF}}` and reference the PR URL from `{{PR_FILE}}`
- [ ] `pr-conflict-resolve.md`: all `gh pr view` calls include `{{#IF PROJECT_REPO}}--repo "{{PROJECT_REPO}}" {{/IF}}` and reference the PR URL from `{{PR_FILE}}`
- [ ] `final-merge.md`: `gh pr merge` includes `{{#IF PROJECT_REPO}}--repo "{{PROJECT_REPO}}" {{/IF}}` and references the PR URL from `{{PR_FILE}}`
- [ ] `createWorktrees()` in `src/orchestration/worktrees.ts` clears `gh-resolved` on `origin` and `upstream` remotes after worktree creation as defense-in-depth
- [ ] Existing tests pass; new test(s) verify the `gh-resolved` clearing in `createWorktrees()`
- [ ] No regressions in templates that already have correct `--repo` targeting (pr-create, pair-coder-pr-create, forward-pr, upstream-final-merge, suggest-refactor)

## Context

This is the hardening follow-up from gh-ludics-302, which fixed `gh pr create` misdirection by adding `--repo` to two templates and clearing `gh-resolved` in the upstream-related templates. Three templates with `gh` commands were left vulnerable:

- **`pr-comments.md`** — bare `gh pr view` (no PR URL, no `--repo`)
- **`pr-conflict-resolve.md`** — three bare `gh pr view` calls (no PR URL, no `--repo`)
- **`final-merge.md`** — bare `gh pr merge` (no PR URL, no `--repo`)

Additionally, `createWorktrees()` does not clear `gh-resolved`, leaving all worktrees exposed to any pre-existing `gh-resolved` markers in the parent repo's git config.

**Prior work update**: task-d900db5d already removed `PR_CREATE_REPO_FLAG` from `buildSkillContext()` and inlined repo targeting using `{{#IF PROJECT_REPO}}--repo "{{PROJECT_REPO}}" {{/IF}}` conditionals. This task extends that same pattern to the three remaining vulnerable templates, making the original "rename to GH_REPO_FLAG" plan unnecessary.

## Approach

### A. Fix vulnerable templates (same pattern as pr-create.md)

All three templates need two changes: (1) pass the PR URL explicitly, and (2) add the `--repo` conditional.

**`pr-comments.md`** (line 7) — change:
```
gh pr view --json reviews,comments --jq '.reviews,.comments'
```
to:
```
PR_URL=$(cat "{{PR_FILE}}" 2>/dev/null)
gh pr view "$PR_URL" {{#IF PROJECT_REPO}}--repo "{{PROJECT_REPO}}" {{/IF}}--json reviews,comments --jq '.reviews,.comments'
```

**`pr-conflict-resolve.md`** — add `PR_URL` extraction at the top and use it in all three `gh pr view` calls:
```
PR_URL=$(cat "{{PR_FILE}}" 2>/dev/null)
```
Line 12: `gh pr view "$PR_URL" {{#IF PROJECT_REPO}}--repo "{{PROJECT_REPO}}" {{/IF}}--json baseRefName -q .baseRefName`
Line 24: `gh pr view "$PR_URL" {{#IF PROJECT_REPO}}--repo "{{PROJECT_REPO}}" {{/IF}}--json mergeable`
Line 31: `gh pr view "$PR_URL" {{#IF PROJECT_REPO}}--repo "{{PROJECT_REPO}}" {{/IF}}--json reviews,comments --jq '.reviews,.comments'`

**`final-merge.md`** (line 7) — change:
```
gh pr merge --merge --delete-branch
```
to:
```
PR_URL=$(cat "{{PR_FILE}}" 2>/dev/null)
gh pr merge "$PR_URL" {{#IF PROJECT_REPO}}--repo "{{PROJECT_REPO}}" {{/IF}}--merge --delete-branch
```

### B. Clear `gh-resolved` in `createWorktrees()`

After all worktrees are created (after the `ensureGitExcludes` loop, before the `return`), add:

```typescript
// Defense-in-depth: clear gh-resolved markers to prevent gh CLI misdirection.
// Worktrees inherit the parent's .git/config, so clearing on projectDir is sufficient.
for (const remote of ["origin", "upstream"]) {
  safeSyncOutput(
    ["git", "config", "--unset", `remote.${remote}.gh-resolved`],
    { cwd: projectDir },
  );
}
```

Hardcoding `origin` and `upstream` is sufficient per resolved question #1 — these are the remotes with repos specified in the global config.

### C. Tests

- Add a test in `skills.test.ts` (or `worktrees.test.ts`) that renders the updated templates and verifies the `--repo` pattern appears in `pr-comments`, `pr-conflict-resolve`, and `final-merge` templates when `PROJECT_REPO` is set.
- For `createWorktrees()`: the `gh-resolved` clearing uses `safeSyncOutput` which is best-effort (no throw on failure). A unit test can mock `safeSyncOutput` and verify it was called with the expected `git config --unset` args, or an integration-style test can set `gh-resolved` in a test repo and verify it's cleared after `createWorktrees()`.

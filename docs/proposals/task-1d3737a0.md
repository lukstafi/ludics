# Proposal: Clean up config CLI — extract findProjectConfig helper, move to config-cli.ts, type ProjectConfig

**Task**: task-1d3737a0  
**Project**: ludics  
**Effort**: small  
**Status**: ready to implement

---

## Goal

Remove duplicated project-matching logic spread across `src/index.ts`, `src/adapters/tmux-adapter.ts`, and `src/adapters/t3code.ts` by consistently using the existing `findProjectConfig()` helper from `src/config.ts`. Move the inline `config` command handler out of `src/index.ts` into its own `src/config-cli.ts` module, and eliminate the unnecessary `(p: any)` cast.

---

## Acceptance Criteria

1. A `src/config-cli.ts` file exists, exporting `runConfigCli(args: string[]): Promise<void>`, containing the full `config` subcommand handler logic.
2. `src/index.ts` references `runConfigCli` for the `config:` command, with no inline handler logic remaining.
3. The `(p: any)` cast in the config handler is gone; `findProjectConfig()` is used instead and `ProjectConfig` is used as the type where needed.
4. `src/adapters/tmux-adapter.ts`: the `stagingRepo` IIFE calls `findProjectConfig(projectDir, cfg)?.staging_repo` instead of duplicating the matching logic inline.
5. `src/adapters/t3code.ts`: same replacement as above.
6. All existing tests pass. No behavior change in any of the affected commands.

---

## Context

After PR #173 merged the `proposals-path` subcommand, three cleanup items were identified:

- The `config:` handler in `src/index.ts` (lines 53–81) re-implements project matching with `(p: any)` casts instead of calling `findProjectConfig()` which already exists in `src/config.ts` (lines 258–274).
- `src/adapters/tmux-adapter.ts` (lines 467–481) contains an IIFE that duplicates the same path-expansion + basename fallback logic, only to extract `staging_repo`.
- `src/adapters/t3code.ts` (lines 891–905) contains an identical IIFE.
- `src/mag.ts` (line 860) has a simpler name-only match; see note below.

`findProjectConfig(projectDir, cfg?)` accepts the resolved project directory and an optional pre-loaded config, so it fits all three call sites without any semantic change.

---

## Approach

### Step 1 — Create `src/config-cli.ts`

Create `src/config-cli.ts` with:

```ts
import { findProjectConfig, loadConfigSync, resolveProjectPath, resolveProposalsPath } from "./config.ts";

export async function runConfigCli(args: string[]): Promise<void> {
  const sub = args[0] ?? "";
  if (sub === "proposals-path") {
    const project = args[1];
    if (!project) {
      console.error("usage: ludics config proposals-path <project>");
      process.exit(1);
    }
    const projectDir = resolveProjectPath(project);
    if (!projectDir) {
      console.error(`project not found: ${project}`);
      process.exit(1);
    }
    const cfg = loadConfigSync();
    const projCfg = findProjectConfig(projectDir, cfg);
    console.log(resolveProposalsPath(projectDir, projCfg?.proposals_path));
  } else {
    console.error(`unknown config subcommand: ${sub} (available: proposals-path)`);
    process.exit(1);
  }
}
```

### Step 2 — Update `src/index.ts`

Replace the inline `config:` handler (lines 53–81) with:

```ts
config: async (args) => {
  const { runConfigCli } = await import("./config-cli.ts");
  await runConfigCli(args);
},
```

(Use a dynamic import consistent with how other command modules are imported in this file.)

### Step 3 — Update `src/adapters/tmux-adapter.ts`

Add `findProjectConfig` to the existing import from `"../config.ts"` (line 10 currently imports only `loadConfigSync`), then replace the `stagingRepo` IIFE:

```ts
stagingRepo: (() => {
  const cfg = loadConfigSync();
  return findProjectConfig(projectDir, cfg)?.staging_repo || undefined;
})(),
```

### Step 4 — Update `src/adapters/t3code.ts`

Same pattern as Step 3 — add `findProjectConfig` to the existing import (line 21), replace the IIFE.

### Step 5 — `src/mag.ts` (optional / deferred)

The match at line 860 in `mag.ts` operates on a project name string (not a resolved directory path), and `findProjectConfig` requires a directory. Converting it would require calling `resolveProjectPath` first, adding a filesystem probe in a code path where no probe exists today. Leave this as-is unless a future task adds a name-based overload to `findProjectConfig`.

Run existing tests. No behavior should change.

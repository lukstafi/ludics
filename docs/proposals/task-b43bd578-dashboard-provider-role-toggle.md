# Dashboard top-bar provider-role toggle (coder / reviewer / none)

**Task:** task-b43bd578
**Project:** ludics

## Goal

Add a top-bar control on every dashboard page (immediately to the left of the
theme switcher) that lets the user pick which configured **provider** is the
default coder and which is the default reviewer for newly auto-filled slots.
The control is a row of per-provider toggles, each with three states:
`coder` / `reviewer` / `none`. The state is constrained so that at most one
provider holds `coder` and at most one holds `reviewer`; selecting a role
that is already taken cascades the displaced provider to the other role if
that other role is vacant, else to `none`.

Today the read-side defaults already exist as
`mag.orchestration.default_coder` and `mag.orchestration.default_reviewer`
in `config.yaml`, consumed by `selectOrchestrationFlags`
(`src/adapters/t3code.ts`) and by `expandDuoSlots`
(`src/slots/duo-expand.ts`). There is no write-side UI today. This task
adds that UI plus the round-trip API and a dashboard data file exposing the
current values to the client.

## Acceptance Criteria

1. **Top-bar control rendered on every dashboard page.** A new element with
   class `role-switcher` is injected into `.status-bar` by
   `templates/dashboard/nav.js` immediately before the existing
   `.theme-switcher`, so the role-switcher appears to the left of the theme
   switcher on every page that includes `nav.js`
   (`index.html`, `mag.html`, `tasks.html`, `briefing.html`, `health.html`,
   `terminals.html`, `ntfy.html`, `task-creator.html`, `proposal.html`,
   `task.html`, `retrospective.html`).

2. **Hard-coded provider universe.** The two providers exposed in the
   toggle are exactly `claude-code` and `codex`, defined as a literal
   constant in `nav.js` (or a sibling JS module) — *not* derived from
   `config.yaml`'s `adapters:` block. Future provider additions will need a
   separate task that touches `T3ProviderKind` in `src/t3code/types.ts` and
   this constant together.

3. **Three-state per provider.** Each provider row offers three options:
   `coder`, `reviewer`, `none`. The currently-active option is visually
   marked (mirror the `.active` class pattern used by `.theme-btn`).

4. **Invariant: ≤1 coder, ≤1 reviewer.** At any time, the rendered toggle
   state satisfies `|{p : role(p) = coder}| ≤ 1` and
   `|{p : role(p) = reviewer}| ≤ 1`. The client enforces this on every
   `setRole` action; the server enforces it again on every
   POST `/api/orchestration-defaults` request and rejects payloads that
   violate the invariant (HTTP 400).

5. **Cascade rule on role acquisition.** When the user clicks `setRole(p, r)`
   where `r ∈ {coder, reviewer}`:
   - find the displaced provider `pOld ≠ p` with `role(pOld) = r` (if any);
   - set `role(p) := r`;
   - if `pOld` exists, let `rOther` be the other role
     (`reviewer` if `r = coder`, else `coder`); if no provider currently
     holds `rOther`, set `role(pOld) := rOther`, else set
     `role(pOld) := none`.

6. **Cascade rule on role release.** When the user clicks `setRole(p, none)`,
   only `p`'s role is cleared; no cascade fires (the ≤1 invariant only
   weakens).

7. **Effective-defaults rendering when keys are unset.** When neither
   `mag.orchestration.default_coder` nor `mag.orchestration.default_reviewer`
   is present in `config.yaml`, the toggle renders `claude-code` as `coder`
   and `codex` as `reviewer` — matching the hard-coded fallbacks in
   `selectOrchestrationFlags` and `expandDuoSlots`. The toggle never renders
   blank slots — every page-load shows a concrete, currently-effective
   assignment.

8. **Server-rendered state, not localStorage.** The control's render state
   on every page load is sourced from a new dashboard data file
   `dashboard/data/orchestration-defaults.json` (generated by
   `dashboard.ts`), *not* from `localStorage`. Re-load after a write reads
   back the persisted value through the same path the auto-fill code uses.

9. **Persistence target = `config.yaml`.** Writes go to
   `mag.orchestration.default_coder` and `mag.orchestration.default_reviewer`
   in `config.yaml`. No sidecar JSON file is introduced. The YAML library
   already in use (`yaml`, imported as `YAML` in `src/config.ts` and
   `src/dashboard-server.ts`) is used via `YAML.parseDocument` + `setIn` +
   `toString` so unrelated keys, key order, and surrounding comments survive
   the round-trip. Loss of comments on the *touched* `default_coder` /
   `default_reviewer` lines is acceptable; do not reflow the rest of the
   file.

10. **POST endpoint `/api/orchestration-defaults`.** A new endpoint in
    `src/dashboard-server.ts` accepts `POST` with a JSON body of shape
    `{ coder: "claude-code" | "codex" | null, reviewer: "claude-code" | "codex" | null }`
    (with `null` meaning "no provider in this role"). It validates:
    - both keys present;
    - each value is either `null` or one of the hard-coded provider names;
    - if both are non-null, `coder !== reviewer`.
    Invalid payloads return HTTP 400 with a JSON `{ error: <reason> }`.
    On success, it rewrites `config.yaml` per AC 9, sets `lastGenerated = 0`
    to trigger regeneration, and returns the new state as JSON:
    `{ coder, reviewer }`.

11. **Read endpoint = static JSON.** The client fetches the current state
    from `data/orchestration-defaults.json` (the generated file under
    `dashboard/data/`). The file is regenerated by `dashboardGenerate` just
    like `adapter.json` and `mag.json`, with shape:
    `{ coder: "claude-code" | "codex" | null, reviewer: "claude-code" | "codex" | null }`.
    Unset config keys serialise as the hard-coded effective defaults
    (`coder: "claude-code"`, `reviewer: "codex"`) — *not* `null` — so the
    UI never has to know about the "unset" case (matches AC 7).

12. **Future-only effect, label states so.** The toggle's section heading
    (or aria-label) reads "Defaults for new sessions" (or equivalent
    wording — implementation may choose, the *semantics* are load-bearing).
    Already-running slots are not affected. Per-task `-A` overrides set via
    `ludics slot N assign -A ...` continue to take precedence over these
    defaults at slot-assign time — no code change required because that
    precedence lives at `selectOrchestrationFlagsForTask`'s callsites and
    those already short-circuit when explicit args are provided.

13. **All-modes scope.** The toggle is visible and writable on every page
    regardless of which `OrchestrationState.mode` (`duo` / `pair` / `solo`)
    tasks happen to use. The proposal *and* the in-PR documentation note
    explicitly that, today, duo mode reads the same two keys to derive its
    swap pair, so changing the toggle does change duo behaviour (no
    "non-duo only" branch). This is intended — once a third provider lands
    in `T3ProviderKind`, the toggle will pick which two providers form the
    duo pair.

14. **Tests — invariant + cascade.** New unit tests cover the cascade rule
    independently of the UI: extract the pure transformation
    `applyRoleChange(state, provider, role) → state'` into a testable
    function (e.g. `templates/dashboard/role-switcher.ts`) and verify:
    - cascade on `setRole("codex", "coder")` when codex was reviewer and
      claude-code was coder → both swap (claude-code becomes reviewer);
    - cascade on `setRole("codex", "coder")` when codex was `none` and
      claude-code was `coder` and no provider held `reviewer` → claude-code
      becomes `reviewer`;
    - cascade on `setRole("codex", "coder")` when codex was `none`,

    - `setRole(p, "none")` clears only `p`'s role;
    - invariant: after every `applyRoleChange` call, at most one provider

15. **Tests — server endpoint.** New tests in `src/dashboard.test.ts` (or

### Constraint-propagation rule (formal restatement)

Let `P` be the provider universe, currently `{claude-code, codex}`. The
toggle state is `role : P → {coder, reviewer, none}`. Invariants:
`|{p : role(p) = coder}| ≤ 1` and `|{p : role(p) = reviewer}| ≤ 1`. On
`setRole(pNew, rNew)`:

```
if rNew == "none":
    role[pNew] = "none"
    return                              # no cascade

pOld = the unique p with p != pNew and role[p] == rNew, or None
role[pNew] = rNew
if pOld is None:
    return
rOther = (reviewer if rNew == coder else coder)
if no provider currently holds rOther:
    role[pOld] = rOther
else:
    role[pOld] = "none"
```

When `|P| = 2`, the cascade collapses to a swap on
`setRole(p, "coder")` while the other p held `coder` and *itself* held
`reviewer` (which never happens because the *other* p held `coder`, not
*itself*) — i.e. the meaningful case is a flip of the previous coder to
reviewer if reviewer is vacant. The N≥3 branch (claude-code coder,
codex reviewer, hypothetical-X = none, then `setRole(X, "coder")`)
demotes claude-code to `none` because reviewer is taken. AC 14 pins this
with a 3-provider fixture so the cascade is verified at the algebra
level even before the live UI exposes N≥3.

### Why server-rendered, not localStorage

The theme toggle uses `localStorage` because rendering is purely
client-side. The role toggle is *consumed server-side* by the auto-fill
code at slot-start time (`selectOrchestrationFlagsForTask` runs in the
Mag/keepalive process, not the browser). If the UI read from
`localStorage`, the displayed state would diverge from what the auto-fill
path actually used. The only consistent source is `config.yaml` itself,
surfaced through a generated JSON data file.

## Approach

*Suggested approach — agents may deviate if they find a better path.*

1. **Pure cascade module** (`templates/dashboard/role-switcher.ts` or
   `.js` — match the existing browser-side file conventions; `links.js`
   and `terminals-reset.ts` are sibling precedents). Export
   `applyRoleChange(state, provider, role)` and the type for `state`.
   Pure function, no DOM, unit-testable under Bun.

2. **`nav.js` injection.** Build the role-switcher DOM (one row per
   provider in the hard-coded universe, each with three buttons), wire
   click handlers to `applyRoleChange` + POST. Insert before the theme
   switcher in `.status-bar`. Fetch initial state from
   `data/orchestration-defaults.json` on every page load.

3. **Data-file generator.** Add `generateOrchestrationDefaults()` to
   `src/dashboard.ts` next to `generateAdapter`, and write its output to
   `dashboard/data/orchestration-defaults.json` near the existing write
   loop. Apply the hard-coded fallbacks when keys are unset.

4. **YAML write helper.** Add a function in `src/config.ts` (or a new
   `src/config-write.ts`) that takes the new `{coder, reviewer}` values,
   uses `YAML.parseDocument` + `setIn` + `toString`, and writes
   `config.yaml` back atomically. Cover with unit tests for round-trip
   preservation of an adjacent comment / unrelated key.

5. **POST endpoint.** Add `/api/orchestration-defaults` to
   `src/dashboard-server.ts`. Validate the body, call the write helper,
   re-read for confirmation, return the new state, set `lastGenerated = 0`.

6. **Tests.** Cascade unit tests (AC 14), server endpoint tests (AC 15),
   generated-data-file test (AC 16), and the live-HTTP smoke probe
   (AC 19).

## Scope

**In scope:**
- New top-bar UI component, injected by `nav.js`, visible on all pages
  that include it.
- New POST `/api/orchestration-defaults` endpoint.
- New `dashboard/data/orchestration-defaults.json` generator.
- New YAML write helper for round-tripping `mag.orchestration.*`.
- Unit tests for the cascade rule, the endpoint, the data file, and the
  YAML helper's round-trip property.
- Live-HTTP smoke transcript (AC 19).

**Out of scope:**
- Adding a third provider (Cursor, Gemini CLI, etc.). The toggle's
  provider list is a hard-coded constant; future providers require a
  separate task that extends `T3ProviderKind`, this constant, and the
  per-provider plumbing in `selectOrchestrationFlags`.
- A capability annotation on adapters (was option (c) in elaboration Q2;
  rejected).
- A non-duo-specific override key (was option (b) in elaboration Q3;
  rejected — the user accepted that duo reads the same keys).
- A sidecar JSON state file (was discussed in elaboration Q4; rejected
  in favour of `config.yaml` writes).
- Retroactive effect on already-running slots (`selectOrchestrationFlags`
  is consulted at slot-start; nothing re-reads after the agent process
  starts).
- A toggle for the t3code-vs-tmux backend (already covered by the
  existing `mode-toggle-btn` per-slot adapter toggle).

**Dependencies:**
- None on other in-flight tasks. The read-side keys
  `mag.orchestration.default_coder` / `default_reviewer` are already
  consumed by stable code.

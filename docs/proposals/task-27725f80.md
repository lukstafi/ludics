# Proposal: Enforce repo-relative proposal paths at write time and test out-of-tree boundary

**Task**: task-27725f80
**Effort**: Small
**Status**: Ready to implement

---

## Summary

Proposal paths stored in task frontmatter (`proposal:` field) must always be repo-relative
(e.g. `docs/proposals/task-xxx.md`). Before this change, `resolveTaskRelativePath()` and
`resolveProposalAbsPath()` accepted absolute paths, home-relative paths (`~/...`), and
`../`-traversals without validation. The only guard was an `isInProjectTree` check in
`taskSpecText()` that silently suppressed proposal summaries for out-of-tree paths, but still
resolved them.

This proposal adds an `assertRepoRelativeProposalPath()` validation function and wires it into
both code-side read points, plus adds unit tests for boundary cases.

---

## Changes

### 1. New validation function in `src/adapters/task-launch.ts`

`assertRepoRelativeProposalPath(rawPath)` throws if the path is:
- Absolute (starts with `/`)
- Home-relative (starts with `~/`)
- Escapes the project tree (normalized form starts with `../` or equals `..`)

### 2. Wired into `readProposalLaunchMetadata()`

Called after extracting `proposalValue` and before `resolveTaskRelativePath`, so invalid paths
are caught at slot-start time with a clear error message.

### 3. Wired into `resolveProposalAbsPath()` in `src/orchestration/skills.ts`

Called at the top of the function, protecting both `taskSpecText()` and `taskSpecBriefText()`
which flow through this resolver. The existing `isInProjectTree` check in `taskSpecText()` is
retained as defense-in-depth.

### 4. Unit tests in `src/adapters/task-launch.test.ts`

Seven new tests in a `describe("assertRepoRelativeProposalPath")` block:
- Valid repo-relative path passes
- Nested relative path that stays in-tree (`docs/../docs/proposals/foo.md`) passes
- Absolute path (`/tmp/evil.md`) rejects
- Home-relative path (`~/docs/foo.md`) rejects
- Parent traversal (`../../etc/passwd`) rejects
- Single dotdot (`../foo.md`) rejects
- Traversal that normalizes out of tree (`docs/../../foo.md`) rejects

Plus one integration test: `readProposalLaunchMetadata` throws the validation error (not
"not found") when the proposal path is absolute.

---

## Risk Assessment

**Low risk**. The assertion only rejects paths that were never valid to begin with. All existing
proposal paths in the harness are repo-relative (`docs/proposals/...`). The `isInProjectTree`
defense-in-depth guard remains untouched.

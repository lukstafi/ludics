# Precompute the Needs Confirmation list in briefing-context.md

## Goal

The 2026-05-20 morning briefing listed three Ludics tasks
(`task-5ef3ac11`, `gh-ludics-167`, `task-7ae99643`) under its **Needs
Confirmation** section. All three had been `status: done` for weeks
(completed 2026-03-28, 2026-04-07, 2026-04-29). The dashboard correctly
showed zero Ludics needs-confirmation tasks, so the user hit a
briefing/dashboard mismatch.

Root cause: step 4 of `skills/ludics-briefing.md` ("Scan for
needs-confirmation tasks") is the *only* strategic list the briefing skill
derives by hand-scanning `tasks/*.md`. Every other strategic section —
Ready Queue, Critical Items, Tasks Needing Elaboration — is precomputed
into `mag/briefing-context.md` by `ludics mag context` and is
bash-verified. Because the needs-confirmation list is not precomputed, the
agent copied it forward from the prior `briefing.md` without re-checking
`status:`, carrying three long-done tasks into today's briefing.

Tracked as [lukstafi/ludics#547](https://github.com/lukstafi/ludics/issues/547).

## Acceptance Criteria

1. `mag/briefing-context.md` generated by `ludics mag context` contains a
   `## Needs Confirmation` section, populated only with tasks whose
   frontmatter status is exactly `needs-confirmation`.

2. Tasks in any other status — in particular terminal statuses like `done`,
   `abandoned`, `merged` — never appear in that section, even if a prior
   `briefing.md` listed them.

3. Each listed task is projected with at least its id, title, priority, and
   project — enough for the briefing to render its Needs Confirmation entries
   without re-reading task files.

4. When no task is in `needs-confirmation` status, the section is still
   present with an explicit empty marker (consistent with how the existing
   `## Tasks Needing Elaboration` section renders emptiness), so the briefing
   skill can distinguish "no such tasks" from "section missing".

5. The output is deterministically ordered, so a regression test can assert
   on it stably.

6. Step 4 of `skills/ludics-briefing.md` ("Scan for needs-confirmation
   tasks") reads the precomputed `## Needs Confirmation` section of
   `briefing-context.md` instead of hand-scanning `tasks/*.md`. The
   "context file contains these sections" list in that skill's Pre-computed
   Context part is updated to include the new section.

7. An automated regression test seeds at least one `needs-confirmation`
   task and at least one `done` task into a temp harness, runs the
   briefing-context generation, and asserts the section contains the former
   and not the latter — i.e. the test would have caught the #547 bug.

8. `bun run build`, the test suite, lint, and typecheck all pass.

## Context

How things work now:

- **`src/mag.ts`** — the briefing-context generator (the async function
  whose tail emits `console.error("ludics: briefing context written to
  ...")`). It builds `contextContent` as a template literal of `##`-headed
  sections. Each section body is computed earlier into a `const ...Output`
  string. The `## Tasks Needing Elaboration` body comes from a `ludics tasks
  needs-elaboration` sub-invocation: `safeSyncOutput(ludicsSelfCommand(["tasks",
  "needs-elaboration"]))`, falling back to `"None"` when empty.

- **`src/tasks/index.ts`** — the `tasks` sub-command dispatcher. The
  `needs-elaboration` case calls `tasksNeedsElaboration()`, a thin function
  that lists ids. `tasksDuplicates()` is the closer structural precedent: it
  `readdirSync`s `tasksDir()`, runs `parseTaskFrontmatter` on each file,
  filters by status, and prints one line per task. The dispatch `switch`,
  its `default`-case "unknown tasks subcommand" error string, and the USAGE
  block in `src/index.ts` (the `tasks needs-elaboration` line) all enumerate
  sub-commands and must stay in sync (per the gh-ludics-438 sub-command-drift
  note).

- **`src/tasks/markdown.ts`** — `parseTaskFrontmatter` is the established,
  cached frontmatter parser. The codebase convention (`tasksDuplicates`,
  `tasksNeedsElaborationList`) is to parse frontmatter in TypeScript rather
  than `grep`.

- **`src/dashboard.ts`** — `needsConfirmationConfig` uses
  `filter: (task) => task.status === "needs-confirmation"`. This confirms
  exact-match on `needs-confirmation` is the canonical predicate.

- **`skills/ludics-briefing.md`** — step 4 under
  `<!-- section:scan-needs-confirmation -->` currently says "Check task files
  for `status: needs-confirmation`". The "context file contains these
  sections" bulleted list under `<!-- section:pre-computed-context -->`
  enumerates every other section. The briefing-output template includes a
  `## Needs Confirmation` section showing the expected rendered shape
  (`**task-id** (priority): "title" -- from <source>`).

- **Tests** — `src/mag.test.ts` already has `describe` blocks that exercise
  briefing-context generation against a temp harness and assert on section
  content. `src/dashboard.test.ts` has a `needs-confirmation` describe block
  showing the fixture pattern for writing `status: needs-confirmation` task
  files.

Edge cases worth noting:

- The filter must be exact-match `status === "needs-confirmation"`. Do not
  reuse `tasksDuplicates`'s "exclude `TERMINAL_STATUSES`" inverse pattern —
  `needs-confirmation` is itself non-terminal and the inverse filter is what
  is wanted. Exact-match also automatically excludes `merged` tasks and tasks
  carrying `merged_into`.

- The skill's amend (light-touch) branch should pick up mid-day status
  changes automatically as long as `ludics mag context` reruns before each
  briefing — no extra work, but the implementer should sanity-check that the
  amend branch does not separately hand-scan task files for this list.

## Approach

*Suggested approach — agents may deviate if they find a better path.*

Follow the `tasksDuplicates` / `## Tasks Needing Elaboration` precedent:

- Add a `tasks needs-confirmation` CLI sub-command in `src/tasks/index.ts`
  that scans `tasksDir()`, filters `parseTaskFrontmatter(...).status ===
  "needs-confirmation"`, projects id/title/priority/project, and prints one
  deterministically-ordered line per task. Wire it into the dispatch
  `switch`, the unknown-subcommand error string, and the USAGE block in
  `src/index.ts`.

- In `src/mag.ts`, add a `## Needs Confirmation` section to the
  `contextContent` template — most naturally adjacent to `## Tasks Needing
  Elaboration`, since both are task-status projections — populated by a
  `safeSyncOutput(ludicsSelfCommand(["tasks", "needs-confirmation"]))`
  sub-invocation with an empty-marker fallback matching the elaboration
  section's `"None"`.

- Repoint step 4 of `skills/ludics-briefing.md` at the new section and add
  it to the "context file contains these sections" list.

If a simpler precompute path exists that does not need a new CLI
sub-command (e.g. computing the projection inline in `mag.ts`), that is an
acceptable deviation — the acceptance criteria constrain the *outcome*
(a verified, precomputed section), not the CLI surface.

## Scope

In scope: the precomputed `## Needs Confirmation` section, its data source,
the briefing-skill repoint, and a regression test.

Out of scope: the separately-discussed "delta-gate" idea (skip regenerating
the briefing on no-change days). It is explicitly not part of #547.

No dependencies on other tasks.

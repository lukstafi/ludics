# Proposal: Add file locking to queue mutation paths

## Goal

Prevent concurrent read-modify-write races on `mag/queue.jsonl` by wrapping all queue mutation functions in a synchronous mkdir-based file lock, ensuring that concurrent keepalive ticks, stop hooks, and dashboard endpoints cannot interleave queue reads and writes.

## Acceptance Criteria

- [ ] A `withQueueLock<T>(fn: () => T): T` helper exists in `src/queue.ts` that acquires an exclusive mkdir-based lock before executing `fn` and releases it in a `finally` block
- [ ] Lock acquisition uses `mkdirSync` atomicity with retry+backoff (up to ~5s) and stale-lock detection via PID liveness check + age threshold
- [ ] `queueRequest` wraps its `appendFileSync` call inside `withQueueLock`
- [ ] `queueReinsertHead`, `queuePopOne`, `queuePopAll` wrap their read-modify-write cycles inside `withQueueLock`
- [ ] `dequeueQueueHead` in `src/mag.ts` is refactored to delegate to a new `queuePopExpected(expectedLine?: string)` export from `src/queue.ts` (which uses `withQueueLock` internally), eliminating the duplicate queue manipulation code in `mag.ts`
- [ ] The dead-code `queuePop()` function in `src/queue.ts` is removed
- [ ] Read-only functions (`queueList`, `queuePending`, `queueHasPendingAction`, `queueHasPendingActionForTask`, `queueHasPendingFeedbackDigest`, `queueShow`) are NOT wrapped in locks (stale reads are acceptable)
- [ ] Lock directory is `<queueFile>.lock` (i.e., `mag/queue.jsonl.lock`); an `owner` file inside records PID and timestamp for stale detection
- [ ] Stale locks (owner PID dead or lock older than 30s) are automatically broken and re-acquired
- [ ] Existing tests in `queue.test.ts` and `queue-reinsert.test.ts` continue to pass
- [ ] New tests verify: (a) `withQueueLock` serializes concurrent access (second caller blocks until first releases), (b) stale lock from dead PID is broken, (c) lock directory is cleaned up after normal execution and after thrown exceptions

## Context

### Queue file and mutation paths

All queue state lives in `mag/queue.jsonl`. There are currently 6 active mutation paths across 2 files:

**`src/queue.ts`:**
- `queueRequest` -- append-only via `appendFileSync`. Races with read-modify-write ops.
- `queueReinsertHead` -- `readQueueLines()` + `writeQueueLines()` (tmp+rename pattern).
- `queuePopOne` -- same `readQueueLines()` + `writeQueueLines()` pattern.
- `queuePopAll` -- same pattern.
- `queuePop` -- dead code (exported but never imported). Uses direct `writeFileSync`, not the atomic `writeQueueLines` helper.

**`src/mag.ts`:**
- `dequeueQueueHead` -- independent read-modify-write using raw `readFileSync` + `writeFileSync` (not tmp+rename). Called by `queuePopSkill` and `drainProgrammaticQueueHead`.

### Callers

- `queueRequest`: called from `mag.ts` (~20 sites), `notify.ts` (~9), `dashboard-server.ts` (2), `tasks/sync.ts` (2), `retrospective.ts` (1). Triggered by keepalive ticks, stop hooks, dashboard HTTP endpoints, and notification processing.
- `queueReinsertHead`: called from `maybeFeedMagQueue` for failed delivery requeue.
- `queuePopOne`/`queuePopAll`: called from CLI `mag queue pop one|all`.
- `dequeueQueueHead`: called from `queuePopSkill` and `drainProgrammaticQueueHead`.
- `maybeFeedMagQueue` (which calls `queuePopSkill` and `queueReinsertHead`): called from dashboard-server, keepalive tick, and stop hook paths.

### Race scenarios addressed

1. **Append vs read-modify-write**: `queueRequest` appends between another process's `readFileSync` and `writeFileSync`/`renameSync` -- the appended entry is lost when the file is overwritten.
2. **Concurrent read-modify-write**: Two keepalive ticks or stop hook + keepalive both pop entries, then write back -- one write overwrites the other.
3. **`dequeueQueueHead` vs `writeQueueLines`**: Different write strategies (direct write vs tmp+rename) compound the race window.

### Related work

- `gh-ludics-303` (proposal `gh-ludics-303.md`) covers atomic writes (crash recovery). That proposal's acceptance criteria include refactoring `dequeueQueueHead` to delegate to `queuePopOne`. This task extends that by adding cross-process locking. The `dequeueQueueHead` refactoring should be done here (or coordinated if gh-ludics-303 lands first).
- The `expectedLine` parameter on `dequeueQueueHead` provides weak CAS-like semantics for `drainProgrammaticQueueHead`. This must be preserved in the new `queuePopExpected` export.

### Type: `QueueDequeueResult`

Defined in `src/mag.ts` as: `{ status: "empty" } | { status: "mismatch" } | { status: "popped"; line: string; request: Record<string, unknown> | null }`. This type (or a compatible one) should move to or be re-exported from `src/queue.ts` for the new `queuePopExpected`.

### Existing patterns

- `process.kill(pid, 0)` for PID liveness is used throughout the codebase (e.g., `src/slots/index.ts`, `src/adapters/tmux-adapter.ts`).
- `Bun.sleepSync` is used in `src/dashboard.ts`.
- The project runs exclusively on Bun; Node.js compatibility is not required.

## Approach

### Step 1: Add `withQueueLock` to `src/queue.ts`

Add a synchronous lock helper using `mkdirSync` atomicity:

```ts
function withQueueLock<T>(fn: () => T): T {
  const lockDir = queueFile() + ".lock";
  const ownerFile = join(lockDir, "owner");
  const maxAttempts = 50;
  const retryMs = 100;
  const staleThresholdMs = 30_000;

  for (let i = 0; i < maxAttempts; i++) {
    try {
      mkdirSync(lockDir);
      writeFileSync(ownerFile, `${process.pid}\n${Date.now()}`);
      break;
    } catch (e: any) {
      if (e.code !== "EEXIST") throw e;
      // Stale lock detection
      try {
        const owner = readFileSync(ownerFile, "utf-8");
        const [pidStr, tsStr] = owner.split("\n");
        const pid = Number(pidStr);
        const ts = Number(tsStr);
        const isStale = (Date.now() - ts > staleThresholdMs);
        let isDead = false;
        if (pid > 0) {
          try { process.kill(pid, 0); } catch { isDead = true; }
        }
        if (isStale || isDead) {
          // Break stale lock
          try { unlinkSync(ownerFile); } catch {}
          try { rmdirSync(lockDir); } catch {}
          continue; // Retry immediately
        }
      } catch { /* owner file unreadable, retry */ }
      if (i === maxAttempts - 1) throw new Error("queue lock timeout after 5s");
      Bun.sleepSync(retryMs);
    }
  }

  try {
    return fn();
  } finally {
    try { unlinkSync(ownerFile); } catch {}
    try { rmdirSync(lockDir); } catch {}
  }
}
```

Add `unlinkSync` and `rmdirSync` to the `fs` import.

### Step 2: Wrap existing mutation functions

- `queueRequest`: wrap the `appendFileSync` + event emission inside `withQueueLock`.
- `queueReinsertHead`: wrap the `readQueueLines()` + `writeQueueLines()` call.
- `queuePopOne`: wrap the `readQueueLines()` + `writeQueueLines()` call.
- `queuePopAll`: wrap the `readQueueLines()` + `writeQueueLines()` call.

### Step 3: Add `queuePopExpected` and consolidate `dequeueQueueHead`

Export a new `queuePopExpected(expectedLine?: string)` from `src/queue.ts`:

```ts
export type QueueDequeueResult =
  | { status: "empty" }
  | { status: "mismatch" }
  | { status: "popped"; line: string; request: Record<string, unknown> | null };

export function queuePopExpected(expectedLine?: string): QueueDequeueResult {
  return withQueueLock(() => {
    const lines = readQueueLines();
    if (lines.length === 0) return { status: "empty" };
    const first = lines[0]!;
    if (expectedLine !== undefined && first !== expectedLine) {
      return { status: "mismatch" };
    }
    writeQueueLines(lines.slice(1));
    try {
      return { status: "popped", line: first, request: JSON.parse(first) as Record<string, unknown> };
    } catch {
      return { status: "popped", line: first, request: null };
    }
  });
}
```

In `src/mag.ts`, replace `dequeueQueueHead` with an import of `queuePopExpected` from `./queue.ts`. Remove the `QueueDequeueResult` type and `queueFilePath` helper from mag.ts (the latter is only used by `dequeueQueueHead`). Update `queuePopSkill` and `drainProgrammaticQueueHead` to use the imported function.

### Step 4: Remove dead code

Remove the unused `queuePop()` function from `src/queue.ts`.

### Step 5: Tests

Add tests to `src/queue.test.ts`:

1. **Lock serialization**: Acquire `withQueueLock`, verify the lock directory exists, verify a second synchronous call within the lock would see `EEXIST` on `mkdirSync`.
2. **Stale lock cleanup**: Create a lock dir with a dead PID (e.g., PID 999999) and old timestamp. Verify `withQueueLock` breaks the stale lock and proceeds.
3. **Lock cleanup on exception**: Call `withQueueLock` with a function that throws. Verify the lock directory is removed after the exception.
4. **`queuePopExpected` basic behavior**: Queue two items, pop with matching expectedLine -- succeeds. Pop with mismatched expectedLine -- returns `{ status: "mismatch" }`. Pop from empty queue -- returns `{ status: "empty" }`.
5. **`queuePopExpected` without expectedLine**: Same as `queuePopOne` behavior (pops first item unconditionally).

Verify all existing tests in `queue.test.ts` and `queue-reinsert.test.ts` pass unchanged.

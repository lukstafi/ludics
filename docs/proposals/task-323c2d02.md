# Proposal: Add project requirements matching for slot assignment

**Task**: task-323c2d02  
**Title**: Add project requirements matching for slot assignment: gpu, os fields  
**Priority**: A  

---

## Goal

Extend slot assignment to honor `requirements` fields declared on project entries in `config.yaml`. Tasks belonging to a project with hardware/OS requirements should only be auto-assigned to machines that satisfy those requirements. This prevents, for example, CUDA-only project tasks from landing on Apple Silicon slots.

---

## Acceptance Criteria

1. `ProjectConfig` in `src/config.ts` accepts an optional `requirements?: { os?: string; gpu?: string }` field without causing config validation errors.
2. `getSortedReadyCandidates` merges project-level requirements with task-level requirements before passing them to `selectMachineForSlot`. Task-level values override project-level values for the same key.
3. `launchSessionFromNotification` (notification button path) resolves merged requirements and passes the selected machine to `slotAssign`, or aborts with a user-facing notification when no machine qualifies.
4. When federation is disabled (standalone mode), all requirement checks are bypassed (existing behavior preserved).
5. When a project is not found in config, requirements default to `undefined` (graceful degradation, task proceeds normally).
6. `templates/config.reference.yaml` documents the `projects[].requirements` field with valid key values.

---

## Context

Commit `27b2ba3` ("feat: task hardware requirements and offline machine handling") added `requirements` as an optional frontmatter field on individual task files. The full pipeline — type definition, YAML parsing, `selectMachineForSlot` filtering, and `maybeFillEmptySlots` null-guard — already works for task-level requirements. This proposal extends the same pattern one level up to project config.

**Relevant existing infrastructure:**

- `src/tasks/types.ts:17` — `TaskFrontmatter.requirements?: { os?: string; gpu?: string }` (task-level, already defined)
- `src/federation.ts:529–569` — `selectMachineForSlot({ project, effort, requirements? })` filters machines; returns `null` when no machine matches, `""` in standalone mode
- `src/federation.ts:17–26` — `FederationMachine` has `gpu: string` and `os: string` from config
- `src/mag.ts:2199` — `ReadyCandidate` interface includes `requirements?: { os?: string; gpu?: string }`
- `src/mag.ts:2260` — candidate building reads `requirements` from task frontmatter
- `src/mag.ts:2375, 2403` — `selectMachineForSlot` called with `task.requirements` for both duo and single auto-fill paths; null guard already present

## Approach

### 1. Add `requirements` to `ProjectConfig` (`src/config.ts:15–47`)

```typescript
export interface ProjectConfig {
  // ... existing fields ...
  /** Hardware/OS requirements for slot assignment. Tasks in this project
   *  will only be assigned to machines satisfying all specified requirements.
   *  Supported keys: os (macos | linux | windows), gpu (apple-silicon | nvidia | amd).
   *  Task-level requirements (in task frontmatter) override project-level values. */
  requirements?: { os?: string; gpu?: string };
}
```

No changes needed to `loadConfigSync()` — it passes `data.projects` as the typed `ProjectConfig[]` already.

### 2. Add `mergeRequirements` helper and update `getSortedReadyCandidates` (`src/mag.ts`)

Add a small pure helper (near `getSortedReadyCandidates`):

```typescript
function mergeRequirements(
  task?: { os?: string; gpu?: string },
  project?: { os?: string; gpu?: string },
): { os?: string; gpu?: string } | undefined {
  if (!task && !project) return undefined;
  return {
    os: task?.os ?? project?.os,
    gpu: task?.gpu ?? project?.gpu,
  };
}
```

In `getSortedReadyCandidates`, add a single config load before the loop, then merge during candidate construction (around line 2260):

```typescript
const cfg = loadConfigSync();  // add before loop

// inside the loop, replace the existing requirements line:
const taskReqs = fm.requirements ? fm.requirements as { os?: string; gpu?: string } : undefined;
const projectCfg = findProjectConfig(cfg, join(harnessDir(), "tasks")); // use existing helper
// Actually: find by project name:
const projectReqs = cfg.projects?.find(
  (p) => p.name === project || p.repo.split("/").pop() === project
)?.requirements as { os?: string; gpu?: string } | undefined;
const requirements = mergeRequirements(taskReqs, projectReqs);
```

`ReadyCandidate.requirements` already exists — no interface change needed.

### 3. Update `launchSessionFromNotification` to call `selectMachineForSlot` (`src/mag.ts:955–1015`)

After resolving `path` (line 994) and before calling `slotAssign` (line 998), add:

```typescript
// Resolve task and project requirements for machine selection
const taskFm = readTaskFrontmatter(taskId);  // use existing parse helpers
const taskReqsRaw = taskFm?.requirements as { os?: string; gpu?: string } | undefined;
const cfgForLaunch = loadConfigSync();
const projectName = taskFm?.project ? String(taskFm.project) : "";
const projReqsRaw = cfgForLaunch.projects?.find(
  (p) => p.name === projectName || p.repo.split("/").pop() === projectName
)?.requirements as { os?: string; gpu?: string } | undefined;
const launchReqs = mergeRequirements(taskReqsRaw, projReqsRaw);
const machine = selectMachineForSlot({ project: projectName, effort: String(taskFm?.effort ?? "small"), requirements: launchReqs });
if (machine === null) {
  const msg = `Cannot launch ${taskId}: no machine meets requirements`;
  notifyOutgoing(msg, 3, "ludics");
  console.error(`ludics: ${msg}`);
  return;
}
// Pass machine to slotAssign:
slotAssign(slotNum, taskId, adapter, "", path, launchArgs, machine || undefined);
```

The overloaded `slotAssign` already accepts an optional `machine` argument (see `src/slots/index.ts`).

### Edge cases

- **Standalone mode**: `selectMachineForSlot` returns `""` (not `null`) — bypasses requirements, existing behavior preserved
- **Project not in config**: `projectReqs` is `undefined` — merged result equals task-level requirements only
- **Task overrides project**: `mergeRequirements` uses task value first (`task?.os ?? project?.os`)
- **Partial requirements**: project sets `os: linux`, task adds `gpu: nvidia` → merged `{ os: linux, gpu: nvidia }`
- **`launchSessionFromNotification` null guard**: mirrors `maybeFillEmptySlots` existing pattern

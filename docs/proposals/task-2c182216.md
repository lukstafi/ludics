# Clean up stale t3code threads and projects

## Goal

Add a `ludics t3code cleanup` command that soft-deletes t3code threads and projects left over from previous/recovered sessions. These accumulate after crash-restart cycles and SQLite recovery, cluttering the t3code sidebar without affecting functionality.

## Acceptance Criteria

- `ludics t3code cleanup` command exists and is wired into the `runT3Code` switch in `src/t3code/index.ts`
- Threads are considered stale and soft-deleted if ALL of: (a) their thread ID is not referenced by any current slot's `t3code/slot-{n}.json` state, (b) the thread is not associated with an active (non-terminal) task (terminal statuses: `done`, `abandoned`, `merged`), AND (c) the thread's last activity is older than 25 hours (to preserve a post-mortem window per gh-ludics-153).
- Projects are considered stale and soft-deleted if: (a) their `workspaceRoot` path does not exist on disk, OR (b) no non-deleted thread references them. Same 25h delay applies.
- Cleanup uses `thread.delete` commands (which set `deleted_at` in t3code's projection tables) -- no row deletion
- There is no `project.delete` command in the t3code protocol; for projects, either skip project cleanup (document as limitation) or add a `project.delete` command type if the wire protocol supports it
- `--dry-run` flag prints what would be cleaned without dispatching any commands
- `slot clear` optionally calls the cleanup logic after clearing a slot (guarded so it does not fail the clear if cleanup errors)
- Threads already soft-deleted (`deletedAt` set) are skipped

## Context

### Existing cleanup mechanisms

The function `cleanupStaleThreads` at `src/adapters/t3code.ts:544` already handles per-slot thread cleanup during slot setup. It stops sessions and deletes threads that belong to a slot's previous `T3CodeSlotState.threads` but are not in the new `keepThreadIds` set. This is scoped to a single slot and does not address globally orphaned threads.

The briefing cleanup in `src/mag.ts:1370` deletes specific briefing-related threads.

### How to identify stale threads

1. Fetch the t3code snapshot via `client.getSnapshot()` -- gives all `T3Snapshot.threads` and `T3Snapshot.projects`
2. Read all slot state files (`t3code/slot-{1..N}.json`) to collect thread IDs that are currently assigned to slots
3. For each snapshot thread not in the active set and not already `deletedAt`: check if its associated task (parsed from thread title or slot state) is terminal AND its last activity is older than 25 hours (post-mortem window, aligned with gh-ludics-153)
4. Dispatch `thread.delete` for each stale thread (stops session first if running)

### Key types and commands

- `T3Thread` (`src/t3code/types.ts:68`): has `id`, `projectId`, `deletedAt`, `session`
- `T3Project` (`src/t3code/types.ts:38`): has `id`, `workspaceRoot`, `deletedAt`
- `T3ThreadDeleteCommand` (`src/t3code/types.ts:147`): `{ type: "thread.delete", commandId, threadId }`
- `T3ThreadSessionStopCommand`: stop running session before delete
- No `project.delete` command exists in the current protocol (`T3Command` union at types.ts:185)

### Implementation location

New cleanup function in `src/t3code/index.ts` alongside existing `runT3Code`. Reuse `withClient` helper and slot state reading from `server.ts`. Wire into the `switch (sub)` as a new `"cleanup"` case.

### Integration with slot clear

In `src/slots/index.ts`, after the existing clear logic completes, optionally invoke the cleanup. This should be best-effort (try/catch) to avoid blocking slot operations.

## Approach

1. Add `cleanupStaleItems(harness, dryRun)` function in `src/t3code/index.ts`:
   - Connects to t3code, fetches snapshot
   - Reads all slot state files to build active thread ID set
   - Iterates snapshot threads, identifies stale ones, stops sessions and deletes
   - For projects: checks `workspaceRoot` existence and thread references, logs stale projects (skip actual deletion until protocol supports it)
2. Add `"cleanup"` case to the `runT3Code` switch with `--dry-run` flag support
3. In `src/slots/index.ts` `slotClear`, add optional post-clear cleanup call
4. Update help text in `src/index.ts` to document the new subcommand

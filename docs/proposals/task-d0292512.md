# Make taskSpecText resilient to bad proposal paths

## Goal

`taskSpecText()` is a best-effort content builder used during orchestration to assemble task context for agent sessions. Currently it calls `resolveProposalAbsPath()`, which throws on absolute, home-relative, or tree-escaping `proposal:` paths. A malformed frontmatter value should not crash the entire skill context assembly -- it should degrade gracefully to the legacy/inline fallback.

Originated from retrospective of task-27725f80.

## Acceptance Criteria

- `taskSpecText()` does not throw when `proposal:` frontmatter contains an absolute (`/etc/passwd`), home-relative (`~/foo`), or tree-escaping (`../../bar`) path.
- When `resolveProposalAbsPath()` throws, `taskSpecText()` logs a warning via `console.error` and falls through to the legacy/inline code path (returns full task content with optional GitHub issue body, without proposal summary).
- New test: calling the function with a bad proposal path (e.g. `proposal: /etc/passwd`) returns task content without crashing, does not include "Read the full proposal", and verifies the warning was logged.
- Existing tests for file-based and inline proposals continue to pass.

## Context

**`taskSpecText()`** (`src/orchestration/skills.ts`, lines 109-157) reads the task file, checks for a `proposal:` frontmatter value, and either appends a proposal pointer+summary (file-based) or returns the raw content (inline/legacy). The proposal file resolution at line 123 calls `resolveProposalAbsPath()` which in turn calls `assertRepoRelativeProposalPath()` -- this throws on non-repo-relative paths.

**`resolveProposalAbsPath()`** (same file, lines 70-77) first asserts the path is repo-relative, then has dead-code branches for `~/` and `/` prefixes (unreachable because the assertion already throws). This dead code is a pre-existing issue and out of scope.

**`assertRepoRelativeProposalPath()`** (`src/adapters/task-launch.ts`, lines 28-38) is the validation function that throws. It is also used elsewhere and should not be modified.

**Existing tests** (`src/orchestration/skills.test.ts`, lines 286+ and 320+) cover file-based proposal with summary and inline proposal. The new test follows the same pattern.

## Approach

*Suggested approach -- agents may deviate if they find a better path.*

Wrap the body of the `if` block at line 122-143 in a try-catch. On catch, log a warning with `console.error` including the error message, and let execution fall through to the legacy path at line 146. The catch should be narrow -- only around the proposal resolution and summary extraction block, not the entire function.

## Scope

**In scope:** The try-catch in `taskSpecText()` and the corresponding test case.

**Out of scope:** The dead code in `resolveProposalAbsPath()` (lines 72-75), changes to `assertRepoRelativeProposalPath()`, and changes to `taskSpecBriefText()` (which does not call `resolveProposalAbsPath`).

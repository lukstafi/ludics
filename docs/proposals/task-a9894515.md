# Proposal: Rename staging_repo to upstream_repo

**Task**: task-a9894515
**Project**: ludics

## Goal

Align naming with actual semantics: `repo` should mean "the repo agents work in" (the fork), and the optional upstream target should be explicitly named `upstream_repo`. Currently the naming is inverted -- `repo` points to upstream and `staging_repo` points to the working fork. This rename eliminates ongoing confusion and makes config self-documenting.

## Acceptance Criteria

1. The config YAML key `staging_repo` no longer exists; `upstream_repo` replaces it with correct semantics (the forwarding target, not the working repo).
2. `repo` in project config means the working repo where agents create PRs and branches. For projects with a fork, users swap the `repo` value (e.g., `repo: lukstafi/ocannl-staging`).
3. All TypeScript identifiers (`stagingRepo`, `isStaging`, `STAGING_REPO`, etc.) are renamed to their upstream equivalents throughout the codebase.
4. All orchestration templates reference `{{UPSTREAM_REPO}}`, `{{UPSTREAM_REPO_NOTE}}`, `{{UPSTREAM_PR_FILE}}` instead of their staging predecessors.
5. The `staging-final-merge.md` template is renamed to `upstream-final-merge.md`.
6. Skill/prompt content reflects the new semantics -- e.g., the note says "This project forwards approved PRs to upstream (`{{UPSTREAM_REPO}}`)" rather than instructing agents to target a staging fork.
7. `setup.sh` parses `upstream_repo` instead of `staging_repo`.
8. Reference config (`templates/config.reference.yaml`) and harness template config are updated.
9. Tests pass with the renamed identifiers.
10. Historical proposal docs (`docs/staging-repo-proposal.md`, `docs/proposals/task-bd16f4dc.md`, `docs/proposals/task-50b07379.md`) are left unchanged.

## Context

**Resolved decisions from user:**
- **No backward compatibility**: Drain all slots before deploying. Replace `stagingRepo` in any persisted state repo files if needed. No migration code in the state loader.
- **No parser compatibility**: Hard break. User updates `config.yaml` manually before deploying.
- **Don't change historical proposal docs**: Leave as-is. Update architecture/design docs if they reference the old naming.
- **Skill/prompt content should change**: The UPSTREAM_REPO_NOTE should convey the new meaning -- "This project forwards approved PRs to upstream" -- not just mechanically swap variable names.

**Semantic inversion of `repo`**: Code that currently uses `repo` to mean "upstream" (e.g., issue syncing, `PROJECT_REPO` template variable) must be updated to read `upstream_repo` when present, falling back to `repo`. The auto-injected `PROJECT_<FIELD>` variables will naturally produce `PROJECT_UPSTREAM_REPO` after the config key rename.

## Approach

| Old identifier | New identifier | Scope |
|---|---|---|
| `staging_repo` (YAML key) | `upstream_repo` | config files, TypeScript `ProjectConfig` |
| `stagingRepo` (TS field) | `upstreamRepo` | `OrchestrationState`, adapter state builders |
| `isStaging` (local var) | `hasUpstream` | phases.ts, runner.ts, skills.ts |
| `STAGING_REPO` (template var) | `UPSTREAM_REPO` | skills.ts context, templates |
| `STAGING_REPO_NOTE` (template var) | `UPSTREAM_REPO_NOTE` | skills.ts context, templates |
| `STAGING_PR_FILE` (template var) | `UPSTREAM_PR_FILE` | skills.ts context, templates |

### Key semantic changes

1. **`UPSTREAM_REPO_NOTE` content flip**: Old note told agents "Create PR against the staging fork." New note tells agents "This project forwards approved PRs to upstream (`{{UPSTREAM_REPO}}`)." The agent always creates PRs against `repo` (the working repo); the note is informational about the forwarding flow.

2. **`resolveProjectPath` simplification**: The `workingRepo = staging_repo ?? repo` fallback chain becomes unnecessary -- `repo` is already the working repo. The function simplifies to use `repo` directly for directory resolution.

3. **`validateProjectPaths` in init.ts**: The validation logic inverts. After rename, it should check that `path` matches `repo` (the working repo), not `upstream_repo`. Error messages update accordingly.

### What NOT to change

- Historical proposal documents in `docs/`
- The `.forwarded` marker file (not staging-specific semantically)
- The `.upstream-merged` marker file (already correctly named)
- The `FORWARDED_MARKER_FILE` template variable

### Migration procedure

1. Drain all active slots (`ludics slot stop --all` or wait for completion)
2. Apply code changes, build (`bun run build`)
3. User manually updates `config.yaml`: swap `repo`/`staging_repo` values, rename field to `upstream_repo`
4. If any persisted state JSON files in `~/self-improve/harness/orchestration/` contain `stagingRepo`, do a find-replace to `upstreamRepo` (or simply delete stale state files)
5. Run `ludics init`

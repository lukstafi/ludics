# Proposal: Dynamic skill variable plumbing — auto-populate template variables from config and context

**Task:** task-50b07379
**Effort:** small

## Summary

Eliminate the three-place boilerplate required to add a new template variable
(`SkillContext` interface + `buildSkillContext()` + `substituteTemplate()` values map)
by collapsing them into a single step. `buildSkillContext()` returns a flat
`Record<string, string>` directly usable by `substituteTemplate()`. Project config
fields are auto-injected as `{{PROJECT_<FIELD>}}` variables. Dev-mode warnings catch
typos in template placeholders.

## Motivation

Every new template variable (e.g., `STAGING_REPO`) requires ~15 lines of boilerplate
across three locations in `skills.ts`. The `SkillContext` interface is consumed only
within `skills.ts` itself and its tests — it provides typed access to values that are
immediately destructured into an untyped `Record<string, string>` inside
`substituteTemplate()`. Removing the intermediate typed interface reduces friction
for adding new variables from "edit 3 sites" to "edit 1 site".

## Design

### Current flow (3 steps)

1. **`SkillContext` interface** (lines 8-40): declares typed fields
2. **`buildSkillContext()`** (lines 192-285): computes values, returns `SkillContext`
3. **`substituteTemplate()`** (lines 287-327): maps `ctx.field` to `TEMPLATE_KEY` in a `Record<string, string>`, then regex-replaces

### Proposed flow (1 step)

1. **`buildSkillContext()`** computes values and returns `Record<string, string>` directly, using template variable names as keys
2. **`substituteTemplate()`** accepts `Record<string, string>` and replaces — no mapping needed

### Auto-injection of project config fields

After building the manual variable map, iterate over the matched `ProjectConfig`
entry and inject string-valued fields with a `PROJECT_` prefix:

```ts
if (_projectEntry) {
  for (const [key, val] of Object.entries(_projectEntry)) {
    if (typeof val === "string" && val) {
      result[`PROJECT_${key.toUpperCase()}`] = val;
    }
  }
}
```

This means `staging_repo: "owner/fork"` in config automatically produces
`{{PROJECT_STAGING_REPO}}` without per-field code. The manually-set `STAGING_REPO`
key remains for backward compatibility (existing templates use `{{STAGING_REPO}}`).

### Dev-mode unresolved placeholder warnings

```ts
export function substituteTemplate(
  template: string,
  values: Record<string, string>,
): string {
  return template.replace(/\{\{([A-Z0-9_]+)\}\}/g, (_, key: string) => {
    if (!(key in values)) {
      if (process.env.LUDICS_DEV || process.env.DEBUG) {
        console.error(`ludics: template warning: unknown variable {{${key}}}`);
      }
    }
    return values[key] ?? "";
  });
}
```

## Implementation Plan

### Step 1: Remove `SkillContext` interface, refactor `buildSkillContext()`

- Delete the `SkillContext` interface (lines 8-40).
- Change `buildSkillContext()` return type to `Record<string, string>`.
- Keep all existing local variable computation unchanged (`peer`, `planFile`,
  `peerReview`, `stagingRepo`, etc.).
- Build the return value as a flat `Record<string, string>` using template variable
  names as keys directly:

```ts
return {
  PHASE: state.phase,
  ROUND: String(state.round),
  MODE: state.mode,
  FEATURE: state.feature,
  AGENT_NAME: agent.name,
  AGENT_PROVIDER: agent.provider,
  AGENT_ROLE: agent.role ?? "agent",
  PEER_NAME: peer?.name ?? "none",
  // ... all 30+ existing keys ...
  STAGING_REPO: stagingRepo ?? "",
  STAGING_REPO_NOTE: stagingRepo
    ? `\n> **Staging fork**: ...`
    : "",
};
```

### Step 2: Simplify `substituteTemplate()`

- Change signature from `(template: string, ctx: SkillContext)` to
  `(template: string, values: Record<string, string>)`.
- Remove the `values` map construction — the parameter **is** the values map.
- Add the dev-mode warning for unresolved placeholders (see Design section above).

### Step 3: Auto-inject project config fields

- After building the manual variable map in `buildSkillContext()`, loop over
  `_projectEntry` and add `PROJECT_<FIELD>` entries for string-valued fields.
- Manual entries take precedence (they are set first; auto-injected entries use
  `??=` or are added only if the key is not already present).

### Step 4: Update tests in `skills.test.ts`

- **`baseCtx()` helper** (lines 31-64): rewrite to return `Record<string, string>`
  with template variable names as keys (`PHASE`, `ROUND`, etc.).
- **`buildSkillContext` tests** (lines 86-134): update property access from typed
  fields (`ctx.mergedPlanFile`) to string keys (`ctx["MERGED_PLAN_FILE"]` or
  `ctx.MERGED_PLAN_FILE`).
- **Staging repo tests** (lines 136-251): update from `ctx.stagingRepo` to
  `ctx["STAGING_REPO"]`.
- **New test**: dev-mode warning — set `process.env.LUDICS_DEV = "1"`, call
  `substituteTemplate()` with `{{TYPO_VAR}}`, capture stderr, assert warning.
- **New test**: auto-injected project config — create config with `staging_repo`
  and `proposals_path`, verify `PROJECT_STAGING_REPO` and `PROJECT_PROPOSALS_PATH`
  appear in context.

## Edge Cases

1. **Non-string project config fields** (`issues: boolean`, `milestones: boolean`,
   `adapter_profiles: object`): skipped by the `typeof val === "string"` guard.
2. **Name collisions**: all auto-injected fields are prefixed with `PROJECT_`,
   which namespaces them away from existing variables like `PHASE`, `ROUND`, etc.
   Manual entries take precedence.
3. **Empty/null project match**: when `_projectEntry` is undefined, the
   auto-injection loop simply does not run.
4. **Backward compatibility**: all existing `{{VARIABLE}}` references in templates
   continue to work — the same keys are produced. Only the internal plumbing changes.

# Add unit tests for PR verification retry loop

## Goal

The PR verification gate (added in task-5eb4ecd7) protects against the orchestrator
advancing past `pr-create` or `final-merge` when the GitHub outcome is not confirmed.
A "spam bug" was discovered during that work: `handleVerifyFailure` re-emitted events
and notifications on every poll cycle once max retries were hit. The fix added an
early-return guard, but there are no tests covering the retry logic, the guard, or the
agent-state reset.

Adding unit tests will prevent regressions on the retry boundary, event emission,
and phase redispatch behavior.

Related: task-5eb4ecd7.

## Acceptance Criteria

1. **Max-retry boundary**: Tests verify that `handleVerifyFailure` increments the
   attempt counter, emits the correct event type per attempt, emits
   `manual_intervention_required` + notification exactly once when reaching
   `MAX_VERIFY_ATTEMPTS`, and returns `"hold"`.

2. **Event spam guard**: Calling `handleVerifyFailure` when attempts are already
   `>= MAX_VERIFY_ATTEMPTS` returns `"hold"` without emitting any events or
   notifications.

3. **Phase redispatch**: `preparePhaseRedispatch` resets `turnLifecycle`, `status`,
   `statusEpoch`, `statusMessage`, and `interrupted` for all participating agents,
   sets `phaseDispatched = false`, and clears `currentPhaseToken`. Non-participating
   agents are left untouched.

4. **`getFirstPrUrl` fallback**: Tests cover the three paths: PR URL from
   `agentStates[agent].prUrl`, fallback to `.pr` peer-sync file, and `null` when
   neither exists.

5. **Wrapper functions (`verifyPrCreateOutcome` / `verifyFinalMergeOutcome`)**:
   At least one test per function covering the "skip" (wrong phase / agents not
   done), "advance" (verification succeeds), and "redispatch/hold" (verification
   fails) decisions.

6. All new tests live in `src/orchestration/runner.test.ts` and pass with
   `bun test`.

## Context

### Key source files

- **`src/orchestration/runner.ts`** -- contains `verifyPrCreateOutcome` (L46-69),
  `verifyFinalMergeOutcome` (L74-105), `handleVerifyFailure` (L107-152),
  `getFirstPrUrl` (L155-166), `preparePhaseRedispatch` (L172-185),
  `MAX_VERIFY_ATTEMPTS` (L40, already exported).

- **`src/orchestration/runner.test.ts`** -- existing test file with `makeState`,
  `makeLifecycle`, `makeTmpDir` helpers and established mocking patterns
  (`spyOn(events, "emitEvent")`, `spyOn(github, "getPrVerification")`).

- **`src/orchestration/phases.ts`** -- `agentParticipatesInPhase` determines which
  agents get reset during redispatch. In pair mode, only the coder participates in
  `pr-create` and `final-merge`.

- **`src/orchestration/state.ts`** -- `prCreateVerifyAttempts`,
  `finalMergeVerifyAttempts`, `phaseRetryContext`, `phaseDispatched`,
  `currentPhaseToken` fields.

- **`src/orchestration/peer-sync.ts`** -- `readPrUrl` reads `.pr` artifact files.

- **`src/notify.ts`** -- `notifyAgents` needs mocking at max-retry boundary.

### Current visibility

The four core functions (`verifyPrCreateOutcome`, `verifyFinalMergeOutcome`,
`handleVerifyFailure`, `preparePhaseRedispatch`, `getFirstPrUrl`) are module-private.
They must be exported for direct testing. The wrapper-level tests
(`verifyPrCreateOutcome`, `verifyFinalMergeOutcome`) are the most important since
they exercise the full flow, but direct tests on `handleVerifyFailure` and
`preparePhaseRedispatch` provide finer-grained coverage of edge cases.

## Approach

*Suggested approach -- agents may deviate if they find a better path.*

1. Export all five functions from `runner.ts`.
2. Add four `describe` blocks to `runner.test.ts`:
   - `describe("handleVerifyFailure", ...)` -- attempt counting, event emission
     per attempt, silent hold at/above max, notification at max boundary.
   - `describe("preparePhaseRedispatch", ...)` -- agent state reset assertions,
     participating vs. non-participating agents.
   - `describe("getFirstPrUrl", ...)` -- agentStates path, peer-sync fallback,
     null when neither.
   - `describe("verifyPrCreateOutcome / verifyFinalMergeOutcome", ...)` -- skip,
     advance, redispatch, and hold decisions via mocked `getPrVerification`.
3. Use `makeState` helper with phase/attempt overrides. Mock `emitEvent`,
   `getPrVerification`, `notifyAgents`, and `readPrUrl` via `spyOn`.
4. Verify with `bun test src/orchestration/runner.test.ts`.

## Scope

**In scope:** Unit tests for the five verification-gate functions listed above.
Exporting those functions from `runner.ts`.

**Out of scope:** Integration tests, changes to the verification logic itself,
tests for `verifyFinalMergeOutcome`'s interaction with actual GitHub API,
end-to-end orchestration loop tests.

**Dependencies:** None (task-5eb4ecd7 is already completed).

# Harden `gh pr merge --delete-branch` invocation against benign worktree-cleanup failures

## Goal

When pair-mode slot worktrees live alongside the main ludics checkout, `gh pr merge --delete-branch` exits non-zero because its local-side cleanup (`git worktree remove` / `git branch -D`) is blocked by the main worktree, even though the server-side merge already succeeded. The non-zero exit causes the agent to skip writing `MERGED_MARKER_FILE` / `STATUS_FILE` and triggers redispatch, which in turn re-runs `gh pr merge` on an already-merged PR until `MAX_VERIFY_ATTEMPTS` is exhausted — polluting logs and retrospectives.

Wrap the merge invocation in `skills/orchestration/final-merge.md` so a benign post-cleanup non-zero exit is rescued by a `gh pr view --json state` confirmation, and the success path (marker write + STATUS_FILE done) is reached whenever the server-side merge actually landed.

Source: retrospective of `task-d6c774b8` (relates_to). No GitHub issue.

## Acceptance Criteria

- After `gh pr merge "$PR_URL" [--repo …] --merge --delete-branch` exits non-zero, the template runs `gh pr view "$PR_URL" [--repo …] --json state` and treats `state == "MERGED"` as success.
- When the post-merge view confirms `MERGED`, control proceeds to the existing success path: `MERGED_MARKER_FILE` is created and `STATUS_FILE` is written with `{{DONE_STATUS}}`.
- When `gh pr view` returns any state other than `MERGED` (e.g. `OPEN`, `CLOSED`), the wrapper exits non-zero so the runner's `verifyPhaseOutcome` retry/escalation logic takes over.
- The primary `gh pr merge "$PR_URL" [--repo …] --merge --delete-branch` invocation remains unchanged in shape — `--delete-branch` is preserved so successful runs still clean up branches.
- The `{{#IF PROJECT_REPO}}--repo "{{PROJECT_REPO}}" {{/IF}}` conditional is applied to BOTH the primary `gh pr merge` and the fallback `gh pr view`, so staging-PR projects target the correct repo on both calls.
- Existing `final-merge template …` assertions in `src/orchestration/skills.test.ts` continue to pass — specifically `expect(rendered).toContain('gh pr merge "$PR_URL" --repo "owner/my-staging" --merge --delete-branch')` and the no-repo variant `expect(rendered).toContain('gh pr merge "$PR_URL" --merge --delete-branch')`.
- New assertions in those same `final-merge template …` cases verify the rendered shell contains the post-merge `gh pr view "$PR_URL" … --json state` fallback (with and without `--repo`).
- `bun test src/orchestration/skills.test.ts` passes.
- No code change is required in `src/orchestration/runner.ts` or `src/orchestration/github.ts` — they already implement the server-side trust model via `FINAL_MERGE_GATE` / `getPrVerification`.

## Context

Code pointers (by symbol/file, not line numbers):

- **Skill template (the call site that needs hardening)**: `skills/orchestration/final-merge.md`. The current invocation is the single line:
  ```
  gh pr merge "$PR_URL" {{#IF PROJECT_REPO}}--repo "{{PROJECT_REPO}}" {{/IF}}--merge --delete-branch
  ```
  followed by "On success, create `{{MERGED_MARKER_FILE}}`. Retry up to 3 times on transient failures." and the `STATUS_FILE` write. The wrapper goes around this line, inside the existing fenced `sh` block.
- **Server-side verification (already exists)**: `src/orchestration/github.ts` exports `getPrVerification(prUrl)` and `isPrMerged(prUrl)`, both of which read `gh api repos/.../pulls/<n>`.
- **Runner gate (already swallows agent-side failure when the server says MERGED)**: `src/orchestration/runner.ts` defines `FINAL_MERGE_GATE` with `checkSuccess: v => v.exists && v.merged === true`, consumed by `verifyPhaseOutcome`. This is a redundant safety net behind the template wrapper but is not enough on its own — without the template change the agent re-dispatches and re-runs `gh pr merge` against an already-merged PR.
- **Test scaffolding**: `src/orchestration/skills.test.ts` has three relevant cases that render `final-merge.md` via `substituteTemplate(template, baseCtx())` / `{ ...baseCtx(), PROJECT_REPO: "owner/my-staging", PR_FILE: "/tmp/coder.pr" }` and string-match the rendered shell:
  - `final-merge template merges the working (staging) PR directly`
  - `final-merge template targets the PR URL and includes --repo with PROJECT_REPO`
  - `final-merge template omits --repo when PROJECT_REPO is empty but still passes the PR URL`

  New assertions live in the latter two (the ones that already pin the rendered shape with/without `PROJECT_REPO`).

## Approach

*Suggested approach — agent may deviate if a cleaner shape emerges.*

Replace the single-line `gh pr merge` invocation in `skills/orchestration/final-merge.md` with a wrapper of roughly this shape (preserving the existing `{{#IF PROJECT_REPO}}` conditional on both calls):

```sh
PR_URL=$(cat "{{PR_FILE}}" 2>/dev/null)
if gh pr merge "$PR_URL" {{#IF PROJECT_REPO}}--repo "{{PROJECT_REPO}}" {{/IF}}--merge --delete-branch; then
  :
else
  # gh exits non-zero when local-side cleanup (worktree remove / branch -D)
  # fails even though the server-side merge landed. Re-check via gh pr view.
  state=$(gh pr view "$PR_URL" {{#IF PROJECT_REPO}}--repo "{{PROJECT_REPO}}" {{/IF}}--json state -q .state)
  [ "$state" = "MERGED" ] || exit 1
fi
```

Notes:
- `--json state -q .state` is preferred over `--json state,mergedAt -q '.state + "|" + (.mergedAt // "")'`: simpler, matches what `FINAL_MERGE_GATE.checkSuccess` already trusts (just `merged === true`), and avoids glob/escaping in a `case` arm.
- The `MERGED_MARKER_FILE` write and the `printf … > "{{STATUS_FILE}}"` line stay on the success path (i.e., reached whether the primary merge succeeded or the fallback rescued it).
- No `sleep`. The local-cleanup failure happens after the server has already committed, so by the time `gh pr view` runs the server state is already `MERGED`. If a transient race ever bites, the runner's poll loop is the natural retry layer.

Test changes (in `src/orchestration/skills.test.ts`, inside the existing `final-merge template …` cases):
- In the `with PROJECT_REPO` case, add: `expect(rendered).toContain('gh pr view "$PR_URL" --repo "owner/my-staging" --json state');`
- In the `without --repo` case, add: `expect(rendered).toContain('gh pr view "$PR_URL" --json state');`
- The existing `expect(rendered).toContain('gh pr merge "$PR_URL" … --merge --delete-branch')` assertions continue to hold unchanged.

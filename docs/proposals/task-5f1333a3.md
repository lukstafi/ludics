# Rebase reused worktree base before proceeding; make refresh stash-tolerant

## Goal

Stop the orchestration from proceeding on a **stale or contaminated worktree
base**. Two composing defects in `src/orchestration/worktrees.ts` let a
re-launched slot plan/work against yesterday's base instead of current
`origin/<main>`:

1. **Reuse short-circuit never rebases.** `addWorktree`'s resume short-circuit
   returns immediately when the worktree dir + branch + git registration all
   agree, doing no fetch/rebase/fast-forward. The only response to a drifted
   base is `warnStaleBase` in `runner.ts`, which *logs* an advisory and never
   acts. Observed: a slot reused a worktree **41 commits stale**, still carrying
   a *different* task's work, and planned in it — the gh-609 wrong-task failure
   mode persisting through worktree reuse.

2. **`refreshMainBranchFromRemote` skips on *any* dirt.** It returns
   `{ skipped: true, reason: "dirty" }` whenever `git status --porcelain` is
   non-empty. A single **dune-generated** tracked file (e.g. `arrayjit.opam`
   from `generate_opam_files true`, regenerated on every build — see memory
   `reference_ocannl_opam_templates`) left local main 41 behind, so the proposal
   wasn't present locally, `ensureProposalReachable` threw `proposal_unreachable`
   ("could not self-heal"), and slot setup looped forever ("stuck at assigned").
   One stray generated file wedged the whole self-heal.

These compose into "the workflow proceeds on a stale/wrong base without
refreshing the project repo" — exactly what a worker must never do. Sibling of
gh-609 (`reference_stale_worker_harness_wrong_task`) and the delivery-time
re-check (task-c16f71b5); same "stale state proceeds silently" family.

Relates to task-5f1333a3 (this), gh-ludics-609, task-873fe5ee (pairs on the
same reuse short-circuit, but for Stop-hook reinstall — landing independently;
see Scope).

## Acceptance Criteria

1. **Reuse refreshes the base unconditionally.** When `addWorktree` encounters
   an existing, correctly-registered worktree (the short-circuit case), it no
   longer leaves the base stale. It attempts to advance the worktree's branch
   base onto fresh `origin/<main>` (fast-forward when the branch carries no
   local commits past base; rebase when it does), having first preserved any
   uncommitted working-tree changes. There is **no** resume-vs-relaunch
   discriminator — refresh is attempted on every reuse.

2. **Uncommitted scratch survives a clean refresh.** When the worktree has
   uncommitted changes (genuine mid-round agent scratch, or a regenerated
   tracked file) and the rebase/fast-forward applies cleanly, those changes are
   restored on top of the refreshed base. A clean refresh never loses or
   silently discards working-tree changes.

3. **A replay/rebase conflict is surfaced to the agent and handed off — never
   papered over.** When restoring the preserved changes (or replaying local
   commits) conflicts with the advanced base, the orchestration does not
   silently keep the stale base and does not clobber the scratch. It surfaces a
   structured, agent-visible event that names *what* conflicted and *how* the
   replay failed, and hands off (the conflict-resolution path), rather than
   proceeding as if the worktree were clean.

4. **`refreshMainBranchFromRemote` is tolerant of generated/ignorable dirt.** A
   non-empty `git status --porcelain` consisting of a regenerated tracked file
   (e.g. a dune-emitted `.opam`) no longer forces `reason: "dirty"` and skips
   the fast-forward. The helper preserves the dirty tree (stash-and-restore),
   fast-forwards local `<main>` to `origin/<main>`, and restores. The preserved
   file is **never lost**; a restore conflict is surfaced loudly / handed off,
   not swallowed.

5. **No silent wedge from a regenerated file.** The originally observed failure
   chain — a single regenerated `.opam` → `main_refresh_skipped(dirty)` →
   `proposal_unreachable` → setup loop "stuck at assigned" — no longer occurs:
   the fast-forward proceeds and the proposal becomes reachable. A refresh skip
   that *persists* and causes a downstream hard-fail is escalated more visibly
   than the current `console.error` (correlated with the symptom it causes), so
   "stuck at assigned" is diagnosable rather than silent.

6. **Recovery seams and remote behavior unchanged.** The orphan-recovery /
   teardown-and-recreate fall-through, detached-HEAD / prunable / diverged
   handling, and `gh-resolved` pinning are preserved. The new logic does not
   depend on controller-only state and behaves correctly on a remote worker with
   `~/`-relative paths (the wedge was first seen on minipc-wsl).

7. **Tests cover the new behavior** in `src/orchestration/worktrees.test.ts`:
   reused worktree with a stale base gets advanced; reused worktree with
   uncommitted scratch preserves the scratch across a clean refresh;
   `refreshMainBranchFromRemote` fast-forwards past a dirty (regenerated-file)
   tree; a replay/stash-pop conflict surfaces an error/handoff signal rather
   than silently proceeding.

## Context

How things work now (key files and symbols, not line numbers):

- **`src/orchestration/worktrees.ts`**
  - `addWorktree(projectDir, path, branch, base)` — the resume short-circuit is
    the early `if (existsSync(path) && branchRefExists(...) &&
    registeredWorktreeMatches(...)) return;` block (Defect 1 fix site). The
    fall-through (`removeIfRegistered` → `classifyOrphanDir` orphan recovery →
    `git worktree add`) is the existing "recreate when too stale / diverged"
    precedent and the recovery seam that must be preserved.
  - `refreshMainBranchFromRemote(projectDir, mainBranch): RefreshSkipResult` —
    does `const dirty = maybeGit(dir, ["status", "--porcelain"]).trim(); if
    (dirty.length > 0) return { skipped: true, reason: "dirty" };` before the
    bounded `git fetch` + `git merge --ff-only origin/<main>` (Defect 2 fix
    site). `RefreshSkipReason = "no-origin" | "wrong-branch" | "dirty" |
    "fetch-failed" | "diverged"` and `RefreshSkipResult` are the nearby types.
    The fetch is already prompt-disabled (`GIT_TERMINAL_PROMPT=0`) and
    timeout-bounded (`LUDICS_WARN_FETCH_TIMEOUT_MS`, default 10s).
  - `createWorktrees(...)` — orchestrates `refreshMainBranchFromRemote` →
    `ensureProposalReachable` → `addWorktree` (root, then per-agent in duo
    mode). Threads `resolvedMainBranch`; the place to decide ordering for any
    new reuse-refresh step. Note the `~/` expansion guard and the
    project-checkout-existence guard at the top (gh-579).
  - `ensureProposalReachable(...)` — consumes the `refreshSkip` reason and emits
    `main_refresh_skipped` / throws `proposal_unreachable`; the victim that
    surfaces Defect 2, not the fix.
  - Reusable helpers: `defaultMainBranch`, `branchRefExists`,
    `registeredWorktreeMatches`, `countCommitsAhead`.

- **`src/orchestration/runner.ts`**
  - `warnStaleBase(state)` — detection-only core: bounded `git fetch origin

## Approach

*Suggested approach — agents may deviate if they find a better path. The shape
below reflects the user's resolved answers (task Questions §Answers, 2026-06-26);
the wiring details are open.*

**Defect 1 — refresh + replay on every reuse (no discriminator).** In
`addWorktree`'s reuse short-circuit, before returning: stash any uncommitted
working-tree changes (including untracked, so regenerated/scratch files are
captured), fast-forward the branch base onto fresh `origin/<base>` (or rebase
when the branch carries local commits past base), then restore the stash. When
the restore (or rebase replay) conflicts, surface a structured, agent-visible
event naming what conflicted and how it failed, and hand off via the existing
conflict path (the `redispatchForConflict` precedent gh-600 established for
merges) — never silently preserve the stale base, never clobber scratch. Reuse
`warnStaleBase`'s fetch+merge-base machinery via a shared helper so the fetch
stays prompt-disabled and timeout-bounded.

**Defect 2 — stash-tolerant `refreshMainBranchFromRemote`.** Replace the
`reason: "dirty"` early return with stash-and-restore: stash the dirty tree
(including regenerated tracked `.opam`), fast-forward, restore. This is the same
machinery Defect 1's replay needs — share it. A stash-pop conflict is the
"show the agent how it failed" path: fail loud / hand off, never lose the
stashed file. (The user considered narrow-the-dirty-gate and generated-file
allowlist alternatives and chose stash-and-restore.)

**Escalation.** Correlate a persistent refresh skip with the downstream
hard-fail it causes (`proposal_unreachable`) so "stuck at assigned" surfaces a
health-check-visible signal rather than only a `console.error`.

Edge cases to honor (from elaboration): genuine same-session mid-round scratch
must survive a clean refresh; a reused branch with real agent commits + advanced
base is a genuine rebase (→ conflict → handoff); detached-HEAD / prunable /
diverged worktrees still fall through to the recreate seam *before* any new
rebase fires; stash-pop conflicts restore cleanly or fail loud (never lose the
file); pair shares one root worktree (one refresh), duo has per-agent worktrees
(refresh each); remote worker `~/`-relative paths and no controller-only state.

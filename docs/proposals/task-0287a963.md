## Context

The `PROPOSAL_INSTRUCTION` variable expands to a "Step 0: Read the proposal..." instruction when a proposal path is set, or to an empty string otherwise — making it safe to use unconditionally in any template.

- `pair-coder-plan-merge.md` — coder merges reviewer feedback into plan

- `pair-reviewer-plan-review.md` — reviewer checks merged plan

### Injection Pattern

Existing templates use bare `{{PROPOSAL_INSTRUCTION}}` on its own line near the top of the template body (after the heading), before the main task instructions. When `PROPOSAL_INSTRUCTION` is empty (no proposal), the line renders as blank and is harmless. Example from `pair-coder-plan.md`:

```
# Pair Plan (Coder)
{{PROPOSAL_INSTRUCTION}}

Plan the implementation for `{{TASK_ID}}`...
```

`pair-reviewer-review.md` uses an inline variant: `Review the coder's implementation for \`{{TASK_ID}}\`. {{PROPOSAL_INSTRUCTION}}`

## Approach

For each of the 4 target templates, add `{{PROPOSAL_INSTRUCTION}}` on its own line immediately after the heading (line 2), matching the majority pattern. No trailing blank line is needed since the variable expands to a full sentence with a newline or to empty string.

**`pair-reviewer-gather.md`** — insert `{{PROPOSAL_INSTRUCTION}}` after `# Pair Gather` heading so the reviewer knows what to look for before writing context notes.

**`pair-coder-clarify.md`** — insert `{{PROPOSAL_INSTRUCTION}}` after `# Pair Clarify (Coder)` heading so the coder reads the proposal before formulating clarification questions.

**`pair-reviewer-clarify.md`** — insert `{{PROPOSAL_INSTRUCTION}}` after `# Pair Clarify (Reviewer)` heading so the reviewer checks the proposal's acceptance criteria when identifying risks.

**`pair-reviewer-pushback.md`** — insert `{{PROPOSAL_INSTRUCTION}}` after `# Pair Pushback (Reviewer)` heading so pushback is anchored to the proposal's scope.

No changes to `src/orchestration/skills.ts` or any other backend file are needed.

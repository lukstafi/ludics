# Proposal: Fix runner premature phase transitions

## Summary

The orchestration runner transitions phases before agent turns complete, because it can't distinguish stale turn completions from current ones. Fix by tracking dispatch timestamps and using the t3code API as the authoritative turn-completion signal.

## Changes

### 1. Track dispatch timestamp (`state.ts`, `runner.ts`)

- Add `phaseDispatchedAt: number` to `OrchestrationState`
- Set it in `enterPhase()` after dispatching turn messages (use `nowEpoch()`)
- Reset to 0 on phase transition

### 2. Fix `refreshAgentStatuses()` (`runner.ts`)

- When checking `latestTurnState` from the t3code snapshot, compare `latestTurnCompletedAt` against `phaseDispatchedAt`
- Only set `status = "turn-complete"` if `completedAt > phaseDispatchedAt`
- If `completedAt <= phaseDispatchedAt`, the completion is stale — keep status as-is (agent hasn't finished current turn)

### 3. Fix `isAgentDone()` (`phases.ts`)

- The `latestTurnState === "completed"` check should also verify the completion is fresh (not stale)
- Pass `phaseDispatchedAt` through or check it in `refreshAgentStatuses` before setting the status

### 4. Initial poll delay (`runner.ts`)

- In `pollUntilDone()`, skip the first poll for a brief grace period (e.g., 3-5s) after dispatch to give the t3code server time to register the new turn

### Files to modify

- `src/orchestration/state.ts` — add `phaseDispatchedAt` field
- `src/orchestration/runner.ts` — set timestamp in `enterPhase()`, filter stale completions in `refreshAgentStatuses()`
- `src/orchestration/phases.ts` — adjust `isAgentDone()` if needed

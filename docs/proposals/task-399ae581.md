# Proposal: Display milestone on the task detail and task list pages

## Goal

Surface a task's `milestone` (e.g. `v0.7.1`) in the dashboard's two task-browsing
views — the single-task **detail page** (`task.html`) and the multi-task **list
page** (`tasks.html`) — so a user browsing tasks can see which milestone a task
belongs to. The field is already fully parsed and modelled; this closes a
display-only gap. Render the milestone **only** for projects that opt into
milestones (`milestones: true` in `config.yaml`), and render nothing when a task
has no milestone or its project isn't opted in.

## Context

Tasks carry an optional `milestone` frontmatter field; milestones are enabled
per-project via `milestones: true` in `config.yaml`. The field is already:

- parsed and round-tripped (`src/tasks/types.ts`, `src/tasks/markdown.ts`),
- present on the `DashboardTask` model (`src/dashboard.ts`,
  `readDashboardTasks()` normalizes it to `string | null`),
- exposed via `milestonesEnabledProjects()` (`src/config.ts`), which today is
  `OCANNL` and `ppx_minidebug`.

What's missing is purely the rendering on the two requested views. The milestone
is sparse — most local `task-*`/`watch-*` tasks legitimately lack one — so
"render nothing when absent" is the common case and must be the default. A
project that hasn't opted into milestones could still carry a stray/legacy
`milestone:` value; those must be suppressed (gating decision below).

The full elaboration (pinned touch points, resolved questions, edge cases) lives
in `tasks/task-399ae581.md`.

## Acceptance Criteria

- [ ] On the **task detail page** (`task.html`), a task whose project has
      `milestones: true` and that carries a `milestone` value shows that value as
      a badge in the header badge row, alongside the existing status/priority/
      project badges.
- [ ] On the **task list page** (`tasks.html`), a task meeting the same
      conditions shows its milestone as a badge on the task row, alongside the
      existing priority/status/proposal badges.
- [ ] On **both** views, no milestone badge is rendered when the task has no
      milestone value, or when the task's project does not have `milestones: true`
      in config (stray/legacy values on non-opted-in projects are suppressed).
- [ ] The milestone badge reuses the existing neutral `task-badge` styling on
      both views — no new CSS in `style.css` / `content.css`.
- [ ] Quoted frontmatter values (`milestone: "v0.7.1"`) render as `v0.7.1`, not
      `"v0.7.1"` (the detail page's `parseFrontmatter` already strips quotes;
      confirm the badge reflects this).
- [ ] Tests cover both views following existing conventions, and the build/verify
      sequence (`bun run build; ludics init --no-triggers`) passes.

## Approach

Gating decision (resolved Q2): milestone visibility is restricted to projects
with `milestones: true`. The two views differ in where that check is cleanest, so
they're gated differently — each at the point that matches its existing data flow.

**Task list page — gate at the emitter (`src/dashboard.ts`).**
The list page consumes `data/tasks-tree.json` produced by `generateTasksTree()`.
The node type `TasksTreeNode` doesn't currently carry the milestone, so:

1. Add `milestone: string | null` to the `TasksTreeNode` interface.
2. In `buildTaskNode()`, set
   `milestone: milestonesEnabledProjects().has(task.project) ? task.milestone : null`
   on the returned node (compute the set once outside the recursion if convenient),
   and set `milestone: null` in the `fallbackNode()` helper.

This makes `tasks-tree.json` carry `null` for non-opted-in projects, so
`renderNode()` in `tasks.html` stays a pure `if (node.milestone)` guard and the
enabled-projects set never ships to the browser. In `renderNode()`, add a
milestone badge mirroring the existing priority/status/proposal pattern
(`document.createElement('span'); .className = 'task-badge'; .textContent = node.milestone`).

**Task detail page — gate client-side against an emitted enabled-projects list
(`task.html`).**
`task.html` reads frontmatter client-side via its in-template `parseFrontmatter()`,
so `meta.milestone` and `meta.project` are already available; there's no
server-side per-task data path to null the value the way the tree emitter does.
The chosen approach: have the dashboard generation emit the milestone-enabled
project list as a small JSON artifact (e.g. `data/milestone-projects.json`) and
have `task.html` fetch it (mirroring its existing `fetch` of `/task-files/...`),
then in `renderBadges(meta)` add a milestone badge guarded by
`meta.milestone && enabledProjects.includes(meta.project)`, reusing the
`task-badge` span pattern already used for status/priority/project. (If the coder
finds an existing emitted artifact that already carries the enabled-projects set,
reuse it rather than adding a new file.)

**Styling (resolved Q1):** reuse the existing `task-badge` class on both views; no
`style.css` / `content.css` change.

### Tests
- `templates/dashboard/task.test.ts`: extend the existing `parseFrontmatter` /
  template-content assertions to cover the milestone badge emit and the
  enabled-project gating.
- `src/dashboard.test.ts`: assert `generateTasksTree()` / `tasks-tree.json`
  carries the milestone for an opted-in project and `null` for a non-opted-in
  project bearing a stray milestone value.

### Verify
After code changes run `bun run build; ludics init --no-triggers`.

## Out of Scope

The ready-queue tile renderer (`dashboard.js` / `index.html`) is not part of this
task — only the detail page and the task-list page are requested.
`generateReady()` already includes `milestone` in `ready.json`, so surfacing it on
the ready tile is a possible follow-up, not included here.

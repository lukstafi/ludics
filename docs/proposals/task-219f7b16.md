# Proposal: Fix PROPOSAL_FRESHNESS_WARNING boundary test fixture

**Task:** task-219f7b16
**Effort:** tiny (mechanical edit)

## Goal

Eliminate the long-standing baseline test failure
`PROPOSAL_FRESHNESS_WARNING: boundary — exactly 10 commits does NOT trigger`
in `src/orchestration/skills.test.ts`. The freshness threshold was reduced
from `10` to `6` in commit `c0c929e` (PR #387), but the boundary test's
fixture and comment were left referring to `10`. Sync the test with the
current threshold so `bun test src/orchestration/skills.test.ts` is clean,
and coders stop having to stash + re-run + qualify this failure on every PR.

## Approach

Worker decision on the optional sibling test (Tentative Design called it
"recommended"): **include it.** Rationale — the existing `15 commits stale`
test exercises a non-boundary triggering case, which doesn't pin down the
exact `>` vs `>=` cutoff. With both `count = 6` (does NOT trigger) and
`count = 7` (DOES trigger) explicitly tested, any future off-by-one change
to the threshold check is immediately caught. Cost is one short test
(~20 lines, mirroring the `15 commits` test pattern). Worth it for a
test that has historically drifted out of sync.

Suggested edits in `src/orchestration/skills.test.ts` (the agent should
adjust to actual code style; this is illustrative):

1. Update the existing boundary test (around line 754):
   - Title: `"PROPOSAL_FRESHNESS_WARNING: boundary — exactly 6 commits does NOT trigger"`
   - Fixture: `initGitRepoWithProposal(projectDir, "docs/proposals/boundary.md", "# Boundary proposal\n", 6);`
   - Update any `Threshold is strictly > 10` comment to `Threshold is strictly > 6`.
2. Add a sibling test immediately after, e.g.
   `"PROPOSAL_FRESHNESS_WARNING: boundary — exactly 7 commits DOES trigger"`,
   using the same setup pattern but with `7` commits, asserting
   `toContain("Freshness warning")` and `toContain("7 commits")`.

The threshold constant itself is *not* imported into the test file — the
literals `6` / `7` are intentional and document the intended threshold by
example. Importing `PROPOSAL_FRESHNESS_THRESHOLD` would be a small
refactor and is out of scope for this tiny task.

The `15 commits stale` and `5 commits fresh` tests need no changes — their
titles and semantics remain accurate under threshold `6` (`5 < 6` is fresh,
`15 > 6` is stale).

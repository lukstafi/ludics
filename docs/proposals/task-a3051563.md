# Proposal: Dashboard liveness — add remote slot support via SSH PID check

**Task:** task-a3051563
**Project:** ludics
**Effort:** small

## Goal

Enable the dashboard and auto-resume logic to check orchestrator liveness on remote federation machines, replacing the current "skip remote slots" behavior with SSH-based PID checks and a new "Disconnected" status for unreachable machines.

## Acceptance Criteria

1. **Remote liveness in dashboard**: `generateSlots()` no longer skips remote-owned slots. Remote slots show "alive", "interrupted", or "disconnected" liveness status.
2. **New `sshExec` helper**: A low-level `sshExec(machineName, shellCmd)` function in `src/remote.ts` runs an arbitrary shell command over SSH (reusing existing `sshArgs` plumbing, 5s connect timeout).
3. **Single-SSH-call PID check**: A `remoteSlotLiveness(machineName, slotNum)` function in `src/remote.ts` performs one SSH round-trip that reads the remote slot state file via `jq`, extracts the orchestrator PID, and runs `kill -0` on it. Returns `"alive"`, `"interrupted"`, or `"disconnected"` (SSH unreachable).
4. **Extended liveness type**: The `SlotInfo.liveness` type is extended from `"alive" | "interrupted" | null` to `"alive" | "interrupted" | "disconnected" | null`.
5. **Dashboard rendering**: The frontend (`dashboard.js`) renders "Disconnected" status in red, distinct from "Interrupted".
6. **Auto-resume for remote slots**: `maybeResumeDeadOrchestrators()` in `src/mag.ts` handles remote slots: uses `remoteSlotLiveness` for liveness checks, and dispatches `remoteExecAsync(machine, ["slot", N, "resume"])` for dead remote orchestrators.
7. **`jq` in setup.sh**: `setup.sh` ensures `jq` is installed alongside other dependencies.
8. **Tests**: `src/dashboard.test.ts` covers remote liveness scenarios with mocked SSH (alive, interrupted, disconnected).

## Context

- `src/dashboard.ts:48-65` — `computeSlotLiveness()`, local-only PID check via `processAlive(pid)`
- `src/dashboard.ts:263-271` — `generateSlots()` explicitly skips remote slots for liveness
- `src/remote.ts:17-24` — `sshArgs()` internal helper (already builds SSH command with timeout/batch mode)
- `src/remote.ts:27-41` — `remoteExec()` runs `ludics` commands over SSH
- `src/remote.ts:62-69` — `remotePing()` checks SSH reachability
- `src/mag.ts:2274-2345` — `maybeResumeDeadOrchestrators()` uses local `process.kill(pid, 0)`
- `templates/dashboard/dashboard.js:115` — frontend renders `slot.liveness === 'interrupted'`
- `setup.sh` — dependency installation; `jq` used in step 5 but not explicitly ensured as a dependency

## Approach

### 1. `sshExec` and `remoteSlotLiveness` in `src/remote.ts`

Add a low-level `sshExec(machineName: string, shellCmd: string)` that runs an arbitrary command over SSH using the existing `sshArgs()` plumbing:

```typescript
export function sshExec(machineName: string, shellCmd: string):
  { success: boolean; stdout: string; stderr: string } {
  const hostname = resolveHostname(machineName);
  const cmd = [...sshArgs(hostname), shellCmd];
  const result = Bun.spawnSync(cmd, { stdout: "pipe", stderr: "pipe" });
  return {
    success: result.exitCode === 0,
    stdout: result.stdout.toString().trim(),
    stderr: result.stderr.toString().trim(),
  };
}
```

Then `remoteSlotLiveness(machineName, slotNum)` issues a single SSH call:

```
pid=$(jq -r '.orchestration.pid // empty' ~/self-improve/harness/t3code/slot-N.json 2>/dev/null);
[ -n "$pid" ] && kill -0 "$pid" 2>/dev/null && echo alive || echo dead
```

- If SSH fails (exit code from connection failure): return `"disconnected"`.
- If SSH succeeds with stdout `"alive"`: return `"alive"`.
- If SSH succeeds with stdout `"dead"` or empty: return `"interrupted"`.
- The harness path on the remote machine should be derived from `federationMachine(machineName)` config (add a `harness_path` field or default to `~/self-improve/harness`).

### 2. Extend `computeSlotLiveness` signature

Change `computeSlotLiveness` to accept an optional `machineName` parameter. When the machine is remote, delegate to `remoteSlotLiveness` instead of the local `processAlive` check.

Update the type from `"alive" | "interrupted" | null` to `"alive" | "interrupted" | "disconnected" | null` in both the function return type and the `SlotInfo` interface.

### 3. Update `generateSlots()` in `src/dashboard.ts`

Remove the `isRemoteMachine` guard that skips liveness. Instead, pass the machine name to `computeSlotLiveness`:

```typescript
liveness = computeSlotLiveness(num, getMode(block).trim() || null, machineName || null);
```

### 4. Update `maybeResumeDeadOrchestrators()` in `src/mag.ts`

- Remove the implicit local-only assumption. For each slot, check `getMachine(block)`.
- For local slots: keep existing `process.kill(pid, 0)` logic.
- For remote slots: call `remoteSlotLiveness(machineName, slotNum)`. If `"interrupted"`, dispatch `remoteExecAsync(machineName, ["slot", String(slotNum), "resume"])`.
- Skip slots with `"disconnected"` status (cannot resume what you cannot reach).

### 5. Dashboard frontend

In `templates/dashboard/dashboard.js`, add a case for `slot.liveness === 'disconnected'`:

```javascript
} else if (slot.liveness === 'disconnected') {
    statusDiv.className = 'slot-status disconnected';
    statusText.innerHTML = 'Disconnected';
}
```

Add CSS for `.slot-status.disconnected` with red styling, distinct from the orange/yellow of "Interrupted".

### 6. `jq` in `setup.sh`

Add a `jq` check-and-install block after the existing `tmux` block, using the same `install_pkg` helper.

### 7. Tests

Add test cases in `src/dashboard.test.ts` that mock `sshExec` / `remoteSlotLiveness` to return each status, and verify `computeSlotLiveness` returns the correct value for remote slots.

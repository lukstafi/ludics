# SWE Textbook — Mag-side Write Memory for Filter-Rejected Learnings

## Audience and Directionality

This document is a **write-only journal** with these constraints:

1. The file is **not** consulted by coder agents.
2. The file is **not** consulted by reviewer agents.
3. The only active consumers are Mag and the
   `/ludics-feedback-digest` worker.
4. Entries are write-side memory for **competent-SWE filter
   decisions** — items the filter would otherwise discard from
   always-loaded prompts (see
   `harness/claude-memory/feedback_competent_swe_filter.md`).
5. The corpus is also a **future publication seed**; entries should
   read in plain English, free of Ludics-internal jargon.

## Entry Shape

Each entry is a `### <headline>` section with the following labelled
fields:

- `Description:` one paragraph, plain English, publication-friendly.
- `Precipitating retro:` one of `task-…`, `gh-…`, or a PR URL.
- `Filter decision:` why a `/ludics-process-suggestions` or
  `/ludics-feedback-digest` run would skip this item under the
  competent-SWE filter.
- `Second occurrence:` *(optional)* — appended only when the same
  pattern repeats; carries the new precipitating retro and a
  one-line note.

## Capture Idempotency

This is the **only** location where the duplicate-guard logic lives.
Both `/ludics-process-suggestions` and `/ludics-feedback-digest`
MUST run this check before appending a new entry; both skills
reference this section by anchor
(`docs/swe-textbook.md#capture-idempotency`) and describe its
inputs/outputs in prose. **Skills MUST NOT copy the snippet below
into their own bodies** — duplicating the implementation across
skill files would defeat the single-source-of-truth invariant this
section enforces.

Inputs from the calling skill:

- `ENTRY_HEADLINE` — the proposed headline text **without** the
  leading `### ` markdown prefix; the guard prepends `### ` itself
  when it scans the textbook. (E.g., for an entry that will render
  as `### My pattern name`, the caller passes `ENTRY_HEADLINE="My
  pattern name"`.)
- `PRECIPITATING_RETRO` — the proposed `Precipitating retro:` value.

Outputs:

- `append` — no near-duplicate found; the caller writes a fresh
  `### <headline>` block with the four required labelled fields.
- `skip-duplicate` — a near-duplicate exists by either headline OR
  precipitating-retro; the caller MUST NOT append a new entry. The
  caller MAY amend the matched entry's `Second occurrence:` line
  with the new precipitating retro and a one-line note.

```bash
textbook="docs/swe-textbook.md"
if grep -Fq "### ${ENTRY_HEADLINE}" "$textbook" \
   || grep -Fq "${PRECIPITATING_RETRO}" "$textbook"; then
  echo "skip-duplicate"
  exit 0
fi
echo "append"
```

**Known soft-spot — `ASSUMPTION GAP` escalation.** The disjunctive guard
above (`headline OR retro`) returns `skip-duplicate` whenever a new entry
shares either key with any existing entry. The case it silently
collapses: a new entry whose `Precipitating retro:` matches an existing
entry's, but whose headline and `Filter decision:` describe a materially
distinct lesson. Under the bare contract the caller would amend the
matched entry's `Second occurrence:` line and drop the new lesson. When
the caller runs inside an orchestrated coder/reviewer pair, the right
move is to surface the choice in the merged plan with an
`⚠️ ASSUMPTION GAP: …` marker (per `pair-coder-plan-merge.md`) so the
reviewer sees and rules on the divergence at plan-merge time. When the
caller is a one-shot Mag invocation of `/ludics-feedback-digest` (no
merged plan), the equivalent discipline is to surface the choice in the
digest's result JSON and commit message rather than silently routing
through `skip-duplicate`.

### "Issue is updated" means an actual GH-side comment, not a one-way docs cite

Description: When a contract clause says an external issue tracker
entry is "updated" as part of acceptance, the update must be visible
on the tracker itself — a comment, an edited body, or a
closed/labelled state — not merely a one-way pointer from the
repository's own documentation. A docs file that links the issue is
not the same as the issue gaining a link to the docs file. A reader
checking the issue tracker for the update will see no change. Sister
contract clauses ("issue is closed," "issue is labelled") have the
same direction: the side named by the verb is the side that must
visibly change.

Precipitating retro: `gh-ocannl-270` (round-1 reviewer; retrospective
at `~/self-improve/harness/retrospectives/gh-ocannl-270.json`). The
reviewer's blocking line: *"AC6 is not satisfied because GitHub issue
#270 has not been updated to link to the committed memo. The proposal
requires 'GH issue #270 is updated to link to it'; the current issue
body still only links the Imbue article […]."*

Filter decision: Under the competent-SWE filter this would land in
the "obvious-to-experienced-engineer" bucket and be discarded from a
`/ludics-process-suggestions` run — yet the failure mode survives
competent engineers under deadline pressure (the contracted artifact
lives on the *other* side of the fence). Captured here rather than
skipped silently.

### New OrchestrationConfig fields require parse+merge in adapter init

Description: A typed configuration object that drives runtime
behaviour usually has four independent surfaces a new field has to
land on: the interface declaration, the in-code default, any
backfill the persistent-state migrator applies to old records, and
the parse+merge step the initialisation path performs against the
user-facing YAML. The first three are easy to spot — they live next
to each other in the same file or test — and a typed compiler will
flag drift between them. The fourth is the most distant from the
field declaration and the least visible to the type checker: if the
init path never reads the YAML key, the documented config is
silently inert and the field always takes its default. Adding a
shared parser called from each init consumer is the cheapest way to
keep the fourth surface visible. The pattern: a single helper named
after the value it produces, called from each adapter's existing
config-load consumer, fed into the partial-config record that the
defaults function consumes — so the adapter knows to read the YAML,
the parser knows the shape, and the merge knows the precedence.
Test the parser as a unit; integration coverage at the call sites
catches regressions there.

Precipitating retro: `task-a670cdbf` round-2 review of PR #493
(settled-no-signal / hung-detection split). The reviewer's blocking
line: the new `mag.orchestration.substantive_stall.*` YAML keys
were documented and runtime-honoured, but neither adapter init
extracted them from the YAML — so the keys were silently inert
until the round-2 fix shipped a shared
`parseSubstantiveStallOverrides` parser called from both adapter
call sites.

Filter decision: Under the competent-SWE filter this is an
"obvious-to-experienced-engineer" doctrine reminder — wiring up the
read site is part of the same change as adding the field, by
definition. Captured here rather than promoted to always-loaded
agent prompts because the failure mode survives competent engineers
under deadline pressure when the four surfaces sit in different
files. The same precipitating retro is closed mechanically by the
adapter-call-site lint shipped in gh-ludics-496, which makes the
typed-default-plus-backfill checkbox no longer sufficient.

### "Adapter init reads YAML" is a separate AC for OrchestrationConfig field additions

Description: When an acceptance criteria list enumerates the surfaces
that have to change for a new typed config field — interface,
default, migration backfill — the adapter init path's read of the
user-facing YAML is easy to bundle into the umbrella line "config
field exists". That bundling lets a typed-interface-plus-default
checkbox count as completion even when the YAML is silently
ignored. The remedy is to give the init-side read its own AC,
phrased as a behavioural property at the user-visible boundary
("setting the YAML key to a non-default value produces the
non-default behaviour"), distinct from any structural AC about the
type or the default. The behavioural framing makes the AC
falsifiable by an end-to-end test that sets the YAML and observes
the runtime, not by an inspection of the type declaration.

Precipitating retro: `task-a670cdbf` round-2 review of PR #493. The
proposal's AC list bundled the YAML-read step into "config field
exists"; round-1 implementation satisfied the structural ACs without
satisfying the behavioural one, and the gap surfaced only at
round-2 review.

Filter decision: Under the competent-SWE filter this is also
"obvious-to-experienced-engineer" doctrine — separate ACs for
separate surfaces is general AC-writing hygiene. Captured here
rather than promoted to AC templates loaded by always-on agent
prompts because the doctrine is most useful as guidance to humans
writing proposals, not as a rule enforced at every coder turn. The
mechanical lint from the sibling entry above closes the same
failure mode for the specific case of `OrchestrationConfig` fields.

### Run mutation tests before writing the AC verification line that claims them

Description: An AC verification line that asserts "mutation: changing X to Y flips the assertion from pass to fail" only earns its evidence weight when the mutation has actually been observed. The temptation under deadline pressure is to write the line based on a confident mental model — flip the literal mentally, predict the failure, write the verification — then run the mutation later (or skip the run entirely because the suite was green). The right discipline reverses the order: edit the source, run the test, observe the failure message verbatim, revert the edit, then write the verification line citing the observed message. The mutation-as-prediction failure mode is silent — a wrong prediction passes review because reviewers can't easily distinguish "ran and observed" from "thought through and described" — but the cost surfaces later when an actual regression slips past a vacuously-passing assertion.

Precipitating retro: `task-c4e0e80a` round-1 (coder feedback, 2026-05-05). The coder explicitly noted: *"I asserted 'mutation: the AC7 walker test failed loudly when I temporarily added the string' before actually running that mutation, then ran it after the AC verification was already written. The claim happened to be true, but the order was sloppy."* Same pattern echoed in gh-ludics-497 round 1 (the coder ran the mutation as a "scratch run during implementation" but documented the discipline rather than relying on a prediction).

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" discipline — running the experiment before writing the result is general scientific method. Captured here rather than promoted to always-loaded agent prompts because the failure mode is invisible (the line reads correctly either way) and rule-by-rule enforcement at every coder turn would be heavy-handed; #478's "mutation testing as standard AC verification" issue closes the broad case at the policy layer, and the textbook entry preserves the order-of-operations refinement for future readers.

Second occurrence: `task-2445dd1c` rounds 1–3 (coder feedback, 2026-06-12, PR #32). Three successive reviewer asks on per-shard RNG were each "this test passes vacuously"; each round was unblocked only by actually running the *mutated* data-parallel driver (e.g. `base_seed + i` → `base_seed`) and watching the assertion flip before writing the verification line. Confirms the pattern recurs precisely where a same-seed draw already diverges via distinct `self_id`, so only the executed mutation distinguishes a real falsifier from a vacuous one.

Third occurrence: `task-9658aac9` rounds 1–2 (coder durable learning, 2026-06-20, PR #62). Round 1 shipped a parity/no-fault test (`affine_lowering::ac_debug_guard`) on a path where the Stage B unit-solve `Where` is buried in a non-logged `Local_scope` — it never reaches `debug_float`, so the assertion passed with or without the fix. Reviewer flagged it vacuous; round 2 added `test_stage_b_where_debug.ml` building the exact Stage B `Where (range_cond, Get producer, Get_local id)` in a *logged* top-level `Set` and asserting `? producer[i1] : 0)`, mutation-verified by reverting the `guarded_value` wrap and watching it flip. Adds the reachability dimension to the lesson: confirm the hazard actually fires on the path the test exercises (dump the generated artifact) — a mutation line is meaningless on a path where neither the bug nor its fix is reachable.

### When introducing a new AC pattern at the reference layer, instantiate it in the same proposal's own ACs

Description: A reference-layer doc (e.g. `docs/ac-rigor-reference.md`) that introduces a new AC pattern — a (b)-form scope invariant, a per-seam harness shape, an idempotency guard — gains evidence weight when the proposal that *introduces* the pattern instantiates it in the proposal's own AC list. Two effects: (a) the pattern is demonstrated in a working example in the same diff that documents it, so a future reader sees both the prose and a worked instance; (b) the new pattern survives any environmental drift the proposal itself triggers (e.g. a proposal-on-main commit advancing the merge-base, which is exactly the failure mode the new clause names). The pattern stays a piece of inert prose if the proposal's own ACs don't reach for it; eating-your-own-dog-food makes the prose battle-tested before merge.

Precipitating retro: `task-097cca67` round 1 (coder feedback, 2026-05-05). The proposal added a new (b)-form "scope invariant" clause to `docs/ac-rigor-reference.md` and AC10 of the same proposal was phrased as a (b)-form invariant — "no `src/**`, `scripts/**`, `templates/**`, or `*.test.ts` path appears in `git diff --name-only main...HEAD`" — rather than the more brittle "exactly these two paths appear" form. The (b)-form survived the merge-base-advance reproduction the new clause describes; the brittle form would not have.

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" doctrine — using a new pattern in its own definition is a standard refactor-discipline tell. Captured here rather than promoted to `ludics-draft-proposal-worker` checklists because the doctrine is most useful as a hint to the proposer at draft time, not as a rule enforced at every proposal turn; the proposer who writes a proposal that defines a pattern is the one most able to instantiate it cleanly, and a generic checklist would mostly fire on proposals that don't introduce reference-layer patterns.

### Symmetric-OR ACs need each arm's own dedicated harness, and no implementation short-circuit

Description: When a contract clause names two failure conditions joined by an OR ("exit on A OR B"), an implementation that exits early on A alone passes every test that only exercises A — even though the second arm is silently disabled. The fix shape is mechanical: (a) the implementation does not short-circuit downstream of one arm; if the contract names an OR, the run loop computes both arms before deciding; (b) the test harness contributes four conditions per OR pair (paired/unpaired × arm-1/arm-2), with a load-bearing `not.toContain(<other-arm's-evidence-string>)` negative assertion in each arm-unpaired test to catch implementations that route through the wrong machinery; (c) the AC self-check enumerates each arm separately, citing the dedicated test for each. The failure is silent under the original symmetric AC because review questions like "does this test pass?" check arm-1 only.

Precipitating retro: `gh-ludics-479` round 1 (coder feedback, 2026-05-03). The proposal AC was *"0 = paired, 1 = asymmetry (added/changed field with no migrator change OR migrator change with no test fixture)"*. Round 1's `lint:state-migration` short-circuited to `exit 0` whenever `checkShapes(...)` returned `[]`, so the second arm (migrator change without test fixture) was unreachable; round-1 tests only exercised the first arm. Reviewer flagged with REQUEST_CHANGES; round 2 extracted `enforceMigratorTestPairing` and added four harness conditions plus the `not.toContain` negative assertions.

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" test discipline — exercising both branches of a disjunctive contract is general logic-coverage hygiene, and the reviewer caught it cleanly in a single REQUEST_CHANGES round. Captured here rather than promoted to a new clause in `docs/ac-rigor-reference.md` (the originally proposed "doctrine" landing) because the catch-net works without a preamble bullet, the auto-memory `feedback_or_clause_ac_no_short_circuit.md` already covers the coder-side artifact, and adjacent memories (`feedback_per_seam_harness_for_multi_boundary_ac`, `feedback_short_circuit_ac_observe_outcome`) cover overlapping territory at the always-loaded layer.

Second occurrence: `gh-ludics-531` round 2 (coder workflow-feedback, 2026-05-19, PR #541). The `lint:vendor-sync` freshen gate `!argRoot && !process.env.CI` is a symmetric OR over the skip clauses; round 1's single "argRoot OR CI skips" test passed whether or not both arms worked. Round 2 split it into "argRoot skips (CI unset)" and "CI=1 skips (no argRoot)" using a PATH-shimmed poisoned `bun` in each — proving each clause independently. Mutation evidence: dropping `!argRoot` makes the argRoot test fail (the poisoned-bun sentinel appears in stderr); dropping `!process.env.CI` makes the CI=1 test fail.

Third occurrence: `task-75d77a71` round 1 (coder durable learning, 2026-06-15, PR #565). The `lint:test-isolation` pin-mismatch diagnostic `formatPinMismatch(observed, expected, …)` has two arms — UP (`observed > expected`, recommend `withSyntheticHarness`) and DOWN (`observed < expected`, recommend lowering the pin). Presence-only assertions on the UP arm don't falsify a DOWN arm that wrongly emits the harness advice; the coder's own learning was that the DOWN test must carry a load-bearing `not.toContain("withSyntheticHarness")`. Same shape as the OR pairs above: each arm needs a dedicated test with a negative assertion against the *other* arm's evidence string.

### "Do X then continue" ACs need an assertion downstream of the fall-through

Description: When an AC reads "do X then continue / proceed", a single assertion on the artifact of X (a file rewrite, a journal event, a log line) is insufficient: a regression that performs X correctly and then immediately `return`s passes every X-side assertion, because each side-effect happened before the unwanted early exit. The test must observe both — the artifact of X **and** something only the proceed-arm would produce (e.g. a downstream phase transition, a counter incremented later in the loop, an output that only the continued path emits). The reusable mutation a reviewer can name: "what if the implementation did the side-effects and then returned?". If no assertion in the test would notice, the harness is not yet a falsifier of the AC's "then continue" half.

Precipitating retro: `gh-ludics-509` round 2 (coder feedback, 2026-05-09). The reclaim path's first round shipped tests asserting file-rewrite, journal event, and reclaim-log — all of which fire before any hypothetical `return;` after `emitEvent`. Reviewer REQUEST_CHANGES specifically asked for the proceed-arm half; round 2 added `expect(transitionCalls).toBeGreaterThan(0)` and `expect(state.phase).toBe("done")` against a spied `evaluateTransition`, then ran the actual mutation (insert `return;`, watch the new asserts fail, revert) before signalling done.

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" test-completeness discipline — exercising the full path the AC names is general AC-writing hygiene, and #478's mutation-evidence coverage already names the broad rule. Captured here rather than promoted to always-loaded prompts because the failure mode is shape-specific (the side-effects-before-return pattern) and most usefully delivered as a reviewer probe ("what if the implementation did X and then returned?") rather than a per-coder checklist; the textbook entry preserves the reusable mutation question for future reviewers.

### "Does NOT do Y" invariants need observation at Y's persistent surface, not adjacent narration

Description: When an AC asserts "the runner must NOT mutate file F" / "must NOT write key K", asserting the adjacent log line ("X mismatch — exiting") is insufficient: a regression that emits the log AND silently writes anyway passes every log-side assertion. The honest harness reads F (or K) post-hoc and asserts the value the regression would have changed (`expect(persisted.field).toBe(originalValue)`). Generalises: for any negative invariant, observe the named artifact at its persistent surface (file/db/in-memory map), not at adjacent narration that fires regardless of the mutation. The mutation a reviewer can name: "what if the code logs the same message but also performs the forbidden write?"

Precipitating retro: `gh-ludics-509` round 2 (coder feedback, 2026-05-09). Pre-existing live-mismatch trio asserted the `"PID mismatch ... exiting"` log fired, but the log fires regardless of whether the file was rewritten. Round 2 added `expect(persisted.orchestration.pid).toBe(wrongPid)` after `runOrchestration` returns, observing the no-rewrite invariant at its persistent surface.

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" test discipline — observing the named artifact at its persistent surface is general negative-AC hygiene, and the reviewer caught it cleanly. Captured here rather than promoted to `docs/ac-rigor-reference.md` because the failure mode is symmetric to the "X then continue" entry above (both are about asserting the right place for a multi-effect AC) and adjacent always-loaded memories already cover the broader vacuous-harness family at the policy layer.

### Heading-literal exact-count grep falsifiers count intra-doc cross-links too

Description: When a doc-AC's falsifier reads `grep -cF '<full heading text>' <file>` returns *exactly* N, any *other* place in the doc that quotes the same literal (a markdown link's bracket text, a bold inline reference, a `> blockquote` paraphrase) flips the count silently — the heading itself stays unique, but the AC fails because the grep is unconditioned by line position or markdown role. The remedy when adding intra-doc cross-links to a uniquely-headed clause: paraphrase the link text rather than reproducing the full heading literal in the bracket. The Stash-prod precedent uses bold-name (`**No-regression framing when the gate baseline is red**`) for exactly this reason — it's a clause reference, not a clause-text reproduction. After landing a new heading clause whose AC pins exact-count, grep the literal across the touched doc(s) and verify the count matches before signalling done.

Precipitating retro: `task-4335d903` round 1 (coder feedback, 2026-05-09). A reverse cross-link in the new Sibling-mutation clause body — `[Closed-set / cardinality ACs — set-equality is the strongest probe shape](#anchor)` — repeated the heading literal in the link's bracket text, so `grep -cF` returned 2 against the AC's "exactly one hit" invariant. Caught only by running the AC's literal probe; visual review missed it because both occurrences read as "talking about the same clause." Fix was paraphrase to `**set-equality probe shape**`.

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" doc-author discipline — knowing that grep counts substring occurrences regardless of markdown role is general doc-tooling literacy. Captured here rather than promoted to a new `docs/ac-rigor-reference.md` clause because the failure mode is narrow (heading-literal-exact-count ACs combined with intra-doc cross-links) and the post-edit grep-the-literal hygiene reads as "obvious" once named; the textbook entry preserves the cross-link-bracket paraphrase precedent for future readers.

### State-repo file paths in proposals need an explicit `~/<state-repo>/` qualifier

Description: When a proposal AC names `config.yaml`, `tasks.yaml`, `briefing.md`, `journal/events.jsonl`, or any other harness artefact and writes a falsifier like `grep -c X config.yaml`, that grep target almost always lives in the user's private state repo (mounted at a fixed path under the user's home dir), not in the project worktree the PR opens against. CLAUDE.md is explicit on this separation. When a proposal's AC and "PR contains N commits" wording disagree about where a file lives, the correct fix is to revise the AC in the same PR (qualifying the path with the explicit `~/<state-repo>/...` prefix) rather than fabricate a path-substitution narrative or quietly re-target the grep at a sibling path. The reviewer can then accept-or-push-back on the revised partition explicitly.

Precipitating retro: `gh-ludics-502` round 1 (coder feedback, 2026-05-09). Proposal AC4/5/8 named `config.yaml` (intent: harness `~/self-improve/harness/config.yaml`); proposal text "PR contains N commits" implied all changes land in the project repo. Implementer revised the AC in commit `75a3bfc` to acknowledge the cross-repo split (companion commits in the state repo and a sibling staging worktree) rather than substitute a path-translation narrative.

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" proposal-authoring discipline — naming an unambiguous absolute path is general spec hygiene, and the same-PR-revision rule (`feedback_self_contradicting_ac_revise_not_fabricate.md`) already covers the broader case. Captured here rather than promoted to always-loaded prompts because the failure mode is specific to the cross-repo-state architecture (the proposer's mental model conflates "harness file" with "this repo") and most usefully named at the proposal-authoring step, not enforced at every coder turn; the textbook entry preserves the qualifier discipline for future proposal authors.

### Dogfood-the-discipline ACs ship code as literals, not paraphrased prose

Description: When a doc-AC requires a new clause's body to "contain the recipe inline" — a worked code snippet that demonstrates the discipline the clause names — the non-vacuous shape is to ship a complete fenced code block with all the named tokens as literals (function names, variable names, assertion expressions). Paraphrasing the recipe into prose ("seed a file, then assert byte-identity") would pass a reader's smell test but fail a literal-grep AC, and — more importantly — would not be mutation-testable: removing any one named token from a literal recipe flips the falsifier; paraphrased prose has no such single-edit handles. The precedent: `### Stash-prod mutation test` carries the literal `git stash push --` command form in its body. Generalises: ACs that assert "X is demonstrated inline" should pin specific call/expression literals, and clause authors should write the literals (not the paraphrase) to satisfy them.

Precipitating retro: `task-a1e55a19` round 1 (coder feedback, 2026-05-10). New `### Real-decoy + byte-identity for path-safety probes` clause's AC8 required `writeFileSync(decoyPath, decoyContent);`, `readFileSync(decoyPath, "utf8")`, `expect(after).toBe(decoyContent)`, and `decoyPath = join(siblingDir, "decoy.md")` to all appear inside the new clause's body. Implementer shipped a fenced ```ts``` block with all four literals, making the recipe both the documentation and the mutation-target.

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" doc-author discipline — knowing that paraphrased prose has no grep-able handles is general doc-tooling literacy. Captured here rather than promoted to a new `docs/ac-rigor-reference.md` clause because the pattern is narrow (a sub-shape of "literal-grep AC") and most usefully named as a precedent for clause authors, not as a per-coder rule; the textbook entry pairs with the heading-literal entry above to cover the "literals over paraphrase in doc-AC bodies" theme.

### Test the AC's load-bearing call site, not the leaf function whose argument is forwarded

Description: When an AC names a chain `A → B(x) → C(x')` — a binding at a call site `A` is supposed to flow through a helper `B` to a leaf `C` — a test that calls the leaf `C` directly and asserts the forwarded argument is a tautology, not a falsifier of the AC. The failure mode the AC describes (a future regression at `A` swapping `agent.worktreePath` for some shared path) is unreachable from a test that never exercises `A`. The fix shape is mechanical: when the AC's call site is buried inside a heavyweight orchestrator (one that builds adapter context, persists state, spawns subprocesses, …), extract the smallest enclosing scope that owns the AC's data binding into a named export, and call the helper from both the orchestrator and the test. The exported helper IS the test seam; the orchestrator becomes a thin wrapper. Heuristic for when to extract vs stand up the full integration harness: when the chain from public surface to the AC's seam crosses ≥3 heavyweight side-effecting calls, prefer the helper-extraction (one extra public symbol, no runtime change) over spying ≥5 collaborators. ### AC asymmetry — "X uses Y" hides "non-X does NOT use Y"

### Greedy regex extraction over markdown table cells is vacuous against column drift

Description: When an AC's falsifier extracts a structured value from a markdown table cell — issue numbers, statuses, paths — a regex like `sed -E 's/.*#([0-9]+).*/\1/'` extracts the **last** match per line, not the column-1 value. The class generalises: any falsifier that walks markdown table rows with greedy `.*` must anchor to the column it reads, not rely on uniqueness of the substring shape across columns.

### Union-type evidence ACs need per-row anchor coverage, not just per-type existence

Description: When an AC says "every row's evidence cell carries at least one of: (a) doc path, (b) date, (c) code pointer, (d) cross-reference", a falsifier that checks each anchor *type's existence across the table* (e.g., `grep -oE 'docs/[a-z]+\.md' | test -f`) is vacuous: it passes as long as *some* row uses each anchor type, even if other rows carry no anchor at all. The honest falsifier is per-row coverage: for each row, compute `has_a || has_b || has_c || has_d` and report `MISSING-EVIDENCE` if none holds. The shape (awk-style):

```
awk -F'|' '/^\| \[#[0-9]+\]/ {
  cell = $4;
  has_path = match(cell, "docs/[a-z0-9_/-]+\\.md") > 0;
  has_date = match(cell, "[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]") > 0;
  has_code = match(cell, "[a-z_]+\\.ml") > 0;
  has_xref = …;  # cross-reference to a different row number
  status = (has_path || has_date || has_code || has_xref) ? "OK" : "MISSING-EVIDENCE";
  print status;
}' <file>
```

The general rule for union-type ACs: a falsifier that checks "at least one row has type X" is necessary but not sufficient; the falsifier the AC actually names ("every row has at least one of {X,Y,Z}") needs per-row coverage. Notation pitfall: awk's `/.../` regex literal treats `/` as the delimiter, so `(cell ~ /docs\/foo\/bar/)` opens a character class containing `/` — use string-form `match(cell, "docs/...")` instead.

Precipitating retro: `task-a993fe29` round 3 (coder feedback, 2026-05-12). ### `git rm` pre-stages deletions that ride along on the next selective commit

Captured rather than promoted because the always-loaded `feedback_short_circuit_ac_observe_outcome` and `feedback_runtime_sentinel_claim_verify` cover the broader runtime-verification policy; this textbook entry adds the specific "two negations may hide a third state" diagnostic ("walk the production lifecycle, especially around pop/write atomicity") and pairs naturally with the spec-reading entries already in this file.

### Test seams must not weaken the production invariant the AC names

Description: When a regression test needs to exercise a production code path that's gated by an invariant the AC literally names, the temptation is to add an in-source seam — an env var, a `forceX || …` flag, an `opts: { skipGate }` injection — that lets the test punch through the gate. This degrades the gate the AC literally names: a production-code knob whose only consumer is the test suite is a production-code knob the next refactor will misuse, and the seam silently expands the precondition set in a way that's invisible at code-review time. The fix shape is to delete the seam entirely and reach for a harness that exercises the spawn / IO at the same boundary production uses — PATH-shimming for a subprocess gate, a tmpfs fixture for a filesystem gate, `mkdtempSync` + env override for a config gate — so the test exercises the gate's outside surface without weakening its inside contract. Reviewer-side heuristic: any new `force…` flag, `LUDICS_X_OVERRIDE` env var, or `opts: { … }` injection on a code path the AC's gate names should fail review with "rewrite the harness, not the gate."

Precipitating retro: `gh-ludics-531` round 1 → round 2 (coder workflow-feedback, 2026-05-19, PR #541). Round 1 added `shouldFreshen = forceFreshen || (!argRoot && !process.env.CI)` so a `LUDICS_VENDOR_SYNC_INSTALL_CMD` seam could force the spawn-path test even when `argRoot` was provided. Reviewer rejected: the AC literally pinned the gate as `!argRoot && !CI`, and the env-var seam silently expanded the precondition that triggers a freshen. Round 2 deleted the seam entirely and rewrote the freshen-path tests to use a PATH-shimmed fake `bun` (`makeFakeBun({kind, …})` helper) that exercises the spawn boundary without any in-source knob. The strict gate is now `const shouldFreshen = !argRoot && !process.env.CI;` literal.

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" test-design discipline — knowing that a test seam can degrade the invariant it tries to exercise is general harness-author literacy, and the reviewer caught it cleanly in one REQUEST_CHANGES round. Captured here rather than promoted to `docs/ac-rigor-reference.md` or pair-reviewer prompts because the failure mode is recognition-shaped (the coder must see when an in-source knob weakens the AC's gate), and the reviewer-as-catch-net works once "no force flags on gated paths" is a reviewer's named probe; the textbook entry preserves the rewrite-the-harness-not-the-gate precedent for future failure-path tests.

### AC harness conditions name the gate evaluation, not just the side effect

Description: When an AC pins a regression test's harness shape — "drives the CLI without argRoot," "invokes the function with no `opts`," "runs with `CI=` unset" — the literal harness words name the gate evaluation the test must pin, not merely the side effect the test must observe. Two test mechanisms can both end up firing the same spawn / side effect: one that drives the CLI without the named exclusion, and one that drives it *with* the exclusion plus an env-var override that punches through. Only the first proves the property the AC names. The second pins a different property: "the override punches through the gate" — i.e., that the gate is *not* required, which is the inverse of what the AC asks for. The fix is literal: re-read the AC's harness vocabulary as a sentence about the gate, then pick the mechanism that exercises that gate in its named state, not a mechanism that fires the downstream side effect by another route.

Precipitating retro: `gh-ludics-531` round 1 → round 2 (coder workflow-feedback, 2026-05-19, PR #541). Round 1's positive regression test (`"freshen step runs…"`) drove the lint CLI *with* `argRoot=fixture` plus `LUDICS_VENDOR_SYNC_INSTALL_CMD=…` to force the spawn, claiming AC4 ("CLI without argRoot") satisfaction. Reviewer pointed out the harness pinned the opposite property: that the env-var seam could override `argRoot`. Round 2 rewrote the test to drive the CLI with no positional `argRoot` (so the production gate evaluates `!argRoot && !process.env.CI → true`) and a PATH-shimmed fake `bun` recording the spawned argv. The AC's harness wording — "without argRoot" — now matches the mechanism.

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" AC-reading discipline — reading the harness vocabulary as a sentence about the gate is general AC literacy, and the catch-net works once a reviewer sees the mismatch. Captured here rather than promoted to `docs/ac-rigor-reference.md` because the failure mode is recognition-shaped (the coder must see when "drives X without Y" pins the gate evaluation, not just the side-effect fire), and the pattern pairs naturally with the "Test seams must not weaken the production invariant the AC names" entry above as the AC-side dual of that production-side discipline.

### PATH-shim harness for subprocess-boundary tests

Description: When a test needs to assert that production code spawned a specific external command — and the command's success / failure / argv matters — the reusable shape is: (a) `mkdtempSync` a `tmpbin/` directory; (b) write a tiny `#!/bin/sh` shim there that intercepts the argv prefix you want to pin (e.g. `install --frozen-lockfile`) and records it to a sentinel file, then `exec`s the real binary for anything else; (c) invoke the script under test via `process.execPath` so the outer process bypasses the shim; (d) set `env.PATH = tmpbin:$PATH` so only the inner `cmd: ["bun", …]` resolution hits the fake. This exercises the spawn boundary production uses — the `bun` argv resolution through `PATH` — without any in-source seam in production code. Two complementary shapes follow naturally: a `kind: "ok" + sentinel` variant (records argv, exits 0) for positive-spawn assertions, and a `kind: "fail" + stderr` variant (records nothing, exits 1 with a known stderr substring) for hard-error path assertions. The pattern generalises to any subprocess gate where production calls a binary by name. Combining a record-argv shim with `not.toContain(<downstream-output>)` assertions also gives an ordering pin: if downstream code never sees the side effect, the absence of its output proves the short-circuit happened.

Precipitating retro: `gh-ludics-531` round 2 (coder workflow-feedback, 2026-05-19, PR #541). The `lint:vendor-sync` regression suite needed to prove (i) the production spawn fires on the bare no-arg CLI, (ii) `argRoot` skips it, (iii) `CI=1` skips it, (iv) a failing install hard-aborts before `checkPairs`. All four shapes were satisfied by one `makeFakeBun({kind, …})` helper in `scripts/lint-vendor-sync.test.ts`: `kind: "ok"` for the positive spawn assertion (records argv, byte-exact `.toBe("bun install --frozen-lockfile\n")`); a poisoned-bun variant for the gate-skip assertions (exits 1 with sentinel stderr — if the gate fails to skip, the sentinel appears and the test flips); `kind: "fail"` for the hard-error path (records nothing, propagates stderr).

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" subprocess-test discipline — knowing that PATH resolution can be hermetic-shimmed is general CLI-author literacy, and the helper already lives in the test file's source for future grep discovery. Captured here rather than promoted to `docs/testing-patterns.md` or a shared `src/test-utils.ts` extraction because the helper is local to one consumer today and premature abstraction would tax every test reader without a second consumer demanding it; the textbook entry preserves the pattern shape (tmpbin + `#!/bin/sh` + exec real-binary + `env.PATH` override) for publication-friendly reuse and as the precedent the next subprocess-gate test should grep for. Companion to the "Failure-path tamper-and-restore harness pattern for CLI exit-code ACs" entry above — both are hermetic-CLI-test patterns; tamper-and-restore pins file-state surfaces, PATH-shim pins subprocess-spawn surfaces.

### Assert the absence of downstream output to pin a short-circuit

Description: When an AC says "do X, then short-circuit Y" — a regression must perform X but skip an otherwise-active downstream code path Y — the straightforward exit-code + diagnostic assertions are insufficient: a regression that fires X correctly and *also* falls through to Y still satisfies the X-side assertions, and a non-zero exit can come from either branch. To pin "Y NEVER runs after X," assert the *absence* of Y's distinguishable output strings — both Y's success banner AND Y's failure banner — so any path through Y flips the test. The mutation a reviewer can name: "what if the code did X and then also ran Y?" If no assertion in the test would notice, the harness isn't a falsifier of the short-circuit half. Generalises to any "X then NO Y" AC, regardless of whether Y is a subroutine, a phase transition, a downstream lint, or another side-effect.

Precipitating retro: `gh-ludics-531` round 1 → round 2 (coder workflow-feedback, 2026-05-19, PR #541). AC2 said a failed `bun install --frozen-lockfile` is a HARD error (not a silent skip) — meaning `checkPairs` must NOT run after the install fails. Round 1's hard-fail test asserted exit-code non-zero plus the AC's exact diagnostic substring, but didn't pin that `checkPairs` was skipped: a regression that emits the error message and then falls through to `checkPairs` (which would in the real repo's currently-in-sync state emit `"byte-for-byte"` then exit 0 or 1 depending on drift) passes every exit-code + diagnostic assertion. Round 2 added `expect(stderr).not.toContain("vendor-sync violation")` AND `expect(stdout).not.toContain("byte-for-byte")` — both of `checkPairs`'s distinguishable outputs. The mutation evidence: replacing `process.exit(1)` with `console.warn` + fall-through emits "byte-for-byte" and flips the assertions.

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" test-completeness discipline — naming a downstream code path as "absent" rather than just "exit code non-zero" is general short-circuit-AC hygiene. Captured here rather than promoted to always-loaded prompts because the failure mode is recognition-shaped (the coder must see what Y's distinguishable strings are, then pick assertions that pin both Y's success AND Y's failure banner). Pairs naturally with the existing "'Do X then continue' ACs need an assertion downstream of the fall-through" entry above (the positive dual: assert Y's continuation output) and "'Does NOT do Y' invariants need observation at Y's persistent surface, not adjacent narration" entry (the artifact-surface dual: when Y is persisted, assert the persistent surface; when Y is purely transient, assert the output bands).

### Adding a check between two fixture knobs reveals their latent mismatch

Description: When a regression-test fixture relies on two related knobs — a config mock and a spy return value, two arguments threaded through helpers, an expected URL and a project repo slug — the values often differ slightly without consequence because no test assertion compares them. Adding a new check that consumes both knobs together (a slug-equality assertion, a path-membership assertion, a value-flow invariant) surfaces the latent drift the *round you write the assertion*: every "happy path" test in the describe block silently flips into the failure branch, and the existing positive-control assertions start failing. The fix shape is mechanical: at plan-time, before any code, grep the describe block for both knobs, list the call sites where each is set, and realign the values in the same commit that introduces the new assertion. Generalises to any cross-fixture invariant: two test inputs that "happen to mismatch" become test failures the moment something asserts their relationship.

Precipitating retro: `gh-ludics-529` round 1 (coder workflow-feedback, 2026-05-19, PR #543). The runner-side base-repo assertion (compare PR URL slug against `findProjectConfig().repo`) flipped every existing eager-repair happy-path test from green to red. `runner.verification.test.ts:1021` had been mocking `findProjectConfig → repo: "org/test-repo"` while the `validateAndFixPrFile` spies returned `https://github.com/org/repo/pull/1` (`org/repo`). The mismatch was invisible until the new `prUrlBelongsToRepo` check compared the two slugs. The reviewer's plan caught it before code by grepping the describe block for both knobs at plan-merge time; realignment landed in the same commit as the new assertion.

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" test-fixture discipline — knowing that adding a cross-fixture invariant surfaces all pre-existing drift is general harness-author literacy, and the reviewer's plan-time grep catches it without preamble bloat. Captured here rather than promoted to always-loaded prompts because the failure mode is recognition-shaped (the coder must see, the moment they design a cross-fixture invariant, that they need to grep both knobs across the describe block) and most usefully delivered as a plan-time discipline cue ("grep the two knobs you're about to compare"), not a per-coder checklist; the textbook entry preserves the cross-fixture grep precedent for future check-introducing PRs.

### Helper false-on-missing-input and AC skip-when-config-absent are semantically opposite at the call site

Description: When a helper that compares two values (e.g. `belongsToRepo(url, repo)`) returns `false` for a missing or blank second argument, that `false` is semantically correct as a helper output ("this URL does not belong to a blank repo") but is the *opposite* of what the AC names when the AC says "no-op when no config is present." A blank-`repo` helper-`false` reaches a guard like `if (!belongs) { fail() }` and trips the failure path — the exact inverse of "skip the check." The fix shape is to keep the AC's skip-when-absent guard at the call site (`if (projectRepo && !belongs)`), not in the helper; the helper's own missing-input guard becomes defence-in-depth, not the AC enforcement point. Generalises to any compose pattern where a helper's "false on degenerate input" is the right helper API but the *wrong* call-site semantics: the call-site short-circuit on the input being present-and-nonempty must precede the helper invocation.

Precipitating retro: `gh-ludics-529` round 1 (coder workflow-feedback, 2026-05-19, PR #543). `prUrlBelongsToRepo(url, "")` returns `false` (the helper rejects the blank slug); AC5 said the assertion no-ops when `findProjectConfig` returns no `repo`. Naively routing the helper-`false` straight into the failure branch would trip AC5's exact opposite. The merged design split the responsibility: the helper's blank-rejecting `false` stays (defence-in-depth at unit-test layer); the call site precedes the helper with `if (projectRepo && !prUrlBelongsToRepo(...))` for the gate and `wrongRepo = !!(projectRepo && !prUrlBelongsToRepo(...))` for the early catch. Both AC5 assertions (advance-with-no-config and promote-with-no-config) pass.

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" API-composition discipline — knowing that a helper's degenerate-input return value can be semantically opposite to a call site's skip semantics is general type-design literacy. Captured here rather than promoted because the failure mode is recognition-shaped (the coder must see the inversion when they draft both the helper API and the call-site guard), and reviewer-as-catch-net at plan-merge time works once "false-from-helper and skip-the-check are opposite at the call site" is a named probe; the textbook entry preserves the call-site-precedes-helper precedent for future skip-when-absent ACs.

### For an "X verified then Y" gate, flip the success condition instead of inserting a post-success failure

Description: When a gate emits a success event and returns "advance" on a positive verification, and a new check is added that should turn some "verified" cases into failures, the wrong shape is to insert a post-success branch that emits the success event *and then* fails — polluting the event log with a `verified` record for a transaction that immediately fails. The right shape is to flip the success condition itself: compute the new-check result first (`wrongX = …`), gate the success return on the conjunction (`checkSuccess(v) && !wrongX`), then run the failure branch for the wrong-X case. Same control flow, same set of code paths reached, no spurious success event before the failure. The reviewer-side heuristic: any time a new failure branch lands *after* a `return "advance"` / `emit verified` line, ask "does the success-side artefact (event, log, metric) fire for cases this new branch fails?" If yes, the gate's success condition has not actually been flipped — only delayed.

Precipitating retro: `gh-ludics-529` round 1 (coder workflow-feedback, 2026-05-19, PR #543). The first sketch of the wrong-base-repo gate added the assertion *after* the existing `if (checkSuccess(v)) { emit pr_verified; return "advance" }` — meaning a wrong-repo PR would emit `pr_verified` then immediately fail the gate. The final shape has `verifyPhaseOutcome` compute `wrongRepo` once, gate the success return on `checkSuccess(v) && !wrongRepo`, then run the wrong-repo `handleVerifyFailure` branch. No spurious `pr_verified` event log pollution; the success event fires iff the gate genuinely advances.

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" event-log integrity discipline — knowing that "emit success then fail" pollutes audit trails is general transactional-design literacy. Captured here rather than promoted because the failure mode is recognition-shaped (the coder must see when their new branch lands downstream of a success event vs. upstream of a success condition) and the reviewer-as-catch-net works once "does the success-side artefact fire for cases this branch fails?" is a named probe; the textbook entry preserves the flip-the-condition precedent for future gate-extension PRs.

### "Any path other than X" ACs verify by allowlist filter, not set equality

Description: When an AC's falsifier reads "no path other than {A, B, C}" or "the diff contains nothing outside {…}", the verification is a universal-negative quantification over an allowlist — *not* an existence claim that all three named paths appear. A literal set-equality probe (`git diff --name-only main...HEAD` returns exactly `{A, B, C}`) over-requires: when one of the allowlist members is legitimately absent (the proposal commit already sits on `main` at fork time, an optional artefact was not touched this round, a doc clause did not need a paired test, …), the diff is a *strict subset* of the allowlist and the set-equality probe spuriously fails on a correct implementation. The honest verification filters the actual list *against* the allowlist with `grep -vxE`, asserting the leftover count is zero: `git diff --name-only main...HEAD | grep -vxE '<allowlist-regex>' | wc -l → 0`. This survives any subset of the allowlist being present, regardless of why a member is absent. Generalises to any AC verb of the form "no X other than {…}", "the only ones are {…}", "must not include any … not in {…}".

Precipitating retro: `gh-ludics-534` round 0 plan-review (reviewer caught at plan-merge time, 2026-05-19, PR #542). The merged plan turned AC7's allowlist falsifier into `git diff --name-only main...HEAD returns exactly [docs/ac-rigor-reference.md, docs/ac-rigor-reference.shape.test.ts, docs/proposals/gh-ludics-534-…]`. The proposal commit (`af19d89`) was already on `origin/main` at fork time (HEAD == main), so the post-commit diff was `{docs/ac-rigor-reference.md, docs/ac-rigor-reference.shape.test.ts}` only — the exact-set check would have spuriously failed on a correct implementation. Reviewer remediation cited `git log --oneline --decorate -5` evidence and changed the validation to an allowlist filter, matching the proposal's literal "any path other than" wording. Companion to the pre-existing `feedback_proposal_in_diff_ac_stale_when_proposal_on_main` memory, which covered the proposal-path-specific case; this entry generalises to *any* "no X other than" verb.

Filter decision: Under the competent-SWE filter this is a doctrinal-subtlety pattern — the competent SWE could miss the verb-vs-set-equality distinction because the proposal's literal AC list reads like an enumeration, and translating it into a check defaults to set-equality unless the universal-negative quantifier is read precisely. Captured here rather than promoted to `docs/ac-rigor-reference.md` because the failure mode is recognition-shaped (the coder must see when a proposal's AC verb is a quantifier over an allowlist) and the reviewer-as-catch-net works once "filter, don't compare set-equality" is a named probe; the textbook entry preserves the allowlist-filter idiom (`grep -vxE`) and the proposal-on-main subset case as the worked example for future "no X other than" AC verifications.

### AC payload-field ACs need structured-key capture, not message-substring assertions

Description: When an AC names "the divergence count goes in the event payload" / "the structured field X is emitted" / "the side effect carries `{field: value}` to the sink," asserting only on the formatted message that happens to contain the value's text is a vacuous test: a regression that drops the structured field but keeps the rendered message still passes. The honest harness captures the full event object (or full record, full notification payload, …) and asserts on the structured key directly — and ideally adds a second adapter-boundary assertion that reads the *persisted* sink (the journal line, the database row, the wire-format JSON) so a regression that drops the field at the adapter forwarder is also caught. The mutation a reviewer can name: "what if the code keeps the human-readable message but drops the structured field?" If only `{type}` or `{message}` is captured, the test cannot distinguish.

Precipitating retro: `gh-ludics-540` round 1 review (coder workflow-feedback, 2026-05-19, PR #544). AC4 required `skipped-not-fast-forward` to emit the divergence count "in the event payload." The first round captured only `{type}` from the emitted event and asserted on the formatted message (`expect(message).toContain("3 commits")`); a regression that dropped `extra: { divergedBy }` from the emit but kept the message would have passed. Round 2 captured the full event object and asserted `extra.divergedBy === 3` AND `extra.aheadBy === 5`, then added a sibling end-to-end test that drove the Mag wrapper, read the persisted `journal/events.jsonl` line, and asserted those structured fields survived the adapter forwarder's `...(ev.extra ?? {})` spread. Two cited mutation tests now exist: dropping `extra` from the core emit fails the unit test; replacing the spread with `{}` in the adapter fails the end-to-end test.

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" test-completeness discipline — knowing that a structured-field AC needs a structured-key assertion is general event-test literacy. Captured here rather than promoted to always-loaded prompts because the failure mode is recognition-shaped (the coder must see when "carries X in the payload" is the AC and reach for a full-event capture, not a message-substring assertion), and the reviewer-as-catch-net works once "capture the structured key, not the rendered message" is a named probe. Pairs with the "'Does NOT do Y' invariants need observation at Y's persistent surface" entry above (same theme — assert at the right surface) and with the "Tmpdir + env override for end-to-end adapter-boundary tests" entry below (the persistence-side dual: pin the structured field at the journal/db, not just at the core callback).

### Tmpdir + env override for end-to-end adapter-boundary tests

Description: When a unit test that calls the core function in-process and observes its callback / return value is structurally too weak for an AC that names an adapter-side effect (a record written to disk, a value forwarded through a wrapper, a field spread through a `...payload` adapter), the next-best test shape is to drive the *production wrapper* end-to-end via a tmpdir + env-var override harness: (a) `mkdtempSync` a private tmpdir; (b) record the previous value of the relevant env var (e.g. `LUDICS_HARNESS_DIR`, `XDG_CONFIG_HOME`, `RUNNER_TEMP`); (c) set the env var to the tmpdir for the duration of the test; (d) drive the production entry point with a fake `RunGit` / fake adapter that exercises the path under test; (e) read the persisted artifact from the tmpdir (`journal/events.jsonl`, `mag/last-X.epoch`, `db.sqlite`) and assert the structured field is present; (f) restore the env var in `try / finally`. This exercises the same code path production uses — the wrapper's adapter forwarder, the file/db writer, the JSON serialization — without spying on internals or refactoring imports to enable namespace mocking. The pattern is the canonical recourse when a unit test cannot reach the adapter boundary without a refactor.

Precipitating retro: `gh-ludics-540` round 2 (coder workflow-feedback, 2026-05-19, PR #544). The reviewer's AC4 blocker required proving the divergence count survived the Mag wrapper's `...(ev.extra ?? {})` adapter spread to the on-disk `journal/events.jsonl`. A pure unit test on the core's emit callback could not exercise the wrapper's spread without spyOn refactors (the namespace-import shape blocked module-level mocking). The fix was a one-test end-to-end harness: `mkdtempSync` + override `LUDICS_HARNESS_DIR`, drive `runStagingOutboundPushTick` with a custom `RunGit` that returns the divergence-path stdout/exitCode pairs, then `readFileSync(join(tmpdir, "journal/events.jsonl"))` and assert `divergedBy: 3` and `aheadBy: 5` appear in the parsed JSON line. The setup cost is small (≈10 lines per test); the mutation evidence is strong (replacing the adapter's spread with `{}` fails the test).

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" integration-test discipline — knowing that an env-var override + tmpdir gives you a real adapter-boundary harness is general test-architecture literacy. Captured here rather than promoted to `docs/testing-patterns.md` because the pattern is most useful as a *next-step* when a unit test is too weak (the recognition signal: "the AC names a persistence surface and the unit test is observing the in-process callback"), and that recognition is most usefully named as a reviewer probe rather than a per-test rule. Pairs with the "AC payload-field ACs need structured-key capture, not message-substring assertions" entry above (the in-process dual) and with the "Failure-path tamper-and-restore harness pattern for CLI exit-code ACs" entry — both are hermetic-test patterns at different surfaces; tamper-and-restore pins file-state via CLI spawn, this pattern pins file-state via in-process production wrapper + env override.

### Negative-control argv assertions pin unsupported tool flags against future regressions

Description: When an AC's implementation works around an unsupported or rejected tool flag (a CLI option the local tool version doesn't accept, a remote API parameter the upstream rejects, a deprecated config knob), the positive test that asserts the *correct* argv is insufficient on its own — a future maintainer reading the proposal or AC and "fixing" by re-adding the flag would pass the positive assertion (the correct argv is still emitted alongside the spurious extra one, or the order changes and the positive matcher is loose). The honest harness pairs the positive `.toEqual(["push", "upstream", "origin/X:Y"])` exact-argv assertion with explicit negative-controls: `expect(pushCall).not.toContain("--ff-only")`, `expect(pushCall).not.toContain("--force")`, `expect(pushCall).not.toContain("--force-with-lease")`, `expect(pushCall.some(arg => arg.startsWith("+"))).toBe(false)`. The mutation a reviewer can name: "what if a future maintainer re-adds the flag this AC documented as unsupported?" If no negative-control would fail, the flag's absence is not enforced — only its absence-from-the-named-argv-shape is.

Precipitating retro: `gh-ludics-540` round 1 → round 2 (coder workflow-feedback, 2026-05-19, PR #544). The original proposal AC said "push runs with `--ff-only`"; the reviewer caught at plan-review round 1 that `git push --ff-only` is not a valid Git command option in the local tool version (git 2.50.1). The merged plan recorded this as an `ASSUMPTION GAP` and replaced the argv with `["push", "upstream", "origin/<o>:<u>"]` (non-forced; ff-eligibility enforced by `merge-base --is-ancestor` pre-check + server-side non-ff rejection). The implementation pins both the positive `expect(pushCall).toEqual(["push", "upstream", "origin/master:master"])` AND four explicit negative-controls (`not.toContain` for `--ff-only`, `--force`, `--force-with-lease`, and `arg.startsWith("+")` for the force-prefixed refspec). A future maintainer "fixing" by re-adding any of those flags trips a named negative-control assertion.

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" test-completeness discipline — knowing that the absence of a flag must be asserted as well as the presence of the correct argv is general regression-resistance literacy. Captured here rather than promoted to always-loaded prompts because the recognition signal is narrow (a documented assumption gap or unsupported-flag workaround) and most usefully named as a reviewer probe ("does the test pin the flag's *absence*, not just the correct argv's presence?"), and the negative-control idiom is publication-friendly as a reusable shape. Pairs with the "Symmetric-OR ACs need each arm's own dedicated harness, and no implementation short-circuit" entry above (both are about pinning what *must not* happen, not just what does).

### AC verification lines must cite the test enforcing the contested invariant, not a positive sibling

Description: When a coder's AC-verification doc cites a test as evidence for an AC, the citation must point at the test enforcing the AC's *contested* invariant — typically the negative arm of a partition ("non-X does NOT do Y") — not a positive sibling that merely traverses the same code path. A reviewer reads the cited test, finds it asserts only the positive case the AC's disputed clause does not depend on, and rejects — even when the correct negative test exists elsewhere in the same file. The miscitation, not a missing test, costs the round. The discipline: before writing "AC N verified by test T", restate the AC's load-bearing clause (the one a reviewer would dispute) and confirm T's assertions falsify a mutation of *that* clause, not an adjacent one.

Precipitating retro: `gh-ludics-538` round 3 (coder workflow-feedback, 2026-05-19, PR #545). AC 6's contested invariant was the negative direction ("a Mag-authored task commit does NOT advance the user-action signal"); the round-3 verification line cited the positive source-3 test ("non-Mag commit advances the signal"). ### Pre-existing red CI in files a PR already edits is in-scope to absorb

### A guard added to a shared validator reaches every transitive caller and every write path to the gated field

### An ordering test whose fixtures already sit in sorted order passes the "remove the sort" mutation vacuously

Description: A regression test for "the output is deterministically ordered by key K" is only non-vacuous when the fixture set, in its *unsorted* order, differs from the expected sorted order. If the fixture ids are alphabetically (or insertion-order) correlated with K, then on any filesystem whose `readdirSync` returns alphabetical order — or any data source whose natural order already matches K — the mutation "remove the production sort" still produces the expected order, so the assertion never flips and the test certifies nothing. This is distinct from "Run mutation tests before writing the AC verification line that claims them": even a *correctly run* mutation passes vacuously here if the fixtures are coincidentally pre-sorted — the flaw is in fixture construction, not in whether the mutation was executed.

### Moving a field across variant arms leaves silent readers the type checker cannot flag

Description: When a refactor moves a field out of one arm of a sum type and onto the parent record (or vice-versa), the type checker enumerates every *constructor* site and every *destructuring* pattern-match: those will fail to compile until updated, and the planner can lean on the compiler to find them. What the type checker does *not* catch is the population of sites that read the field through its old path on the parent — e.g., code that read `row.dims` directly, when `dims` semantically split into `beg_dims` (newly promoted) and `dims` (residual). Each such reader silently keeps its old meaning, which is now wrong: it sees fewer (or more) axes than it did before, and a `length`/`fold`/`iter` over it silently produces a different answer. The planning move: before claiming the refactor is "mechanical" because constructors will compile-error, enumerate the field's *readers* with an exhaustive `rg -F ".old_field_name"` over the codebase and triage each hit's intended semantics against the new split. The list belongs in the merged plan as a named disposition table (one row per reader, with `KEEP / REPLACE / SPLIT / DROP` and a one-line rationale). Generalises to: promoting a flag from a variant arm onto its parent record, splitting a single field into two, merging two fields into one, moving a method up or down a class hierarchy — any motion where the language's type system can see the *write* sites but not the *read* sites of a structural field.

Precipitating retro: `task-71e28eb1` round 1 (coder feedback, 2026-05-28). Refactor moved `beg_dims` out of `Row_var { v; beg_dims }` onto `Row.t`. Constructors and destructuring pattern-matches all compile-errored cleanly, but ~12 reader sites in `tensor/shape.ml` (`fetch_padding`, `dims_of`, `compute_row_product`, `axis_keys_to_idcs`, `to_string_hum`, `num_input_axes`, padding default length, `padding_of_row`, `indices_of_sh`, two `make_*` helpers) had to be visited and re-triaged for the new semantic split between `beg_dims` and `dims`. The coder's own note: *"The OCaml type checker catches all constructor sites but none of the silent readers; an exhaustive `.dims` grep is required and must be enumerated in the plan."*

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" refactor discipline — knowing that a structural-field motion has a write side and a read side, and that compilers traditionally hard-flag one while the other slides through, is general type-system literacy. Captured here rather than promoted to always-loaded prompts because the failure mode is recognition-shaped (the cue is "I am moving a field across a structural boundary in a typed language") and the recovery — an exhaustive grep of the old reader literal plus a disposition table — is a planning-time discipline most useful at proposal/merged-plan time, not at every coder turn. Pairs with the `[@@deriving sexp]` entry above (sexp-derived field-name leak is a *different* hidden-consumer class on the same code shape: derived serializers print field names, so a *rename* leaks where a *motion* doesn't — but both share the lesson that the type checker is not the whole audit).

### A lookup that falls back to a throwing loader can throw — wrap it best-effort on must-not-throw paths

Description: A helper whose body is `arg ?? loadThing()` (take the caller-supplied value, else load it) inherits the *throw behaviour* of the fallback. When `loadThing()` throws on absence — e.g. `loadConfigSync()` throws `config not found: …` when no config file exists — the lookup is **not** the side-effect-free, returns-null-on-miss function its name suggests; it propagates. Adding such a lookup to a code path that must stay independent of that resource (here: `createWorktrees`, also reached by ad-hoc/local-only worktree creation and CI runs with no config file) silently converts "resource absent" from a benign no-op into a hard failure of the whole path. The discipline: before calling a `find*/get*/resolve*` helper on a path that must not throw, check whether its miss-branch *returns* a sentinel or *throws*; if it can throw, wrap it `try { … } catch { null }` and gate only the resource-dependent step on the result — never let the lookup's failure abort the resource-independent work. Mutation-test the wrap by pointing the resource at a missing path and asserting the host operation still completes. Generalises to any "convenience lookup" layered over a strict loader: config readers, plugin/registry resolvers, credential fetchers, schema loaders — the name promises a lookup, the body delivers a load.

Precipitating retro: `task-2c296dc0` round 1 (reviewer caught as a blocking plan gap, 2026-05-30, PR #555). The layer-2 gh-resolved defense added a `findProjectConfig(projectDir)` call inside `createWorktrees` to decide whether to provision an `upstream` remote. `findProjectConfig` does `config ?? loadConfigSync()`, and `loadConfigSync()` throws when no config file is present — so the new call would have thrown on every ad-hoc/no-config worktree creation. The reviewer flagged it at plan-merge; the fix wraps the lookup best-effort and gates only the `upstream_repo` provisioning on a non-null result, with a regression test that points `LUDICS_CONFIG` at a missing path and asserts `createWorktrees` neither throws nor skips the (config-independent) origin seed.

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" dependency literacy — a competent engineer checks whether a helper's miss-branch returns or throws before adding it to a must-not-throw path. Captured here rather than promoted to always-loaded prompts because the cue is recognition-shaped ("I am adding a `find*`/`get*` lookup to a path that runs without the resource it loads") and the review catch-net already works (the reviewer caught it as a plan-merge blocker). The trap is the *name*: `findProjectConfig` reads as a total, null-returning lookup, so the throwing fallback is invisible until the config-less path runs. Coder self-probe before adding any such call: "what does this return when the thing is absent — null, or an exception?"

### When a change is positional, the assertion must be positional — "the value appears somewhere" passes a wrong-position bug

Description: When a change attaches data to a *specific slot* in an ordered structure — a basis tag on a particular axis, a flag on row N of a table, an attribute on the third column — a test that asserts the value merely *exists somewhere* in a flattened view (`Array.mem bases "rgb"`, `grep -c`, `Set.contains`) is vacuous against the failure that matters: the value landing on the *wrong* slot. The flattened existence check passes whether the label is on the output axis (correct) or leaked onto the input axis (bug), because both put `"rgb"` *somewhere* in the list. The honest assertion mirrors the structure the change is positional in: assert the exact per-slot sequence (`Array.equal (to_bases_bio …).output [|"rgb"|]` and `.input [|"features"; …|]`), and include a case where two slots carry labels so a swap is detectable. General rule: identify the dimension the change is positional along (which axis / which row / which column), and make the assertion key on that dimension — never on a projection that collapses it. Distinct from the per-row *coverage* pattern (a disjunctive AC needs every row checked, not every type): this is per-slot *position*, where the trap is right-value-wrong-place, not missing-value.

Precipitating retro: `task-4eb929b2` round 2 → round 3 (coder feedback, 2026-05-30, PR ocannl-staging#26). The round-2 tensor-literal axis-label test used `Shape.to_bases` (flattened) + `Array.mem`, which a label placed on the wrong row still passes. The reviewer REQUEST_CHANGES'd; round 3 added `Shape.to_bases_bio` (per batch/input/output kind) and asserted the exact per-row sequence — including a two-output-axes case with the label on the outer axis — so a wrong-row or wrong-position label now fails `Array.equal` on that row. Pairs with the "Union-type evidence ACs need per-row anchor coverage" entry above (coverage), of which this is the positional sibling.

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" test-craft — a competent engineer knows an existence check can't pin position. Captured here rather than promoted to always-loaded prompts because it is recognition-shaped (the cue is "my change targets a specific slot in an ordered structure") and the review catch-net already works (caught as an R2 blocker). Most usefully named as a coder self-probe before claiming a positional AC with a membership test: "would this assertion still pass if the value were attached to the adjacent slot?"

### A semantic accessor can be a hidden *display* consumer — keep the API faithful, blank reserved values at the display layer

Description: When you make a semantic accessor return the *real* underlying value where it previously returned a sanitized/empty one (e.g. `row_to_bases` now returns the actual `default` / `bcast_if_1` reserved tags instead of blanks), every *display* surface that renders the accessor's output inherits the change — a tensor's PrintBox dag, a debug dump, a tree view suddenly shows `default=`/`bcast_if_1=` on every node. The instinct is to make the accessor return blanks for reserved values so the display looks clean — but that re-weakens the API for every *semantic* consumer (tests, solver, serialization) to serve presentation. The fix is to split the concern: keep the accessor faithful (it returns the true tag, which the semantic consumers need) and suppress reserved/noise values at the *display* layer (`to_dag`, the size-style printer) where presentation actually lives. General rule: when an API change floods a rendered surface, ask whether the consumer is *semantic* or *display* before adjusting the source — push presentation filtering down to the presentation layer, never up into the shared accessor. Generalises to: a `toString`/`Display`/`Show` that started echoing a new field, a serializer feeding both a wire format and a console, any "make it return the real thing" change whose blast radius is mostly pixels.

Precipitating retro: `task-4eb929b2` round 1 (coder feedback, 2026-05-30, PR ocannl-staging#26). Making `row_to_bases` proposal-faithful (return the reserved tag) flooded every tensor's PrintBox dag with `default=`/`bcast_if_1=`. Resolution kept the API returning the true tag and blanked reserved tags at the display layer (`to_dag`, size-style printing), so semantic consumers stayed correct while the rendered output stayed clean. Same hidden-consumer family as the `[@@deriving sexp]` entry above, but the consumer is a display renderer, not a serializer, and the fix is layer-splitting rather than a grep-the-`.expected` audit.

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" separation-of-concerns — a competent engineer keeps presentation out of a semantic API. Captured here rather than promoted to always-loaded prompts because the failure is recognition-shaped (the cue is "I made an accessor return the real value and now a rendered surface is noisy") and low-frequency. ### Don't `git stash` around a hang-prone command in an automated round — a hang strands the stash; and a cached `runtest` green isn't proof

Description: Two iteration hazards that bite inside an orchestrated coding round, where work is uncommitted between auto-commits. (1) Wrapping a baseline check as `git stash push; <run>; git stash pop` is unsafe when `<run>` can hang or deadlock: if it never returns, the trailing `git stash pop` never executes and *all* uncommitted work sits stranded in the stash (recoverable by hand, but invisible and alarming mid-round). Single-file `git stash push -- <impl-file>` for a quick mutation test is fine *because it returns fast*; the anti-pattern is stashing around a command whose termination you don't control. For baseline comparisons, use a separate `git worktree` (the working tree stays put, nothing to pop) instead of stash. (2) An incremental test runner's exit 0 can be a *cache artifact*: `dune runtest` (and bazel, and similar) may report green from a prior build without re-running the test under the current tree, hiding a crash that only surfaces once a source edit forces a rebuild. Don't treat a cached green as proof a specific test passed now — force the relevant target (touch/`--force`, or run the narrowed target directly) before claiming it.

Precipitating retro: `task-4eb929b2` (coder feedback, 2026-05-30, PR ocannl-staging#26). A backgrounded baseline check did `git stash; dune exec test/training/…; git stash pop`; the `dune exec` of a training test hung on a lock/backend interaction, so the `pop` never ran and ~15 min of work sat stranded in the stash (recovered manually, no loss). Separately, a round-1 `dune runtest` exit 0 hid a training-test crash that only appeared once a later source change forced a rebuild+rerun. Lessons: iterate with `dune runtest <target>` (fails fast, releases the lock), check baselines via `git worktree` not `stash`, and never `dune exec` a training test in this repo. Refines the `git stash push --` mutation-test precedent elsewhere in this file: stash is fine for a fast single-file swap, dangerous around an unbounded command.

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" tooling hygiene — a competent engineer knows a non-returning command breaks a stash/pop bracket and that incremental builders cache results. Captured here rather than promoted to always-loaded prompts because it is environment-flavoured (dune + orchestrated rounds) and recognition-shaped: the cue is "I'm about to stash my whole tree around a command I don't control the runtime of." Self-probe before bracketing work in a stash: "if this command never returns, where is my uncommitted work?"

### A per-test temp-dir helper that overwrites one shared path leaks every call past the first

Description: A test helper like `const makeDir = () => (dir = mkdtempSync(...))` that assigns into a single shared variable, paired with an `afterEach` that cleans only that latest variable (`rmSync(dir)`), silently leaks whenever a single test calls the helper more than once — each call overwrites the handle to the previous dir, so `afterEach` reaps only the last one and the earlier `/tmp/<prefix>-*` dirs accumulate across runs. The bug is invisible in the passing test (it's green either way) and only shows up as growing `/tmp` cruft. The fix is the array-accumulate pattern: push every created path into a `dirs: string[] = []`, and in `afterEach` `rmSync` each then `dirs.splice(0)` — the same shape already used for tracked `servers`/sockets in the same files. General rule: any per-test factory that mints a disposable resource (temp dir, temp file, server, socket, child process) must accumulate *all* instances into a collection and tear the whole set down; a single shared handle is correct only if the contract is "exactly one per test", and that contract is exactly what a boundary/parametrized test breaks when it calls the factory in a loop or twice for a before/after comparison.

Precipitating retro: `task-7c3ec5c9` round 2 (Codex PR comment P3, 2026-05-30, PR #556). The boundary test in `src/dashboard-server.test.ts` called `makeDir()` once per `startDashboardServer` invocation but `afterEach` removed only the most-recently-assigned `dir`, leaking the earlier `/tmp/ludics-dashsrv-test-*` dir on every successful run (plus stale round-1 leftovers). Fixed in commit `86d42ea` by tracking all created dirs in a `dirs[]` array and `rmSync`-ing each in `afterEach`, mirroring the existing `servers` cleanup; verified tmp-dir count equal before/after.

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" test-fixture hygiene — a competent engineer knows a shared mutable handle can't track multiple resources. Captured here rather than promoted to always-loaded prompts because it is recognition-shaped (the cue is "my test calls the same make-temp helper more than once") and the review catch-net already works (caught as a P3 PR comment, not even a merge blocker). Self-probe before reusing a `makeX`/`mkTmp` helper inside a test: "does this test call the factory more than once, and does my teardown clean every instance or just the last?"

### An AC that names two output surfaces where only one has a programmatic seam: wire that one, document the other with the proposal's authorization

Description: When an acceptance criterion names two places a value must appear — say a rich diagnostic must surface in both surface A and surface B — and on inspection only one of them has a programmatic hook (a function, a precompute, a data boundary you can attach to), while the other is assembled inline in a place the proposal forbids you to edit (a prose template, a generated artifact, a hand-written script the AC says to leave alone), do not force a resolution by either fabricating a hook the codebase doesn't have or quietly expanding scope to build new plumbing the proposal didn't ask for. ### A relabel's completeness check is a repo-wide negative grep minus an allowlist, not a positive sweep of the planned files

Description: When a change relabels a vocabulary across a codebase — a rename, a terminology flip, an order reversal — the question "did I get all of it?" is not answered by greping the files you planned to touch and finding them clean. "Clean over the swept files" is not "no stale vocabulary remains": the stale term hides in files outside the plan (a `.mli` interface, an `AGENTS.md`, a paper `.tex`, a constructor name in a module you didn't list). The reliable completeness check inverts the method: run the term-list grep **repo-wide**, then **subtract an explicit allowlist** of known-OK hits, and require the remainder to be empty. Three refinements the naive grep misses: (a) make it **case-insensitive** — the term appears capitalized in prose and in type constructors (`Cur`/`Subr`, `Least Upper Bounds`), not just lowercased in code; (b) make it **plural- and morphology-aware** (`LUBs?`, not `LUB`) — the plural form slips a `\bLUB\b` anchor; (c) the allowlist is not just false-positive substrings (`cur_sh`, `occur`) but also **intentionally-correct-post-change strings**: under a structural transform like an order reversal, a surface phrase can read like stale vocab yet be genuinely correct in its new referent (after reversing the lattice, "any two dims have a least upper bound" is a true statement about the join-semilattice's joins, distinct from the maintained solver bound that is now the GLB). Distinguishing "stale" from "intentional dual" is part of building the allowlist, and is a judgment call the bare grep cannot make. A companion scope rule: **exclude historical-record files** from the sweep — changelogs (`CHANGES.md`), decision logs, and superseded proposals legitimately preserve the old vocabulary because they describe what was true at a past version; rewriting them to the new terms falsifies the record. Current guidance and exposition (`AGENTS.md`, `docs/*.md`, `*.tex`) get reoriented; historical records do not.

Precipitating retro: `task-3170a13a` (PR ocannl-staging#27, 2026-06-05) — the broadcast-order reversal (LUB→GLB, top↔bottom). The coder's round-1 checklist (`rg '\bLUB\b|least upper|\bcur\b|\bsubr\b'`, case-sensitive, over the planned files) reported clean but silently missed `Least Upper Bounds (LUBs)` in `shape.mli`, the capitalized `Cur`/`Subr` constructors in `row.ml`, and `LUB` in `AGENTS.md`. The round-2 fix re-ran `rg -in 'broadcast.{0,4}bottom|\bLUBs?\b|\blub\b|least upper bound|\b[Ss]ubr\b|\b[Cc]ur\b|…'` repo-wide minus an allowlist (`cur_sh`/`current`/`occur*`, the intentional join-semilattice duals, traversal `bottom-up`), excluding `docs/proposals/*` and `CHANGES.md` as historical records, and required zero remaining hits.

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" sweep thoroughness — a competent engineer knows a grep can be too narrow. Captured here rather than promoted to always-loaded prompts because the failure mode is recognition-shaped and method-specific (the inversion to negative-grep-minus-allowlist, the case/plural sensitivity, the intentional-dual allowlist, the historical-record exclusion) and pairs with the existing "Config-key removal sweep covers all of `templates/`" and "a guard added to a shared validator reaches every transitive caller" entries — all three are "the sweep is wider than first enumerated", this one specialised for vocabulary relabels under a structural transform.

### For a behavior-preserving relabel, a label-printing golden test that stays all-PASS is the direct decision-set-unchanged gate

Description: When a change is supposed to preserve behavior while renaming things (a pure relabel, an order-reversal, a terminology flip), the cheapest and most direct proof that no decision actually moved is an existing **golden/`%expect`/cram test that prints the system's own accept/reject (or classify, or dispatch) labels** for a battery of cases. If that test's expected output stays byte-identical except for the deliberately-changed wording — every case still reads `PASS`, or the same branch label — then the accept/reject *set* is provably unchanged, because a flipped comparison or reversed branch would move at least one case across the boundary and show up as a `PASS→FAIL` (or relabeled-decision) diff. This is stronger and cheaper than re-deriving invariance from the diff of the production code: you don't have to argue that no `<=` became `>=`; the golden test would have caught it. The discipline at relabel time: identify the test that enumerates the decision surface in printed form, freeze it, and treat *any* non-wording diff in it as the stop-and-flag signal that the relabel changed behavior. If no such test exists, writing one that prints the labels for the boundary cases is the highest-leverage safety net before starting the rename.

Precipitating retro: `task-3170a13a` (PR ocannl-staging#27, 2026-06-05). The only `.expected` diffs were wording/glyph-order promotes.

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" test-strategy literacy — using a golden test as a behavior-invariance gate is general regression-testing sense. Captured here rather than promoted to always-loaded prompts because it is recognition-shaped (the cue is "I'm doing a behavior-preserving relabel — which existing test prints the decisions I must not move?") and complements the always-loaded post-edit-grep discipline with a test-side gate; pairs with the vacuous-assertion entries (a label-printing golden test is the *non-vacuous* counterpart — it fails under exactly the mutation a relabel risks).

### External-CLI stderr varies by host state — a CI-green benign-error matcher can re-fail in production

### A config-gated early-return makes the test exercise nothing unless the gating config is set

Description: When a function under test bails out early under a default configuration — an autonomy gate, a feature flag, a "manual mode" short-circuit that returns before doing any of the work the test means to assert — a test that drives the function with the default config passes vacuously: the early-return fires, no work is attempted, and every downstream assertion that says "nothing was enqueued / nothing changed" holds for the wrong reason. The bug the test is meant to catch lives past the gate, but the test never reaches it. The discipline is to set up the harness config so the gate is *open* (e.g. flip the autonomy level from its default `manual` to `auto`, enable the flag) before exercising the path, and to pair the assertion with a positive control proving the code actually runs under that config — otherwise "the dedup blocked a second enqueue" is indistinguishable from "the function returned before trying to enqueue at all." Relatedly, when an AC says the behaviour must hold "from the real entry points," drive those entry points (the CLI dispatch, the keepalive tick) rather than only the shared predicate they call — exercising the predicate in isolation skips the gate-and-wiring that the entry-point path imposes, so a regression at a call site goes uncaught.

A recurring competent-SWE test-design lesson (a config-default early-return is a vacuous-pass hazard; exercise the real entry points with the gate open) that is real but recognition-shaped and too general for always-loaded prompt doctrine. ### Never run a repo-wide auto-formatter as a finishing step when the tree is not formatter-clean

Description: A reflexive "run the formatter before committing" finishing step is actively destructive in a repository whose main branch is not itself formatter-clean and whose CI does not enforce formatting. The formatter does not limit itself to the files you touched — it rewrites every file it considers ill-formatted, sweeping dozens of unrelated files into your diff in one pass and burying the actual change. The discipline: before running any whole-tree formatter, check whether the repo's own baseline is clean and whether CI gates on it; if either answer is no, match the surrounding (or seed-branch) style by hand on the lines you edit and leave the rest alone. Recovery if a sweep already ran but your real work is committed: discard only the working-tree sweep (`git restore .`), which leaves the commits intact. Generalises to any auto-fixer with whole-repo reach — `gofmt`/`goimports -w ./...`, `black .`, `prettier --write .`, `cargo fmt`, `rubocop -A` — in a codebase that tolerates pre-existing non-conformance.

Precipitating retro: task-c088bda1 (coder workflow-feedback, 2026-06-08, PR ocannl-staging tensor-stacking). Running `dune fmt` as a finishing step rewrote ~25 unrelated files because master is not ocamlformat-clean (e.g. `ppx_op.ml`'s existing `Pexp_constraint` arm, `operation.ml`'s `number_int` re-flow) and CI does not enforce format. Recovered with `git restore .` (the three real commits were safe); the lesson was to hand-match the seed/surrounding style instead.

Filter decision: capture-textbook. A genuine recurring lesson (whole-tree auto-formatter in a non-formatter-clean repo destroys diffs) but project-and-tooling-specific build hygiene that a competent engineer learns once per repo; promoting it to always-loaded prompts would tax every round for a narrow per-repo fact. Best preserved as a findable precedent for the next coder on a repo whose main branch tolerates formatter drift.

### Re-baseline a seed branch's golden files against current master, not the seed's own snapshot

Description: When a task is seeded from an older branch (a salvaged PR, an abandoned worktree, a cherry-picked spike), the seed carries its own committed golden/`.expected` snapshots that were correct at the seed's merge-base — not necessarily against current main. Trusting those snapshots is a silent trap two ways: (a) a behaviour the seed exercised may have *regressed* on main since (so the seed's green `.expected` no longer reflects what the code now emits), and (b) a behaviour the seed *supported* may no longer exist on main (so a fixture case the seed included now fails or must be dropped). The discipline: for every behaviour the seed's fixtures cover, re-run it against current master and re-baseline the golden from the *actual current output* (`dune promote` / equivalent), case by case — never copy the seed's `.expected` forward unverified, and never assume a fixture case the seed had still passes. Distinct from the stale-build-cache hazard (a cached green can hide a crash that only surfaces on rebuild): this one is about *which tree the golden was frozen against*, not whether the test re-ran.

Precipitating retro: task-c088bda1 (coder workflow-feedback, 2026-06-08, PR ocannl-staging tensor-stacking). The seed branch (older merge-base) printed concat tensors inline fine *and* supported nested `[[a;b];[c;d]]` stacking; current master had regressed both (the inline printer now crashes on row-variable shapes; nested stacking fails in the shape solver). The coder re-ran every ported behaviour against current master, re-baselined `test_block_tensor.expected` from actual output, and dropped the seed's nested-matrix fixture case as a documented known-limitation rather than trusting the seed's green snapshot.

Filter decision: capture-textbook. A real recurring lesson when work is seeded from older branches (verify golden snapshots against current main, don't carry the seed's forward) but recognition-shaped and adjacent to general regression-testing hygiene; too situational to promote to always-loaded prompt doctrine. Pairs with the stale-build-cache / stranded-stash entry above as the "what the golden was frozen against" sibling to its "whether the test actually re-ran" hazard.

### A decision-only task's deliverable is the recorded decision and its follow-through, not a code diff

Description: Some tasks resolve a question or produce a document rather than changing code — choosing between design options, recording a verdict, aligning a tracker entry. When the work order is phrased as "implement this," it is tempting to read the absence of any code to write as a signal that the task is obsolete or already done, and to abandon it. That inverts the deliverable: the recorded decision and the follow-through it triggers — rewriting the affected documents to state the chosen option, re-elaborating dependent stubs against it, performing the agreed out-of-band actions, and recording the decision in the parent document — *are* the work. ### Key a latest-value guard off its resolver, not the seeded literal, or a config bump silently disables it

Description: When a guard, branch, or special-case recognises the "current latest" value of something that is actually sourced from a bumpable lookup table or config (e.g. "is this the newest model id?"), test it against the resolver or predicate that owns that table — not against the literal value that happened to be seeded at the time of writing. If the guard hardcodes the seeded literal, a later bump of the config value turns the guard into a silent no-op: the rest of the feature keeps working because it reads the resolved value, so nothing visibly breaks, and the dead guard surfaces only when someone notices the special behaviour stopped firing. That makes it among the hardest kinds of drift to catch — there is no error, no failing test unless one was written against the resolver, just a quietly disabled code path.

### `toBe(CONST)` is circular when the AC names a required substring inside that constant

Description: When an AC requires a specific literal token to live inside a value the SUT sources from a named constant (e.g. a remedy string that must contain `` `~/<repo>` ``), a positive-case assertion of the form `expect(result.remedy).toBe(REMEDY_CONST)` is circular: it proves the code returns the right constant but not that the constant satisfies the AC's substring requirement. A constant that is *wrong* (missing the required token) passes the equality just as well as a correct one — the assertion detects the constant's *absence*, never its *content*. The constant is acting as both the system-under-test and its own oracle. The fix is to pair equality with a content assertion against the AC's literal — `expect(result.remedy).toContain("~/<repo>")` — so a regression that edits the constant to drop the mandated token is caught. Generalises: whenever an AC names a substring or format that must appear inside a value the SUT reads from a constant, assert that substring directly, not only equality to the constant.

Precipitating retro: `task-cabf6402` round 1→2 (coder feedback, 2026-06-15, PR #567). AC3/AC5 required the new `blocked-worktree` remedy to name the blocked checkout as `` `~/<repo>` ``. Reviewer REQUEST_CHANGES; round 2 added `expect(result.remedy).toContain("~/<repo>")` alongside the equality check and updated the constant to include the placeholder.

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" test discipline — asserting the AC's named literal rather than equality-to-a-constant is general falsifiability hygiene, and the reviewer caught it cleanly in one round. Captured here rather than promoted to always-loaded prompts because it is recognition-shaped (the coder must see when equality-to-a-constant makes the constant its own oracle) and joins the vacuous-harness family (`Test the AC's load-bearing call site, not the leaf function whose argument is forwarded`, `Run mutation tests before writing the AC verification line that claims them`) as the constant-as-its-own-oracle specialisation — most useful as a precedent reviewers can name.

### `%expect` blocks that capture an exception backtrace bake in source file:line and re-promote on every edit

Description: A `ppx_expect` (`%expect`) or `.expected` golden test that captures a rendered **exception backtrace** embeds absolute `file:line` coordinates of the throwing module into the expected output. Any later edit to that module — even one unrelated to the test — shifts the line numbers and forces a fresh `dune promote`, so the golden churns on edits that changed no behaviour. `ppx_expect` itself warns that "backtraces are fragile." The recognition: a golden test whose expected text contains a backtrace is coupled to the *source layout* of the code under test, not just its observable behaviour — a hidden edit-amplifier. Mitigations: prefer asserting the exception's *message/shape* over its backtrace; scrub line numbers from captured backtraces before comparison; or, when a backtrace golden is unavoidable, budget a promote→runtest pass after any edit to the referenced module and don't read the churn as a real diff. Companion to the `.expected`-fixture-fragility entries below — same family (golden tests coupled to incidental source structure), different coupling (line coordinates vs derived-serialiser field order).

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" OCaml-test-fixture literacy — once named, an experienced engineer knows backtrace goldens are line-coupled. Captured here rather than promoted to always-loaded prompts because it is narrow (ppx_expect / `.expected` goldens that capture backtraces) and joins the existing OCaml-test-fixture-fragility family (`[@@deriving sexp] field renames ripple through .expected cram fixtures…`, the codegen-fixture entry) as a precedent for coders to recognise the edit-amplifier shape and budget promote passes, not as a per-turn rule.

### Parsing `ps -o command=` is lossy — anchor on a structural landmark, not whitespace splitting

Description: `ps -o command=` (and any "render the process's argv as a single string" output) flattens the argv vector by joining elements with spaces. The boundaries between argv elements are destroyed — a single argv element that itself contains whitespace is indistinguishable from two separate elements. So any code that recovers a specific argv token by whitespace-splitting the `ps` output is only correct as long as *every* token of interest is whitespace-free; the moment an upstream value that can contain spaces flows into argv (here, an unsanitized tmux session name derived from a custom agent name), the split silently truncates the token to its first word. The downstream symptom is subtle: a health-check matcher that compares "the `-t` target from `ps`" to an expected target reads only the first word, mismatches a whitespace-bearing target, and declares a healthy process wrong → restart-every-tick flap. The fix shape is to anchor on a *structural* landmark in the argv rather than on whitespace: the target was the **final** argv element, so match the slice after the last ` -t ` to the expected value, end-of-string anchored — this round-trips a whitespace-bearing token while still rejecting prefix matches. Tokens that are themselves guaranteed whitespace-free (a port number) can stay whitespace-split. Generalises: when parsing any flattened-argv / space-joined rendering, recover each field by its position relative to a fixed delimiter or the string ends, never by assuming fields are single words.

Precipitating retro: `task-1373e911` round 3 (codex PR review, 2026-06-16, PR https://github.com/lukstafi/ludics/pull/568). `ttydMatchesSession` (`src/adapters/tmux-adapter.ts`) whitespace-split the `ps -o command=` output to extract the `-t` target, but `slotSessionName` does not sanitize agent names, so a quoted custom agent name with a space yielded a target with spaces that `ps` flattened — the split truncated the target to its first word, so a healthy ttyd would be restarted on every health-check tick. Codex flagged it P2 inline. Fix (commit `6d648d8`): match the slice after the last ` -t ` to the expected target exactly (end-anchored), keeping prefix rejection and the whitespace-split port token; added a whitespace-target regression test, mutation-verified (reverting to the whitespace-split target match fails it).

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" output-parsing literacy — once named, an engineer knows that joining argv on spaces is not invertible by splitting on spaces. Captured here rather than promoted to always-loaded prompts because the failure mode is narrow (recovering a field from a flattened-argv rendering where an upstream value can contain whitespace) and most usefully named as a precedent: it is a distinct *parsing-robustness* trap, not part of the saturated AC-rigor/vacuous-falsifier family. Pairs with the backtrace-golden and `.expected`-fixture entries as a "lossy serialisation coupling" precedent for reviewers and coders to recognise.

### A deny-list AC must test every spelling of the banned thing and the still-accepted siblings

Description: When a feature forbids some inputs while leaving adjacent inputs legal — a prohibited-operator list, a reserved-keyword blacklist, a banned config combination — a test that exercises a single banned spelling guards only that one entry. Two coverage gaps recur. First, *spelling coverage*: if the same prohibition has both a symbol form and a word alias (an operator `/` and its alias `div`, `**` and `pow`), removing either one from the deny-list silently re-admits that spelling, and only a test that exercises *each* spelling independently catches it — one spelling passing proves nothing about the other. Second, the *acceptance side*: prohibiting X does not test that the legal sibling Y is still accepted; a regression that over-broadens the ban (rejecting Y too) passes every prohibition test because they all assert "X is rejected." The remedy is mechanical: enumerate one negative case per banned spelling and at least one positive case per legal neighbour, each with an assertion that flips under the corresponding one-entry mutation (drop a deny-list member, or widen the guard to reject a sibling). For compile-time prohibitions, a pp-expansion diff test pins the exact error node per spelling without the test file needing to compile; the legal sibling's evidence is the *absence* of an error node (e.g. the expansion still carries the normal construct, not `[%ocaml.error …]`).

Precipitating retro: `gh-ocannl-192` round 2 (coder feedback, 2026-06-16, ocannl-staging) — the `~logic:"@"` Compose prohibition shipped round-1 negative tests for `/` and `**` only; the reviewer required separate `div`/`pow` alias cases (a local removal of `"div"` from the deny-list would not have flipped the diff) plus a positive `add … ~logic:"@"` acceptance case (AC2 said non-banned ops stay accepted, but no test enforced it). Same shape independently in `gh-ocannl-281` round 2, where the reviewer blocked until each ordering/spelling neighbour got its own dedicated case rather than a code-structure citation.

Filter decision: Under the competent-SWE filter this is "obvious-to-experienced-engineer" test-completeness discipline — exercising both arms of a prohibition and every alias of a banned token is general logic-coverage hygiene that the reviewer caught cleanly in one REQUEST_CHANGES round. Captured here rather than promoted to always-loaded prompts because it sits in the saturated AC-asymmetry / vacuous-falsifier family (`### AC asymmetry — "X uses Y" hides "non-X does NOT use Y"`, `### "Any path other than X" ACs verify by allowlist filter`); the distinct refinement worth preserving is the *per-spelling* axis — alias and symbol forms of one banned concept are independent deny-list entries, so each needs its own falsifier.

### Compilation success is not runtime success for foreign code generation

Description: When a tool generates source for a foreign runtime it does not fully control — a GPU shading language, a JIT'd kernel, an FFI binding, embedded SQL — the generated artifact passing its compiler is a necessary but not sufficient proof of correctness. A construct can be accepted by the target compiler and still fault, mis-execute, or silently produce wrong results at dispatch time, because the compiler validates syntax and types but not the runtime contract (memory residency, addressing model, lifetime, alignment). The discipline: never let "it compiles" stand in for "it works" on a foreign-codegen boundary; run a real end-to-end kernel/query/call on the actual runtime before treating the construct as viable. The cheapest form is a throwaway probe — a tiny program that links the real foreign toolchain and exercises the single candidate construct against real inputs — which settles "does this construct actually run?" for pennies before the design commits to it. The corollary for code review: a verification line that cites only successful compilation of generated foreign code has not yet demonstrated the feature works.

### Deduplicating branches with opposite invariants needs a parameterized ordering knob, not a global swap

Description: When several branches share enough structure to invite extraction into one helper, the structure that is visually identical can hide a per-branch ordering or sequencing invariant that the inlined code silently encoded by position. Folding the branches into a shared helper makes that hidden invariant a single global choice — and if two branches needed *opposite* orderings, no global choice satisfies both. The trap is iterative: pick one ordering, one branch's tests go green and another's go red; flip it globally, the failures swap sides. The fix is not to keep flipping but to recognise the invariant is branch-specific and lift it into a parameter the helper takes (with a documented safe default), so each caller passes the ordering its branch requires. The general rule: before extracting a shared helper across branches, ask which sequencing each branch's inlined code was implicitly relying on; if the answer differs by branch, the shared helper needs that sequencing as an explicit argument, and each branch's choice deserves a comment naming why.

### A feature that "already works via existing filtering" still needs its gatekeeper checked for the new input shape

Description: A common plan-time shortcut for relaxing an admissibility restriction is "the downstream transformation already handles the general case, so we only need to loosen the check." When the transformer genuinely already generalises, the residual risk concentrates entirely in the gatekeeper — and an occurrence sweep over the function names the plan mentions will not find a rejection that lives in a *different* validation clause than the one being relaxed. The gatekeeper often carries several independent rejection paths (escaping-variable checks, uniqueness checks, recurrence checks), and the new shape can trip one the plan never enumerated. ### When one pass walks a body mixing kinds of elements, test the cross-product of what each kind does

Description: A transformation pass that walks a heterogeneous collection — a loop body containing both virtual and materialized statements, a list mixing several node kinds, a batch holding both cached and uncached entries — has behaviour that depends not just on each element kind in isolation but on how the kinds *co-occur and order* within one traversal. A test matrix that covers "two of kind A" and separately "one of kind B" can still miss the crossing case "kind A and kind B in the same body, where processing A's element reaches across to a not-yet-processed B's element." Staged or order-dependent processing (store-then-inline, allocate-then-resolve, register-then-reference) is especially prone: a pass that mutates siblings as it processes one candidate can touch a sibling that has not reached its own processing turn yet, violating an invariant that holds whenever the kinds are tested apart. The discipline: when one pass walks a body mixing element kinds, enumerate the cross-product of "what each kind reads/writes relative to the others within a single traversal," and build at least one fixture where the kinds co-occur in the order that stresses the staging — not only fixtures isolating each kind.

### `git diff --check` flags trailing whitespace only on lines you touch — and the editor hides it, so strip it in the same edit
Description: `git diff --check` (the whitespace linter that gates many review/CI hooks) reports trailing-whitespace and space-before-tab errors *only on lines that appear in the diff*. The trap compounds because most file-reading tools (here the agent's Read tool; also many editors with trim-on-display) do **not** render trailing whitespace, so the offending characters are invisible at the point of editing — you fix the line, it looks clean, and the check fails for a reason you can't see in the buffer. Mitigation: when editing a line in a file with loose whitespace hygiene, strip trailing whitespace on that line in the same edit. To *see* it, don't trust the editor — use `git diff --check` (or `sed -n '<N>p' | cat -v` to make the chars visible) and strip a single line with `sed -i '' '<N>s/[[:space:]]*$//'`. Generalises to any line-scoped diff linter (clang-format `--Werror` on touched ranges, pre-commit `trailing-whitespace` hook, EditorConfig CI): editing a dirty line inherits its latent lint debt, and the failure is invisible if your viewer trims whitespace on display.

### A pinned lint/test net-count is a whole-tree delta — re-measure after all edits
Description: When a lint or test gate pins a numeric budget — a `--max-warnings N`, a `lint:test-isolation` rule-violation count, an allowed-failure tally — that number is a **net** property of the whole tree, not a per-file increment you can reason about locally. ### A correct-by-spec normalization a fixpoint solver never reaches needs the solver-level test plus a documented reachability gap
Description: A constraint solver that runs to a fixpoint by re-substituting and re-partitioning its work-list on every re-entry can make two different deferred forms — "defer the original equation" versus "defer a normalized residual of it" — functionally equivalent for resolution, because the next iteration re-derives the same progress either way. ### Import the authoritative validator instead of re-mirroring its logic inline

### A dynamic await import() view defeats namespace spies — spy the real global transport instead
Description: When the code under test reaches a dependency through a *runtime* `await import("../mod.ts")` — a deliberate pattern to break a circular dependency — a `spyOn(modNamespace, "fn")` installed on the statically-imported `import * as modNamespace` view can silently register **zero calls** even though the call site is provably executed. The two import views (`import * as` at file-top vs. the per-call `await import()`) can resolve to different module-namespace objects under the test runner's module state, so the spy patches a binding the SUT never consults — and worse, the breakage is *full-file-specific*: a standalone one-test probe of the same path passes, masking the problem until the assertion lands in the real suite and reads as a non-vacuous green that is actually testing nothing. The robust fix does not chase the right namespace object; it drops below the indirection and spies a **true global transport** the call must traverse regardless of import-view identity. ### systemd-run --scope is not a pid-preserving cgroup escape — use KillMode=process on the unit
Description: When a short-lived process (a oneshot systemd unit, a keepalive tick) spawns a detached child that must outlive it, the cgroup-default `KillMode=control-group` reaps the child along with the parent on unit exit. The pid-preserving escape is to leave the spawn as an in-place `setsid`/`exec` (so the spawn API returns the child's *real* pid) and move the cgroup escape to the **unit** instead: set `KillMode=process` on the generated unit, which kills only the main process on unit stop and lets detached descendants survive. "Keep parallel constructors in sync" is general engineering hygiene, but the specific recurring shape here — a queue/record type with two serializers where a *dispatch-re-parsed* side-band field must land on both, fail-safe-guarded by an allow-list so absence means "ungated" — is a ludics-internal precedent worth a coder's recognition rather than always-loaded doctrine. It is the enqueue-side sibling of the proposal-pointer-verification family (verify both writers, don't trust one).

### An API-drift fix's occurrence list must include every file kind that shares the drifting code — compiled `.ml` examples, not just the failing `.md` block

Description: When a dependency's API drifts (a renamed/removed value like Bogue's `Draw.grey`) and the fix is "replace the broken call everywhere", the surface that triggered the task is often only a subset of the occurrences. In a docs-with-executable-examples repo — mdx prose blocks whose code is copy-pasted into compiled `.ml` example executables — the same broken expression lives in BOTH the `.md` mdx blocks and the `.ml` files, and they drift together. An occurrence list scoped only to the failing mdx block (what surfaced as a `dune runtest` mdx diff) silently omits the `.ml` copies, which fail `dune build` with the identical error. Scope the fix by grepping every file kind that can carry the drifting symbol (`*.md` AND `*.ml`) and verify with `dune build`, not just `dune runtest`: runtest's mdx layer evaluates only the `env=`-tagged blocks, so a `skip` block or a sibling `.ml` executable can stay broken without producing a runtest diff (it still breaks the build, but the proposal's narrow scope hides it from the spec).

Precipitating retro: `task-8f7e5362` round 1 (coder durable learning, 2026-06-25, PR curious-ocaml#13). The elaboration/proposal scoped the `Draw.grey` → `Draw.find_color "grey"` fix to two `chapter10/README.md` blocks, but a project-wide grep also hit `chapter10/chapter10.ml` (3 occurrences, a built executable per `chapter10/dune`). The coder found them only because the build failed until they were fixed too; the proposal's occurrence list was incomplete.

Filter decision: capture-textbook. "Fix all occurrences, not just the one that failed" is obvious to a competent engineer, but the specific recurring shape — a docs repo whose prose examples are ALSO compiled, so an API-drift fix must grep `.md`+`.ml` and `dune build` because `dune runtest`'s mdx layer masks `skip`-block and `.ml` breakage — is a precedent for the recurring "Fix broken test suite: Curious-OCaml" family worth a coder's recognition rather than always-loaded doctrine.

### A verification build/test run regenerates a tracked generated file, leaking it into the orchestration completion commit

Description: A repo can carry tracked files that a build/test step regenerates as a side effect — opam manifests under `generate_opam_files true` (dune regenerates `<pkg>.opam` from the `dune-project` package stanzas), mdx-rendered READMEs/site HTML, codegen outputs. When the committed copy on the base branch is stale relative to what the build emits, the very verification run you must perform to prove the suite green (`dune build`/`dune runtest`) dirties the working tree by regenerating that file — and the orchestration's done-time auto-commit then snapshots the dirty tree and ships an out-of-scope edit the reviewer bounces. The trap is recursive: any future build on the branch (or on the base) re-creates the file in the working tree, so it keeps coming back until the last action before signaling done is a cleanup. Mitigation: after the final green verification and immediately before signaling done, restore build-regenerated tracked files to HEAD (`git checkout HEAD -- <file>`), confirm `git status` is clean, and verify `git diff <base>..HEAD --name-only` lists only the intended source files. The permanent cure (regenerating the stale artifact on the base branch) is usually out of the task's scope.

Precipitating retro: `task-059ebb82` round 1-3 (coder durable learning, 2026-06-26, ocannl-staging). `arrayjit.opam` is dune-generated; every `dune build`/`runtest` re-added `"menhir" {>= "20180523"}` to its depends (arrayjit/ uses no menhir — the dep is inferred), because origin/master's committed copy is stale. The line leaked into the round-1 completion commit and recurred through rounds 2-3 until the working tree was cleaned as the final step. The sibling shape appeared in `task-8f7e5362` (curious-ocaml): `dune build` regenerates the root `README.md` and `site/*.html` from chapter sources, which prior fix commits had to leave unstaged.

Filter decision: capture-textbook. "Don't commit generated files / keep a clean tree" is competent-SWE hygiene the reviewer catches, but the specific recurring shape — the green-proving verification step itself silently regenerating a stale-on-base tracked artifact that the orchestration's completion auto-commit then captures, costing review rounds — is a precedent worth a coder's recognition rather than always-loaded prompt doctrine.

### A pipe upstream of the exit-code check reports the pipe's last stage, masking a red build/test

Description: `dune runtest | tail` (or any `cmd | filter`) makes `$?` report the *filter's* exit status, not `cmd`'s — a non-`pipefail` shell only surfaces the last pipeline stage. Since `tail`/`grep`/`head` almost always exit 0, a failing build or red test suite reads as green and the coder can sign off `done` on a broken tree with no error anywhere. The fix is to never put the command whose status you care about upstream of a pipe in the same line you check: capture directly (`cmd > log 2>&1; echo $?`) and then grep the log, or `set -o pipefail` before the pipe. This pairs with the dune `diff --git` rendering trap — both belong to the "the exit code is the only honest signal" family for build/test drivers.

Precipitating retro: `task-059ebb82` round 1 (coder durable learning, 2026-06-26, ocannl-staging). A `dune runtest | tail` invocation nearly signaled `done` on a non-green tree because `$?` reported `tail`'s status (always 0), masking the red suite; resolved by switching to `dune runtest > log 2>&1; echo $?` then grepping the log for `diff --git`.

Filter decision: capture-textbook. A classic shell pitfall competent engineers know, but it is recognition-shaped and silent (no error is raised; the run merely "looks" green), and it recurs across every build/test driver invoked over a pipe. Journaled as a precedent rather than promoted to always-loaded doctrine.

### Validate a promoted build-artifact target from a clean state — stale intermediates mask a missing dep

Description: When verifying that a dune `(mode promote)` / build-artifact rule produces the *correct* artifact, run `dune clean` first: the honest acceptance harness is `dune clean && dune build @alias`, not a bare `dune build @alias`. Stale files left in `_build/` by a prior build of other targets can satisfy a rule that does not actually declare them as deps, so an incomplete build "succeeds" and the missing-dependency bug stays invisible. The dune mechanic behind it: a `(copy_files ...)` stanza creates *passive* copy rules — they do NOT run automatically when you build a sibling target in the same directory; they fire only when listed in that target's `(deps ...)` or targeted explicitly. So a rule consuming copy_files outputs must list them in its own `(deps ...)`. Pair the clean-state run with a content-fidelity assertion rather than mere file existence: for a generated PDF, assert byte size and `/Subtype /Image` object count (`len > 10_000_000`, `count >= 20`), not `ls` success — an incomplete artifact (2MB, 1 image) passes existence but fails both content checks.

Precipitating retro: `task-1ab288b7` (coder durable learning, 2026-06-26, curious-ocaml). The `@pdfs/new_book` rule was missing 20 chapter-image deps; rounds 1-2 passed falsely because earlier builds had left the images in `_build/default/pdfs/`, so pandoc found them off-deps and emitted a complete-looking PDF — until a `dune clean` build exposed the 2MB/1-image incomplete artifact. Fixed in commit `ec0000c` by listing all 21 image deps; acceptance fixed to `dune clean && dune build @pdfs/new_book` plus the size + image-count check.

Filter decision: capture-textbook. "Build from a clean state" and "list your deps" are competent-SWE hygiene the reviewer can catch, but the specific recognition-shaped trap — stale `_build/` intermediates silently masking a missing-dep bug so a promoted-target rule passes verification while emitting an incomplete artifact — cost two rounds and is worth a coder's recognition rather than always-loaded doctrine.

### A proposal's "no change to X needed" premise carries a claim — verify it before honoring the scope restriction

Description: A proposal that says "leave X alone / no change to X — it is correct as-is" is asserting a *factual premise*, not just drawing a scope boundary. The negative-scope instruction is only as sound as its justifying reason; when the reason is false, the restriction does not hold. Before honoring a "don't touch X" boundary, verify the premise the way you would any load-bearing proposal claim (a line-level grep / build check at the actual call site — cf. the sibling entries on a proposal's writer-pointer red herring and its "existing code already satisfies this property" claim). If the premise is factually wrong, make the needed change, declare it with a `scope-expansion:` trailer in the commit message, and let the reviewer rule on it at review time — silently obeying a wrong premise ships a broken result, while silently expanding scope hides the decision.

Precipitating retro: `task-1ab288b7` (coder durable learning, 2026-06-26, curious-ocaml). The proposal's AC5 parenthetical — "the pandoc invocation and `new_book` rule are correct as-is, no change to `pdfs/dune`" — was false: the rule was missing 20 image deps. The coder made the change anyway under a `scope-expansion:` trailer (commit `ec0000c`), which the reviewer accepted. Same verify-the-proposal's-claim family as the existing entries "A proposal's named writer pointer can be a read-only red herring" and "A proposal's 'existing code already satisfies this safety property' claim needs a line-level callsite grep" — here for a *negative-scope* premise.

Filter decision: capture-textbook. Reinforces the permissive-scope doctrine (record limits as "doesn't need to broaden," not "must not") without bloating always-loaded prompts; the recurring, recognition-shaped angle is that a *negative-scope* instruction smuggles a verifiable premise, and the clean remedy is scope-expansion-with-declaration, not silent obedience.

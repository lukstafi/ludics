---
name: ocannl-ci-red-triage
description: Cloud routine that claims and triages a red CI run on ocannl-staging master; fired by ci-env.yml on a master push red and by ci.yml on a scheduled master red, with a daily backstop sweep
---

You are the CI-red triage routine for the OCANNL staging repository (lukstafi/ocannl-staging, now with scope including upstream ahrefs/ocannl). You fire when CI fails on master (the workflow POSTs the failing run's context into this message via the fire API), and on a daily backstop sweep. Remote CI covers the CPU (cc) backend only; this cloud session has no GPU — expected and fine. The sandbox has no `gh` CLI — use the GitHub MCP tools (load via ToolSearch, e.g. mcp__github__actions_list, mcp__github__get_job_logs, mcp__github__search_issues, mcp__github__issue_write).

1. FIND: a verdict is a JUDGED run (concluded green: `success` or `neutral`; or red: `failure`, `timed_out` or `startup_failure`, which no job of the run could report to this routine; `cancelled`, `skipped`, `stale` and `action_required` judged nothing), and a verdict speaks only for its own workflow AND event. Master has two: `ci-env` push runs, one clean-room build per merge (a fresh checkout, dependencies solved from the opam files alone, ubuntu only, minutes), and `ci` schedule runs, the full matrix daily at 03:00 UTC and the only Windows and OCaml-floor coverage. `ci` push runs ended with gh-ocannl-1816 (2026-11-02): an old one is history, never a live verdict, and an open claim on one is closed as below by a later green `ci` schedule verdict, whose matrix holds every job the push matrix ran. If this message includes a specific failing run (URL/id/sha), triage THAT run — but first confirm it is still the live verdict: skip it as stale if a NEWER green verdict of the same workflow and event exists on master. With no run named (backstop sweep), first close your own flake claims: an open `CI red on master@…` issue carrying this routine's triaging note is closed, with a comment citing the run, when a later green verdict of the same workflow and event has a head at or after the claimed commit AND the claim recorded the failure as a flake (step 4's re-run went green, or the logs show runner, network, fetch or timeout trouble rather than a test verdict); a deterministic break stays open for whoever fixes it. Then list recent completed runs on branch master of `ci-env` (push event) and of `ci` (schedule event), and collect the failures that no newer green verdict of the same workflow and event supersedes. A `workflow_dispatch` run named `ci at <sha>` (step 4's re-runs) judged the commit its name gives, never master's head. If nothing relevant is red, say so and stop.
   Every verdict covers a SPAN: the merges on master's first-parent history after the head_sha of the previous verdict of the same workflow and event, up to the failing run's head_sha. With no previous verdict in reach (a new workflow, expired runs), the lower bound is unknown: say so and attribute no merge. A span with no merge (a scheduled red at the head the previous scheduled verdict judged) points at no change of ours: the dependency cone, the runner image, or a flake. `ci-env` keys each master push's concurrency group on its own commit and cancels none, so every merge gets its own verdict and a push span is normally that one merge (more only when a nearer push run has not concluded or judged nothing); a scheduled `ci` run is daily, so its span is about a day of merges. If that previous verdict was red in the same job with the same error, the break is older: follow the streak back while the failure stays the same, and take the span of the first run that shows it. A previous red with a different failure is a different break and does not extend the span.

2. CHECK FOR AN EXISTING CLAIM before anything else, once per collected failure: search open issues on ahrefs/ocannl and open PRs on lukstafi/ocannl-staging for the failing commit SHA (short or full) or the failing run. A match on the workflow name alone is not a claim: every claiming issue names its workflow, so an older open claim for the same workflow may be about a different regression — read it and confirm it covers THIS failure (the same workflow and event, and the same SHA or the same failing job and error) before treating it as owned: a push red and a scheduled red at one SHA are two failures. If a claim covers it, optionally comment with genuinely new information, then move on to the next collected failure — someone else owns this one; stop only when every collected failure is claimed.

3. CLAIM: open an issue on ahrefs/ocannl titled `CI red on master@<short-sha>: <workflow> (<event>) — <span>`, the span written as `unknown lower bound` when there is none, `no new merge` when empty, as the merge's PR (`lukstafi/ocannl-staging#N`) when it is one merge, and as `lukstafi/ocannl-staging#A..lukstafi/ocannl-staging#B (K merges)` otherwise, with the failing run URL, each merge of the span with its PR (always the `lukstafi/ocannl-staging#N` form: a bare `#N` in an ahrefs/ocannl issue links an unrelated upstream number), and a note that this routine is triaging.

4. RE-RUN, once, to tell a deterministic break from a flake, before naming any culprit, the way the red's workflow allows. Load the GitHub MCP's run-trigger tool through ToolSearch (search "run workflow"; the consolidated GitHub MCP toolset that `actions_list` and `actions_get` come from calls it `actions_run_trigger`). A `ci-env` push red: ci-env.yml takes no dispatch, so re-run the failed run's failed jobs (method `rerun_failed_jobs`), which rebuilds the same commit with that commit's workflow file, solving the dependencies fresh again; the new attempt replaces the run's conclusion, so wait for that run's next attempt (minutes). A red attempt fires this routine again, and that session finds this claim at step 2. A `ci` scheduled red: dispatch `ci.yml` (method `run_workflow`) on ref `master` with `expected_sha` set to the failing run's full head_sha, adding `windows_only: true` when only Windows jobs failed, or `ocaml_compiler: 5.3.x` when only the OCaml-floor job failed; when the failed jobs fall in more than one of those groups (Windows, the OCaml floor, the rest), take the ordinary dispatch when any of the rest failed, else the Windows one. ci.yml builds that commit, names the run `ci at <sha>`, and does not fire this routine on its red. Note the time before dispatching, take the run of that name created after it (an older re-run of the same commit carries the same name), and wait for it (about 45 minutes; a Windows-only run 1-3 hours). Classify each failed job of the original run on its own (a `startup_failure` has no jobs: classify the run as a whole, deterministic when the re-run fails to start too), in the claim: deterministic when the re-run's same job is red with the same error, a flake when that job is green, and otherwise UNCLASSIFIED, with the reason. Unclassified covers a job the re-run did not run (a mixed red's jobs outside the dispatch it took), a re-run that judged nothing (`cancelled`, `stale`, `action_required`) or was never made (no such tool loads, the dispatch is refused), and a green dispatched re-run after `.github/` changed since the red commit, since the dispatch runs master's current `ci.yml`, not the red commit's. Only a red whose every failed job is a flake ends here; the step 1 sweep closes its claim once a later green verdict covers it. Anything else goes on.

5. DIAGNOSE: read the failing job logs, the span's diffs, and the checkout's AGENTS.md conventions. Prefer diagnosis from logs and git history. Name a culprit only on evidence: a one-merge span's merge, or within a longer span the merge whose diff the failure ties to. A `ci-env` red solves its dependencies fresh, so its one-merge span names that merge only when the merge's diff ties to the failure: a solver error or a dependency's build failing after a merge that touched no opam file points at the dependency cone. Retitle the claim with it and comment on its PR. A span nothing narrows stays named as the span, for a local session to narrow by dispatching `ci` at commits inside it. Only build the project when a candidate fix needs verification: `opam install . --deps-only --yes`, then `dune build @check`, then the narrowest test alias covering the failure (AGENTS.md documents the alias conventions; pin `OCANNL_BACKEND=cc`). If the toolchain is not preinstalled in this environment, a from-scratch opam switch takes 10-20+ minutes — weigh that against the value of verification, and stop at diagnosis if it does not fit.

6. FIX (only when verified or high-confidence): branch `ci-fix/<short-sha>-<slug>`, commit per the repo's commit conventions, push, and open a PR against master on lukstafi/ocannl-staging linking the failing run and the claiming issue. Do NOT merge the PR; never force-push; never rewrite existing branches. Update the claiming issue with the PR link.

7. OTHERWISE: update the claiming issue with your diagnosis — the failing test, the first bad commit if determinable, what you tried and ruled out — so a local session can take over. An honest partial diagnosis beats a speculative patch.
